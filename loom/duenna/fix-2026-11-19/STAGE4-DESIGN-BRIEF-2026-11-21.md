# Stage 4 — Design Brief (for settlement with Vane before build)

Loom prototype, from spec v0.1 Rev 9 (d7d65c96) + Amendment A1, on the accepted Stage 2 harness (dbdf1769) and the accepted Stage 3 build (1e69f5d3 + correction round 57e081a3). Prepared by Remmy, 2026-11-21, after Vane's Stage 3 acceptance. Status: PAPER — no build until the design is settled in the Remmy–Vane loop.

## Scope

Stage 4 is the last mechanical stage of the commissioned slice: the weave seals and the independent checker (§7), closing the structural lifecycle for real.

1. **Seal attempts (§7).** Attempted after **every accepted commit**, and once more at run close if the last accepted commit was not already followed by an attempt. Attempts are unconditional: an open structural tension never prevents, delays, or conditions one. Each attempt runs the structural checks against the current derived state — dependency integrity (S1), version consistency (S2), schema conformance of the state, hash-chain continuity to the sealed position — and is recorded as a `SEAL_ATTEMPTED` event with an explicit outcome. On `pass`, a seal is issued for that event position recording: the position; the contributions included since the last seal; the checks performed; and the outstanding semantic questions, each marked examined-by-whom or *unexamined* — with the record stating in terms that a seal never implies semantic clearance. On `fail`, no seal is issued and the event records which checks failed and the affected records.
2. **The structural lifecycle, genuinely (§7).** A structural tension's identity is the pair (check name, affected record set). A failing check raises it (`TENSION_RAISED`, origin `checker`, status `open`) as part of the same attempt processing — unless one with that identity already stands open, in which case no duplicate is raised and the attempt records its finding against the standing tension. A later attempt whose checks pass over a state where the inconsistency no longer appears resolves it (`open → resolved`, `TENSION_STATUS` whose evidence is the passing attempt's event id). This delivers the **genuine TV-13 resolution path** deferred from Stage 3.
3. **The independent checker (§7).** Its own implementation of the check functions, executed as a separate process against the event history — not a second entry point into shared logic (standing safeguard 4 from Stage 1). Before any run opens, **both** implementations (the engine's checks and the checker) run against the Annex E test-vector pack — canned histories and contract cases with known-correct outcomes, authored from the specification's text, not derived from either implementation's code. Both must agree on every vector; the pack's hash is recorded in the run record; a disagreement means the run does not open. A seal the checker does not reproduce is not a seal, and the discrepancy is recorded.
4. **Vectors in scope:** TV-1 (the non-circular structural lifecycle, incl. the fault injected into the live derived state only), TV-6 (one inconsistency, one tension — no duplicates across repeated failing attempts), TV-8 (stood-down follows the declared regions, exactly — the close-out accounting form), and TV-13's genuine resolution half. Each as a named executable test with observable evidence.
5. **Carried hardening item (from Vane's Stage 3 acceptance note, non-blocking there, built here):** malformed event payloads must convert to a controlled `ReplayHalt`, never a Python `TypeError` — e.g. a hash-valid event whose tension `type` is a list or object, or whose transition `from`/`to` values are unhashable. Negative replay tests in the Stage 3 corrections style.
6. **The closing exercise.** After the above: one full mechanical lifecycle run exercising the whole slice end to end (opens, reads under breadth, contributions, examinations, assessments, claims, tensions to resolution/standing, seals after commits, a structural fault raised and resolved, run close with its final attempt), with the complete Annex E TV-1..TV-20 evidence pack executed and presented together — the package for the later integrated examination of the whole commissioned slice. Still mechanical/driver-run; **no live agents**.

## Not in scope

Live agents (unauthorised); the observer's next round (follows the mechanical lifecycle); anything beyond the commissioned slice.

## Design questions for Vane (Remmy's proposed answers in brackets)

- **Q1 — Checker independence boundary.** The checker re-implements state derivation and the §7 checks from the spec text, runs as a separate process, and reads the event store directly (read-only). It imports **no** engine or harness code. It does use the same canonical-JSON + hash primitives — those define the record format itself, as a file format defines its reader; the *logic* (fold, checks, verdicts) is independently written. [Proposed: this is the line — format primitives shared, all logic independent. If you want the primitives re-implemented too, say so and it will be.]
- **Q2 — Attempt placement and grouping.** Per §4's commit order (tension protocols, then the seal trigger): the attempt is evaluated as part of the accepted commit's atomic group, appended after the derived tension/facet transitions as the `SEAL_ATTEMPTED` event, followed in the same group by any structural `TENSION_RAISED` / `TENSION_STATUS` events the attempt produces, deterministically ordered. [Proposed: yes — one group per commit, exactly as Stage 3's grouping contract extends.]
- **Q3 — The vector pack's authorship and record.** §7 wants the pack authored from the spec's text by the examiner side, not derived from either implementation. In this loop the honest form is: Remmy authors the pack from Rev 9's text, Vane examines the pack itself as part of this round (authorship disclosed, never dressed as independent), and the pack's hash is recorded in the run record — proposed as a field in the `RUN_OPENED` payload for runs opened under Stage 4, with the pre-open validation exercised in the suites. [Proposed as stated; the alternative — Vane authors the pack — is yours to choose, and would be stronger.]
- **Q4 — TV-1's fault injection.** Exactly per the vector's own setup: the fixture harness drops a region record from the **live derived state only**; the event history stays entirely valid, so replay is never contradicted — the divergence between live state and replay is what the checks exist to catch. The injection point is the service's in-memory derived state, performed by the test driver, labelled as fixture in the evidence. [Proposed as stated.]
- **Q5 — Run close and the external anchor.** `RUN_CLOSED` carries the final state hash and the chain head; the external anchoring in this environment is the shelved record itself — the closing exercise's history and head hash are recorded in the build notes and shelved, which is the anchor the slice can honestly offer. [Proposed as stated.]
- **Q6 — Starvation measures (§7).** The measures (rejections by outcome, consecutive rejections, wakes between commits, changed-read diff sizes, progression) are fold/history-derivable reporting. [Proposed: computed as a derived report in the closing exercise only — the machinery is a read over the record, not new state; a live run's §9 accounting would consume the same derivation. If you want the derivation built as a named module with its own tests, say so.]
