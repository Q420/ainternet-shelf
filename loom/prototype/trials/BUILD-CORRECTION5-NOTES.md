## The defect (as examined)

In `ledger/gt_release.py`, step 5 read the sealed material with `subprocess.run(..., capture_output=True, text=True)` and step 6 hashed `out.stdout.encode()`. Text mode decodes the returned bytes and performs newline normalization; re-encoding the resulting string does not guarantee the original byte sequence, so the digest was not a byte-exact hash of the subprocess output — and the examiner output was likewise written in text mode. Bytes differing only in ways text mode normalizes (e.g. LF vs CRLF) could pass the check while different bytes were released.

## The correction — the post-anchor read and write are binary, end to end

**Declared code change — `ledger/gt_release.py` only** (plus its regenerated bytecode; verified by diff against the round-4 shelf copy: the only hunks are the two docstring blocks and the step 5/6 + write block — `find_scoring_order`, `manifest_binding`, `sealed_packet_binding`, `selected_packet_sha256`, and the anchor parse/validate functions are untouched):

1. **Step 5 captures raw bytes.** `subprocess.run(["runuser", "-u", "loomgt", "--", "cat", GT_FILE], capture_output=True)` — no `text=True`, no decoding. The material is held as a `bytes` buffer (`material = out.stdout`). The read-failure branch decodes `stderr` with `errors="replace"` for its diagnostic message only; no material bytes pass through it.
2. **Step 6 hashes the buffer directly.** `read_sha = hashlib.sha256(material).hexdigest()`, required to equal the packet hash from the sequence's `GROUND_TRUTH_SEALED` event — the same value steps 2.5 and (round 4's) 6 bind against, read from the sealing record, never hardcoded.
3. **On mismatch:** refusal at stage `post-anchor-binding` with both digests recorded, **before any examiner output is created or written** (the output file is only ever opened on the success path). The access event and its anchor remain in the sequence as the record of the attempted access — not rolled back, exactly as in round 4.
4. **On success:** the exact same verified buffer is written with `open(out_path, "wb")` — no reread, no decode/encode, no transformation of any kind between verification and write. The result's `material_sha256` is the step-6 digest of that same buffer.
5. **Nothing else changed behaviour.** Steps 0–4 and the step 2.5 pre-verification are as they were. **Noted, not changed (per the dispatch):** step 2.5's helper `selected_packet_sha256()` runs `sha256sum` with `text=True` — but there the digest of the *file* is computed by `sha256sum` itself over the raw bytes, and text mode touches only the tool's ASCII hex-digest output, not the hashed material; the examiner's blocker concerned the released material's read, so the helper stands as it was.

## The new negative test — LF-to-CRLF change between pre-verification and the post-anchor read

**Construction.** The sealed Annex D packet is pure LF (5,189 bytes, 68 LF, no CR anywhere). The variant is the packet's bytes with every LF replaced by CRLF (5,257 bytes), SHA-256 `abcbc36ec3da5a215cff83e67505ac182d1137ba85eca7b035b520bb4d4fbbad`, held in the gt-store as `annex-d-packet-crlf-variant.txt` (loomgt, mode 600). Phase 0 records why this targets the exact defect: a text-mode decode of the variant (universal-newlines translation, as `subprocess text=True` performs) followed by re-encoding reproduces the packet digest `54a70da4…e40f` exactly — a simulation of the round-4 step-6 computation, recorded as a simulation in the evidence — i.e. **the round-4 check would have computed the sealed digest over these changed bytes and released**; the binary check must refuse.

The selected file was a fresh byte-exact copy of the Annex D packet (`gt-store/annex-d-packet-correction5-crlf-copy.txt`), so step 2.5's pre-verification passed on the genuine sealed bytes. The sealed original was never written by this test.
