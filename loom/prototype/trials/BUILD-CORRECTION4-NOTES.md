## The defect (as examined)

In `ledger/gt_release.py`, the selected packet's digest was verified **before** the access append + anchor (step 2.5, `selected_packet_sha256()` hashing the path in one subprocess), but after the access event was anchored a separate `cat` read the path again and the returned bytes were written to the examiner output **without comparing their digest** to the expected sealed-packet hash. A writable selected file could change between verification and release — a check/use gap.

## The correction — the release decision now binds to the bytes actually read

**Declared code change — `ledger/gt_release.py` only** (plus its regenerated bytecode; verified by diff against the round-3 shelf copy: the only hunks are the docstring and the step 5/6 block — `find_scoring_order`, `manifest_binding`, `sealed_packet_binding`, `selected_packet_sha256`, and the anchor parse/validate functions are untouched):

1. **Step 5 unchanged in form:** after `GROUND_TRUTH_ACCESSED` is appended (step 3) and anchored (step 4), the material is read as the `loomgt` identity, exactly as before.
2. **New step 6 — post-anchor digest binding.** The SHA-256 of the **exact bytes just read** is computed and required to equal the packet hash from the sequence's `GROUND_TRUTH_SEALED` event (the same value step 2.5 binds against, read from the sealing record, never hardcoded). The bytes are written to the examiner output **only after** that comparison passes. The successful result now also carries `post_anchor_read_sha256`.
3. **On mismatch:** the release returns `{released: False, stage: "post-anchor-binding"}` with both digests, the sealing event's seq, and the access event's seq + anchor commit recorded. Nothing is written to the examiner output. The access event and its anchor are **not** rolled back — they remain the accurate record of the attempted access.
4. **Step 2.5's pre-verification stays exactly as it was.** This round ADDS the post-anchor binding; it removes and weakens nothing.

## The new negative test — swap between pre-verification and the post-anchor read

**Method, and why it exercises the actual gap.** The gap existed between two concrete points in `release()`: the step-2.5 hash of the selected path, and the step-5 read of the same path after the access anchor. The test interposes at the last event before the read: the real `anchor.anchor_head` call for `GROUND_TRUTH_ACCESSED`. The invoker (`tests/invoke_release_swap_once.py`, a fresh process, like every case) wraps `anchor.anchor_head` in-process: the **real** anchor executes first — the access head is written to the shelf staging tree and pushed to Q420/ainternet-shelf (anchor commit `12e09d4fe6d96faf03625b60dbc36aeedca7c187`) — and immediately after it returns, before `release()` performs its step-5 read, the wrapper replaces the selected file's bytes (`runuser -u loomgt -- cp <tampered> <selected>`). Neither `gt_release` nor `anchor` is altered on disk; the wrap exists only inside the test process, and the file on disk genuinely changes between verification and read.

The selected file is a **byte-exact copy** of the Annex D packet (`gt-store/annex-d-packet-correction4-copy.txt`, created for this test, owned by `loomgt`, mode 600) — so step 2.5's pre-verification passes on the genuine sealed bytes. The sealed original (`gt-store/annex-d-packet.txt`) is never written by this test. The tampered content is plain ASCII marked text in the gt-store, SHA-256 `5b27e5f2b343021f3fdd332d8a38409b05984fd2fc0217357ad624e520f42527` (its `sha256sum`-as-`loomgt` digest and the digest of the text written agree, so the post-anchor read digest is directly comparable).

**Result — refused, nothing released, access record retained:**
- Swap record: selected digest before swap `54a70da4…e40f` (= the sealed packet hash — pre-verification passed on genuine bytes); after swap `5b27e5f2…2527` (the tampered digest).
- Release result: `released: False`, stage **`post-anchor-binding`**, reason naming both digests; `expected_packet_sha256` = `54a70da4b02f578a88a406df2b1b8a14c244125d2a50bfd9e4172dde23aae40f`, `post_anchor_read_sha256` = `5b27e5f2b343021f3fdd332d8a38409b05984fd2fc0217357ad624e520f42527`.
- Examiner output file: **absent** — no material reached the output.
- The ledger head moved 9 → 10: the `GROUND_TRUTH_ACCESSED` event (seq 10) **was appended and remains in the sequence** (the final chain lists both access events, seqs 10 and 11, followed by `LAYER4_RECORDED`; the 12-event chain verifies).
