## The defect this repairs

The worker chooses which files to read but not how much it retrieves: `sandbox.read` returns a whole document, the result enters the next package in full, and the package re-carries it thereafter. Attempt 6's composition request (134,844 bytes) was refused by the provider (HTTP 413) — the pattern now has a hard external limit behind it, not only a design objection.

## The new tool contract (registry v3; v1/v2 frozen for history, both copies amended together)

Three retrieval tools, added to a new `tool-registry-v3` in the framework registry and the checker's independent copy, rendered in the worker's catalogue under the A3-CAT contract (assemblies declare the new catalogue contract; historical assemblies keep their exemption):

1. **`sandbox.list`** — discovery without contents. For a permitted path: the file's name, size, and **structure map** (for markdown/text: its headings with line numbers; for other text: line count). Returns no body text.
2. **`sandbox.read_range`** — a bounded slice: a permitted path plus a line range (or a heading's section, by heading text). The executor enforces a **hard result ceiling** (proposed: 12,000 bytes per result); a range whose content exceeds the ceiling is **refused with a recorded reason naming the bound**, and the worker narrows — a refusal is information, never a silent truncation. **Exact semantics (§2 of the corrections):** lines are numbered from 1; a line is the bytes up to and including its newline (the final line may lack one); a line range [start, end] is **inclusive at both ends**. A heading section begins at its heading line and ends immediately before the next heading of the same or higher level (equal or fewer `#`), or at end of file; deeper nested headings lie inside the section. A heading request must match **exactly one** heading: if the text matches several, the request is **refused as ambiguous**, the refusal naming the match count and their line numbers (metadata inside the boundary), and the worker disambiguates by line range. No request is ever resolved by guesswork. **Byte windows (INDEX 240, correction 3):** for a range consisting of a single line, `sandbox.read_range` accepts an optional byte window — `byte_start` / `byte_end`, 0-based, start inclusive and end exclusive — returning that slice of the line, subject to the same per-result ceiling. This is the path the oversized-line stub advertises, and it succeeds: the worker fetches the line in ceiling-sized slices. **Straddling characters are assigned deterministically to exactly one slice (INDEX 242, correction 3), guaranteeing lossless reconstruction:** the served start advances to the first character boundary at or after the requested start (a character straddling the start belongs to the previous slice); the served end **extends** to the first character boundary at or after the requested end (a character straddling the end belongs to **this** slice). Adjacent requested windows therefore tile the line exactly — the next slice's start advances to precisely where this slice's extended end fell — with no gap and no duplication, and the concatenation of the slices reproduces the original line **byte-for-byte**. Because the end-extension adds at most 3 bytes, the maximum requestable byte window is the per-result ceiling **minus 3**, so a served slice never exceeds the ceiling. **The actual window served is what the record's provenance carries** — the slice returned, its served byte window, and its hash are exact.
3. **`sandbox.search`** — search within permitted material: a query string plus an optional path; returns matching passages (the matching line ± up to 2 context lines, each passage labelled with its file and line numbers). **Completeness and overflow (§1 of the corrections):** matches are ordered deterministically — by path, then by line number — and returned in **pages**: each page independently respects the ceiling and a passage cap (proposed ≤ 40 lines per page). A page never ends mid-passage; if the next passage would breach the ceiling, the page ends before it. Every search result states `total_matches`, how many this page returns, and — when more remain — a **continuation**: the worker repeats the query with the returned page offset to receive the next deterministic page. A result never silently looks complete. A single match whose minimal form (its matching line alone) exceeds the ceiling is reported as a **stub** — path, line number, line byte size, no content — which the worker can then fetch exactly in slices via `sandbox.read_range`.

**`sandbox.read` is unchanged for files within the ceiling**; a read whose content exceeds the ceiling is refused on the same terms as an oversized range, naming the bound — whole-document injection of large material becomes impossible through any door, not just discouraged.

## §3a — The aggregate per-package ceiling (INDEX 240, correction 1)

A per-result ceiling does not bound a package: several retrievals in one iteration present together in the next. The scope therefore defines an **aggregate per-package retrieval ceiling** (proposed: **36,000 bytes** of retrieved content per package — three times the per-result ceiling; a design bound, named as such). The accounting is derived from the record: the aggregate for the package now forming is the sum of the retained content sizes of retrieval outcomes settled since the previous package was built. **Enforcement is pre-execution**, at the same doorway bounds check that verifies the grant: a retrieval request is admitted only if *aggregate-so-far + the per-result ceiling* (the request's worst-case return) **≤ the aggregate ceiling**. **Serialization (INDEX 242, correction 1): retrieval dispatches are processed serially** — when one model response carries several retrieval requests, each dispatch's outcome **settles before the next request's admission check runs**, so the accounting at every check already includes every previously admitted request's actual settled size; no two requests are ever admitted against the same settled total. The accounting is closed over unsettled state: a retrieval whose outcome settles as **uncertain** counts its **full per-result ceiling** against the window's aggregate for the remainder of that window (its content may exist; the bound assumes the worst), and an admitted request can dangle into a later package in no case — the loop's existing stall discipline closes dispatch accounting before any stall is recorded, so a window never ends with an admitted-but-unaccounted request. **The checker verifies all of it from the record**: for each package window, settled retrieval sizes plus the ceiling for each uncertain retrieval in that window must total ≤ the aggregate ceiling. Otherwise the request is **refused before dispatch**, the refusal recorded with the aggregate bound and the remaining allowance named, and the worker chooses differently — proceed to compose, or retrieve something smaller in a later iteration, when the allowance resets as the next package is built. The guarantee is absolute, not behavioural: no package's retrieved content can exceed the aggregate ceiling regardless of how the model asks. The checker verifies the accounting from the record (the refusal's figures are recomputable from the settled outcomes it cites).

## Boundary enforcement (the manifest is the wall, for every operation)

Every retrieval operation — list, range, search, read — is admitted by the doorway under **one of two authority paths (INDEX 242, correction 2), enforced by the doorway, not merely described**: **(a) Source retrieval** — the path lies under `sources/`; admission requires the retrieval grant **and** the path's membership in the case's sealed evidence boundary (the manifest's files). **(b) Scratch retrieval** — the path lies under the designated `scratch/`; admission requires the **separately sealed scratch grant** for that path, and nothing else: scratch is never treated as source evidence, and the scratch grant exempts no other path from the manifest — a path under neither scope is refused. Each retrieval outcome records **which authority path admitted it**, and the checker preserves the distinction: a source outcome must show boundary membership, a scratch outcome the scratch grant, and any outcome whose recorded basis does not match its path's scope is a correspondence failure. Search results and metadata obey the same boundary: a listing shows only permitted material; a search over a non-permitted path is refused; no sizes, headings or existence signals leak from outside the boundary. A request outside the boundary is a doorway refusal, recorded as today.

## How results enter the package

A retrieval result enters the next package as exactly what was returned — the bounded piece, with its provenance label (file, range/section, query). Nothing is auto-injected: the package carries the assignment, the catalogue, and the results the worker actually pulled, in the order it pulled them. Successive requests are the worker's: what it retrieves next is decided from what it has already seen, inside the existing loop and its step ceiling.

## Context retention across iterations (§4 of the corrections — stated explicitly)

The loop builds each iteration's package from the record delta since its previous cursor. The rule for retrieval, made explicit: **a retrieval result is presented in the package of the iteration immediately following its dispatch, and is not automatically re-presented in later packages.** A package's size is therefore bounded by construction — the case view plus one iteration's results (each ≤ the ceiling) — and context overload cannot re-form by accumulation. The worker reasons across successive retrievals through two levers, both existing mechanisms — **no new memory subsystem is introduced**:

- **Re-retrieval.** Any earlier result can be pulled again by repeating the operation: same parameters return the same bytes under the same recorded hash. Deterministic, recorded, and cheap on a fast route; the step cost is real and is counted (it feeds the step-ceiling evidence).
- **The worker's own notebook — under its own explicit authority (INDEX 240, correction 2).** The notebook lives in a dedicated **`scratch/`** location in the worker's sandbox, **outside the case's evidence boundary and outside the manifest**. It is not covered by the sources read grant and this scope does not pretend otherwise: the assembly's grants must name scratch explicitly and separately — write authority over `scratch/` and retrieval/read authority over `scratch/` — distinct in the sealed record from the sources scope, so no examiner can mistake notebook content for source evidence, and every retrieval outcome's recorded path shows which scope it drew from. What the worker writes there is its own retention decision, under the same bounds. **Qualification:** the same-parameters-same-bytes guarantee holds for the pinned, immutable sources; for scratch it does not — the worker may modify its own notes — and it does not need to: each retrieval's retained outcome preserves **the version actually retrieved** (content, hash, size), so the record always shows which version of a note the worker was holding.

The durable memory of the work remains the record alone; the sandbox is the worker's scratch. What the worker retains is its choice, exercised through pulls and notes — never an accumulation the framework imposes.

## Provenance and record evidence

Retrievals are tool acts under the existing A2 machinery — request (with its parameters), dispatch intent, start, outcome — so the record already carries them. **Provenance, closed (§3 of the corrections): the exact returned content is retained in the authoritative record.** The retrieval outcome's payload carries the operation, its parameters, the path, the returned content itself (bounded by the ceiling, so at most 12,000 bytes per result), and the content's **sha256 and byte size** as separate recorded fields. Reconstructibility therefore rests on the record, never on the digest alone: an examiner reads the exact bytes the worker was given from the outcome itself. **The checker verifies it**: within dispatch correspondence for v3 retrieval outcomes, the checker recomputes the sha256 and byte size over the retained content and compares them against the recorded fields — a mismatch is a correspondence failure. The checker gains the v3 registry entries and no new check kinds beyond that verification.

## Witnesses (deterministic; stub model where a worker is needed)

- **R1 Discovery without contents:** `sandbox.list` over the three run sources returns structure maps whose total size is a small fraction of the corpus, and contains no body text beyond headings.
- **R2 Selective retrieval:** a scripted worker retrieves one named section of the index tail (e.g. a single INDEX entry) and the returned bytes match that section exactly — the rest of the file never crosses.
- **R3 The bounds hold:** an oversized range request and an oversized whole-file read are each refused with the bound named; nothing partial is returned. **The aggregate bound:** a scripted worker requesting four ceiling-sized retrievals in one iteration sees the fourth **refused before execution** (no dispatch recorded for it; the refusal names the aggregate bound and the remaining allowance), the formed package's retrieved content totals ≤ 36,000 bytes, and the allowance resets for the next package. **The byte-window path:** a fixture line longer than the ceiling is retrieved in two byte slices whose concatenation reproduces the line exactly, each slice's served window recorded — and the fixture includes a **multibyte character deliberately straddling the requested slice boundary**, its bytes appearing in exactly one slice. **Serialized admission:** a single model response carrying several retrieval requests is processed serially — the record shows each outcome settling before the next request's admission, and the window's accounting (settled sizes, uncertain at ceiling) never exceeds the aggregate ceiling at any check.
- **R4 Search within the wall, completely:** a search returns labelled passages from permitted material; a search aimed outside `sources/` (and a list of a non-permitted path) are refused, and no metadata about the outside is returned. A query with more matches than one page returns page 1 with `total_matches` and a continuation; page 2 fetched by continuation is the deterministic next slice, and the two pages together contain no duplicates and no silent gap. An ambiguous heading request (a repeated heading name) is refused with the match count and line numbers named.
- **R5 Successive, agent-directed retrieval:** a scripted worker performs list → search → read_range in sequence, each request informed by the previous result, all recorded as dispatches with parameters, result hashes and sizes. The same run witnesses the retention rule: a result pulled in iteration 1 is **not** re-presented in iteration 3's package; re-pulling it reproduces byte-identical content under the same recorded hash; and the worker's notebook round-trips **under its own scratch grant** (write a note to `scratch/`, read it back in a bounded range) — while a retrieval aimed at a non-scratch, non-source path is still refused, proving the scratch authority expanded nothing else.
- **R6 The whole-collection proof:** across R5's run, the sum of returned content is strictly less than the corpus size, and no single result exceeds the ceiling — the worker demonstrably worked without swallowing the library.
- **R7 Checker correspondence:** the record of R5 replays clean under the independent checker with the v3 registry in both copies.
