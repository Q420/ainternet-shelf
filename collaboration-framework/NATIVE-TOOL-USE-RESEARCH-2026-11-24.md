# LLM Native Tool-Use Behaviour — Sourced Synthesis

## Summary

**Verdict (high confidence on the mechanism, moderate on the specific `container.exec` origin):** The observed behaviour is a documented, reproducible failure mode, not an idiosyncrasy of one framework. A reasoning model post-trained with reinforcement learning for agentic tool use (gpt-oss) has a strong learned prior to *act via a native tool call* as its first move. Presenting tools only as prompt text while the provider enforces `tool_choice="none"` puts two systems in direct conflict: the model's Harmony-native tool channel still fires, and the provider's validator rejects the *entire* response instead of delivering the call to the application. The same failure — exact error string `"Tool choice is none, but model called a tool"`, gpt-oss on Groq, tools described as text in the prompt — is independently reported in at least two other builds (see §5). Offering the granted tools as real native definitions removes the conflict: the call the model wanted to make anyway becomes a legal, parseable, validatable request that the *application* — not the model, not the provider — decides whether to execute.

Established vs speculative is flagged throughout. The one genuinely speculative link is *why that specific name* `container.exec`: it is a real tool in ChatGPT's environment (documented Jan 2026 for GPT-5.2 Thinking), but it is **not** a documented gpt-oss built-in (gpt-oss built-ins are `browser` and `python` only). Its appearance in gpt-oss-120b output is best explained as transfer from OpenAI-family agentic/coding training and pre-training exposure — plausible, consistent with the tool-hallucination literature, but not directly documented for this checkpoint.

## Findings

### 1. Why tool-trained models reach for tools by default, including unoffered tools

**Established:**

- **Tool calling is token prediction, not a registry lookup.** There is no in-model router that checks an offered list before generating. Tool names are generated autoregressively from the full vocabulary, so probability mass learned in pre-training / fine-tuning for plausible tool names is not zeroed out by their absence from the current schema. Practitioner synthesis, consistent with Toolformer (arXiv:2302.04761, models trained to insert tool calls as a language-modelling task): https://www.salmanq.com/blog/llm-tool-call-hallucination/ — *index, read 2026-11-24*
- **Tool hallucination is a named, benchmarked category:** "models either fabricate non-existent tools or misappropriate available but irrelevant tools" (Patil et al., cited in *The Reasoning Trap*). Gorilla (NeurIPS 2024) measured GPT-4 hallucinating API calls in zero-shot APIBench evaluation and showed fine-tuning + retrieval mitigates but does not eliminate it: https://papers.neurips.cc/paper_files/paper/2024/file/e4c61f578ff07830f5c37378dd3ecb0d-Paper-Conference.pdf — *index*
- **Reasoning enhancement *causally* amplifies it.** *The Reasoning Trap: How Enhancing LLM Reasoning Amplifies Tool Hallucination* (arXiv:2510.22977, ACL 2026) introduces SimpleToolHalluBench with two conditions — (i) no tool available, (ii) only distractor tools — and finds: "progressively enhancing reasoning through RL increases tool hallucination proportionally with task performance gains"; the effect appears via RL, distillation, SFT and mere inference-time step-by-step elicitation, and **even RL on mathematics alone (no tools) amplifies subsequent tool hallucination**. Prompt engineering and DPO mitigations show a "fundamental reliability–capability trade-off: reducing hallucination consistently degrades utility." Its summary figure: base models "more reliably abstain when tools are missing"; reasoning models "hallucinate non-existent tools when unavailable, prioritising action over honesty." https://arxiv.org/html/2510.22977v1/ and https://aclanthology.org/2026.acl-long.376.pdf — *index*
- **Abstention is out-of-distribution for tool-tuned models.** BFCL v4 (Berkeley Function Calling Leaderboard) weights Hallucination/irrelevance at 10% — correctly *declining* to call when no offered function matches — precisely because "the models topping this leaderboard were instruction-tuned and then tool-tuned specifically to *produce calls*. Refusing to act is out-of-distribution for them." https://www.dreaming.press/posts/berkeley-function-calling-leaderboard-bfcl-v4.html — *index*
- **Serving surface matters.** A 2026 measurement preprint, *Closed-World Resolution Against Tool Hallucination* (arXiv:2609.19425), reports across 10 hosted models that fabricated-tool calls "concentrate on the unconstrained raw-JSON surface (34 vs. 3)" versus a native surface, and that scale does not help. **Flag — thin:** single-author, independent, unreviewed preprint; use the direction (native/constrained surface ≪ raw text for fabrication) as corroboration, not as a precise effect size. https://arxiv.org/abs/2609.19425v1 — *index*

**Implication for the concrete case:** an assignment-shaped prompt ("inspect your sources, then…") is exactly the context in which an agentic model's training trajectories *begin* with a tool call. With no native tools offered, the prior does not disappear — it fires at the nearest learned tool.

### 2. gpt-oss and Harmony — channels, built-ins, and `container.exec`

**Established (primary source, verified live):**

OpenAI's Harmony specification — https://raw.githubusercontent.com/openai/harmony/abd677f7ac962629c808197caa1feb9e3e95d2b0/docs/format.md — *verified live, read 2026-11-24*:

- "The `gpt-oss` models were trained on the harmony response format… `gpt-oss` should not be used without using the harmony format, as it will not work correctly."
- Three assistant channels: `analysis` = chain-of-thought (not safety-trained to final standards, do not show users); `commentary` = "Any function tool call will typically be triggered on the `commentary` channel while built-in tools will normally be triggered on the `analysis` channel. Occasionally this channel might also be used… to generate a preamble to calling multiple functions"; `final` = user-facing.
- Tool calls are a distinct stop condition: `<|call|>` (token 200012) "Indicates the model wants to call a tool", vs `<|return|>` for a finished answer. A call is a message with header recipient `to=functions.<name>`, channel `commentary`, usually `<|constrain|>json`, body = JSON arguments. Results return as a `tool`-role message (`<|start|>{toolname} to=assistant…`) and, for tool use, prior CoT *is* passed back in.
- Developer-provided functions belong in the **developer** message, in a `functions` namespace, rendered in TypeScript-like syntax — "generally `functions` is the namespace you should use to not conflict with other tools that the model might have been trained on." Sticking closely to the format is explicitly said to "improve accuracy of function calling."
- **Built-in tools are exactly two:** "During the training of the `gpt-oss` models, they were trained with two common tools" — a `browser` tool and a `python` tool (stateful Jupyter execution) — defined in the **system** message, not the developer message.
- Training intent (OpenAI release / model card): models "trained using large-scale distillation and reinforcement learning. We optimise the models to have strong agentic capabilities (deep research browsing, python tool use, and support for developer-provided functions)"; post-training uses CoT RL and the model "can seamlessly interleave CoT, function calls, and responses within a single session"; evaluated on Tau-Bench. https://openai.com/index/introducing-gpt-oss/ and https://hyper.ai/en/papers/2508.10925 — *index*

**On `container.exec` specifically:**

- `container.exec` **is a real OpenAI-environment tool — in ChatGPT, not in gpt-oss's documented set.** Simon Willison's elicited tool list from GPT-5.2 Thinking (26 Jan 2026) lists, under namespace `container`: `container.exec` — "Run a command inside the container and return stdout/stderr", signature `container.exec({ cmd: string[], session_name?, workdir?, timeout?, env?, user? })`, plus `container.feed_chars`, `container.open_image`, `container.download`, alongside `python.exec` and `web.run`. https://simonwillison.net/2026/Jan/26/chatgpt-containers/ — *verified live*
- **No source found** states gpt-oss-120b was trained with a `container` namespace. Therefore: the model emitting `container.exec` as its *first* action to "inspect its sources" is best read as (a) the generic shell affordance an agentic/coding-trained model expects — a shell in a container is the universal first inspection tool in coding-agent trajectories — instantiated with (b) a specific name plausibly absorbed from OpenAI-family training/pre-training data where that exact namespace exists. **(a) is well supported by §1; (b) is inference, flag as speculation.** It is *not* evidence the framework ever offered, or Groq ever executed, such a tool.
- **Mixing native syntax into text:** also documented in the Groq ecosystem — models emitting `<function=name>{…}</function>` or `<tool_call>` blocks as text, which Groq rejects (see §5). And a second serving stack (llama.cpp via Spice) notes the inverse handling for gpt-oss: "A message addressed to `functions.<name>`, a tool the request offers, is returned as a `tool_calls` entry… A message addressed to a tool the request does not offer, such as gpt-oss's built-in `browser.search`, is dropped." — i.e. unoffered-call handling is a *provider policy choice* (drop / return / reject-wholesale), not a model property. https://spiceai.org/docs/next/components/models — *index*

### 3. Native function calling vs text-serialised protocols — framework/provider decisions and reliability evidence

**Where the ecosystem has converged (established):**

- **OpenAI:** the canonical flow is 5 steps — request with tools → receive tool call → "**Execute code on the application side** with input from the tool call" → return tool output → final response (or more calls). https://developers.openai.com/api/docs/guides/function-calling — *index*. Strict mode adds constrained decoding so arguments are guaranteed to match the JSON Schema (structure only — semantic validation remains the app's job).
- **Groq:** its own pattern is literally called **Local Tool Calling** — "execution happens in your code. You control the environment, security, and implementation. You orchestrate the entire loop… The model doesn't know how your tools work — it only sees the schema." Its worked examples use `openai/gpt-oss-120b` natively. https://console.groq.com/docs/tool-use/local-tool-calling — *verified live*
- **LangChain/LangGraph:** the original text ReAct agent (`Thought: / Action: / Action Input:` parsed by regex) is now legacy/classic. LangGraph's `create_react_agent` is deprecated in favour of LangChain `create_agent`, whose loop is native: "If the resulting AIMessage contains `tool_calls`, the graph will then call the 'tools' [node]… repeats until no more `tool_calls` are present." https://reference.langchain.com/python/langgraph.prebuilt/chat_agent_executor/create_react_agent — *index*. Practitioner consensus phrasing: text ReAct "is strictly worse than tool-calling for any model that supports native structured output… Parsing free-form text for an 'Action Input:' line is fragile"; native is preferred because it removes brittle parsing, enables parallel calls, and allows schema validation *before* execution with errors fed back to the model.
- **AutoGen:** the cleanest statement of the doorway pattern — two separate registrations: `register_for_llm` (the assistant learns the tool *exists* and its schema) and `register_for_execution` (a *different* agent, the user proxy, holds the implementation). LLM-awareness and execution capability are deliberately decoupled. https://www.autolearningagents.com/autogen/tool-use.php — *index*
- **Anthropic / OpenAI Agents SDK (pattern, index):** tool calls surface as structured `tool_use` blocks / interruptions; SDKs support `needs_approval`, tool-input guardrails that run *immediately before* invocation (including re-checking after approval), and client-executed tools where the loop stops and hands the pending call to the caller. The model proposes; host code disposes.

**Reliability evidence — including the important counter-result:**

| Evidence | Design | Result | Limits |
|---|---|---|---|
| BFCL v4 / Gorilla (Berkeley) | AST-checked function calling, incl. irrelevance/abstention | Native FC is measurable, improvable; hallucination/abstention remains a distinct failure axis even for frontier models | Benchmark, not production traffic |
| Closed-World preprint (2026) | 10 models × 2 invocation surfaces | Fabricated-tool calls 34 on raw-JSON surface vs 3 on native surface | Single-author preprint — **thin** |
| Natural Language Tools replication, July 2026 (StackOne summary of Somma et al.) | 14 models, 8,560 trials, text YES/NO selection vs structured FC | **Overall text won:** 62.3% vs 47.4% selection, 755 vs 51 critical (parse) errors, −25.2% tokens. **But per-model spread was 77pp: 11 improved, 3 worsened — and gpt-oss-120b worsened, 49.0% → 42.6% (−6.4pp); gpt-oss-20b +3.4pp** | Single-turn, **no parameters at all**, 7 tools only — does not test argument extraction, chaining, or recovery, i.e. most of a real agent |
| Groq production guidance | Provider docs | Recommends retry-on-400 with temperature adjustment; validate/sanitise args in app code; return tool errors as tool messages so the model self-corrects | Guidance, not a controlled study |

Source for NLT: https://www.stackone.space/blog/natural-language-tools-vs-function-calling/ — *verified live*. Its authors' own interpretation is directly on point: "**Models tuned hard on structured tool calling through reinforcement learning have that path reinforced, so taking the schema away removes the thing they were optimised for**" — and their recommendation is to measure format *per model*, never assume a global default. For the pinned model in this mission, the only head-to-head text-vs-native measurement found points **against** text.

### 4. Is forcing text tool use "unnatural" and degrading? — what is evidence, what is metaphor

- **"Unnatural" as a literal claim: speculation / shorthand.** No source measures "naturalness." Do not cite it as a finding.
- **The defensible, evidenced version has three parts:**
  1. *Distribution mismatch (established in effect):* gpt-oss was post-trained (CoT RL + agentic RL-style training) on Harmony, where a tool need is expressed as a `commentary`-channel message to `functions.<name>` ending in `<|call|>`, and the environment returns a `tool` message. A prompt-text contract (e.g. "write `Search[…]`") asks for a token sequence the model was *not* optimised to produce in that context, while simultaneously suppressing (via `tool_choice=none`) the sequence it *was* optimised to produce. The NLT per-model result for gpt-oss-120b (−6.4pp when the schema is removed) and the Reasoning Trap's action-over-abstention result are the quantitative shadows of this mismatch.
  2. *Action-loop expectation (established as training design):* agentic RL trains "entire decision-making processes… as the agent plans actions, invokes tools, observes outcomes, and adapts over multi-step trajectories" — the act→observe→act loop is the trained unit of behaviour, not a single completion. Harmony even specifies passing CoT back in *only* in the tool-calling case, i.e. the format presumes the loop continues. A one-shot text contract that cannot return a real observation in `tool`-role form breaks the trained trajectory shape; the Medium case in §5 shows a downstream symptom — the model fabricating its own observations when none arrive.
  3. *Affordance prior (well-supported interpretation):* a task phrased as work-on-sources strongly cues the shell/browse/python affordances from training. The model does not first check "was a shell offered?"; per §1, generation has no such gate. Expecting prompt text to install that gate is expecting the weakest mechanism (an instruction) to override the strongest (RL-shaped first-action distribution) — and the Reasoning Trap shows prompt mitigations trade away utility rather than cleanly installing abstention.
- **Contested/thin:** whether text protocols are *generally* worse. The NLT study shows they are *better on average* across 14 models for parameter-free selection. The correct general claim is **format fit is per-model and per-task-shape**; the specific claim for *this* pinned, RL-tool-trained model on a *parameterised, multi-step* assignment is that native fits and text fights the training — supported by the gpt-oss-120b row, the Harmony specification, and two independent Groq failure reports, but not by a controlled study of this exact framework/task. Flag accordingly.

### 5. Provider-side wholesale refusal (Groq / OpenAI-compatible) and the translation pattern

**Established (Groq primary docs, verified live):**

- Groq API Reference — https://console.groq.com/docs/api-reference — *verified live*: `tool_choice`: "`none` means the model will not call any tool and instead generates a message… `none` is the default when no tools are present." That is a *validation/enforcement* statement, not a generation guarantee: if the model generates a call anyway, enforcement takes the form of rejecting the response.
- Same page, the key escape hatch: **`disable_tool_validation`** (default false) — "If set to true, groq will return called tools without validating that the tool is present in request.tools. tool_choice=required/none will still be enforced, but the request cannot require a specific tool be used." Note the asymmetry: it relaxes *unoffered-name* validation, **not** the `none` enforcement — so it does not by itself rescue a `tool_choice=none` request. To receive calls at all, tools must be offered with `tool_choice=auto/required`.
- Groq Local Tool Calling docs — *verified live*: "Groq API verifies that the model generates valid tool call objects. When a model fails to generate a valid tool call object, Groq API returns a **400 error** with an explanation in the `failed_generation` field" (code `tool_use_failed` in client libraries). Groq's recommended handling is retry (it suggests adjusting temperature) — i.e. even the provider treats the 400 as a *recoverable generation event*, not a terminal refusal.
- **Exact-error corroboration (independent, same stack):**
  - ReAct rebuild, gpt-oss-20b on Groq, tools as prompt text: 'My code crashed with an error saying "Tool choice is none, but model called a tool." This model has its own built-in tools… My prompt told it about Search, Lookup and Finish, so it tried to press its own button instead of writing Search[…] as plain text like my code expected. Groq refused the reply and showed what the AI had tried to do inside the error. **The fix was code that catches the error, reads what the AI tried to do, and turns it back into text** like Search[Danny Green].' https://medium.com/@zamarai.omar/i-rebuilt-an-ai-research-paper-with-free-tools-my-ai-kept-trying-to-cheat-86d89c82cad3 — *verified live*
  - LangGraph comparison, gpt-oss-20b on Groq: single-ReAct system completed 8/15 runs; "**All seven failures were the same error type: 'Tool choice is none, but model called a tool'**" — *index*: https://www.15jq.com/html/comparisons/9116.html
  - Privatemode (vLLM-based, gpt-oss-120b): "With `tool_choice: 'none'` the tools stay in the prompt, so the model may still try to call one… **With gpt-oss-120b the model may still call a tool, and the response is then empty**." https://docs.privatemode.ai/cookbook/tool-calling/ — *index* (different stack, same model behaviour, different provider symptom — empty response instead of 400.)

**The established translation/recovery pattern (multiple independent implementations):**

1. **Catch the 400, harvest `failed_generation`, do not execute it.** Pydantic AI's Groq adapter and TanStack's Groq adapter both parse `failed_generation` back into a tool-call part, *do not run it*, and return the provider error **as the tool result** so the agent loop can repair/retry on the next step. https://tanstack.com/ai/latest/docs/adapters/groq ; https://github.com/pydantic/pydantic-ai/pull/4354 — *index*. This is salvage, suitable as a safety net — it depends on an error payload whose shape is not a stable API contract (Pydantic AI issue #100-lineage shows non-JSON `failed_generation` bypassing recovery).
2. **Prefer not needing salvage: offer the tools natively and interpose your own dispatch.** This is the providers' own architecture (OpenAI step 3, Groq Local Tool Calling, AutoGen's split registration): the model emits a structured call → **your code** checks name ∈ registry (closed-world resolution: registry membership + signature check *before* any gating — the Closed-World paper's one architectural claim, and plain least-privilege practice), validates arguments against schema + authorisation policy, executes only if approved, and returns the result (or an `is_error` tool message) under the call's ID. Groq's own production example does exactly this: `if function_name not in available_functions: raise…`, JSON-parse args, catch per-call errors into tool messages, cap iterations. Nothing in native calling grants the model execution: a tool call is a *request object*, and every mainstream framework treats the host as executor.
3. **Approval as a first-class interruption, not a prompt instruction:** Agents-SDK-style `needs_approval` / tool-input guardrails (re-checked immediately before invocation, fail-closed on error) and client-executed tools (loop stops, pending call handed to the caller) are the documented mechanisms for keeping consequential actions behind a human/policy doorway while keeping the model's native expression.

## Design implications (evidence-backed)

1. **Offer granted tools as native definitions (`tools=[…]`, `tool_choice="auto"`) for gpt-oss-120b on Groq. Do not use a prompt-text-only contract with `tool_choice="none"`.** Basis: Harmony spec (functions belong in the native/Harmony tool channel), Groq enforcement semantics, two independent exact-error reproductions, and the mission's own A/B observation, which matches the literature's prediction.
2. **Native expression ≠ native execution. Keep the doorway in host code:** registry allow-list check → schema validation → authorisation/policy (and human approval for consequential calls) → sandboxed execution → result returned as a `tool` message with the call ID. This is OpenAI's step 3, Groq Local Tool Calling, and AutoGen's `register_for_llm`/`register_for_execution` split. The model's call is a proposal; dispatch is yours.
3. **Treat unoffered calls as an expected, logged event, not an anomaly:** expect `container.exec`-/built-in-shaped attempts (Reasoning Trap / BFCL irrelevance). With native tools offered, an unoffered name should be rejected *by your resolver* with an `is_error` tool result the model can learn from in-loop ("no such tool; available: …"), rather than by the provider as a wholesale 400 that destroys the turn. Note `disable_tool_validation=true` exists on Groq for returning unoffered calls to you — evaluate it for this purpose, but remember it does **not** lift `tool_choice=none/required` enforcement, and test its current behaviour before relying on it.
4. **Keep a `failed_generation` salvage path as a safety net only** (parse → validate → translate into your dispatch pipeline; never execute directly from the error payload), following Pydantic AI / TanStack precedent. Do not build the primary loop on it: payload shape is unstable.
5. **Return denials and validation failures as tool results, not exceptions that end the run** (Groq + LangGraph ToolNode practice): the model self-corrects in-loop; a crashed turn teaches it nothing and loses its reasoning.
6. **Bound the loop in code** (max iterations/calls, per-tool budgets, least-privilege credentials per tool) — prompt instructions are not enforcement (Reasoning Trap: prompt mitigations are weak and cost utility).
7. **Measure format per pinned model before generalising:** if the framework later supports non-tool-trained models, re-run a small selection+argument benchmark per model (NLT protocol) rather than assuming native always wins — on parameter-free selection, text beat native on average across models, just not for gpt-oss-120b.
8. **Do not expose Harmony `analysis` (CoT) to end users**, and preserve it across tool-call turns as Harmony specifies; drop it after final answers.

## Could not verify / thin or contested

- **No direct evidence gpt-oss-120b was trained with `container.exec`.** Its documented built-ins are `browser` and `python` only. The ChatGPT (GPT-5.2) provenance of the exact name is documented; transfer to gpt-oss is inference.
- **No controlled study of this exact configuration** (gpt-oss-120b + Groq + parameterised multi-step assignment, text vs native). The conclusion rests on converging evidence: spec, provider docs, two independent failure reports, one per-model benchmark row, and the mission's own A/B.
- **Closed-World Resolution (arXiv:2609.19425)** is a single-author unreviewed 2026 preprint — its 34-vs-3 figure should not be quoted as settled.
- **NLT results cut against any blanket "native > text" claim** — they are the strongest counter-evidence and are single-turn/no-parameter by design.
- Groq docs do not publish the literal string "Tool choice is none, but model called a tool" — that exact string is attested in independent practitioner reports and the mission statement, not in Groq's reference pages (which document the enforcement semantics and `tool_use_failed`/`failed_generation` mechanism).
- AutoGen/CrewAI/Anthropic specifics were read via index summaries and secondary guides, not full primary documentation deep-dives; the architectural patterns attributed to them are uncontroversial and multiply corroborated, but exact API names should be re-checked against current docs before implementation.
