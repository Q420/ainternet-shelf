**Date:** 2026-11-23. **Revision 4** — Revision 2 folded in the examiner's first corrections (PB pb-mwtoa7va-1o-2wyc, INDEX 176): all five questions settled as recorded in §7, and the four clarifications incorporated at §2, §4, and §5. A1 gave an instance an identity; A2 gave it hands. A3 gives it the working loop: perceive → act → see the result → act again, inside bounds, until it yields or is stopped by the record.

## 1. Where the loop sits

- A **new module, `src/framework/loop.py`** — the runtime for generated instances. The seat `Driver` (Piece 4) is seat-bound: it wakes on recorded reasons, once per wake. The loop is **activation-bound**: it starts when an instance is activated (A1) for its part and runs iterations until the instance yields, declines, or a bound stops it. The seat driver is untouched.
- The loop is machinery, never an authority (§8): a model requesting a tool does not authorise it (A2's doorway check does); the loop reporting success does not establish completion (the record does).
- The loop depends on a **narrow model-callable contract** — package in, typed outcome out — which is the adapter's existing `__call__` signature, extended (§3). A scripted fake model implements the same contract in tests (Pieces 4/8 precedent). No contract term — identity, grants, record acts, retrieval rules, lifecycle — lives in the callable (R51): substituting the runtime changes nothing the checker or the doorway enforces.

## 2. The iteration

1. **The iteration sequence, exactly:** (i) check the activation bounds and remaining deadline; (ii) construct and **freeze** the package from a specific record snapshot; (iii) record the **`LOOP_ITERATION`** event (§6) under the loop's constrained machinery identity, carrying that package's exact cursor range; (iv) invoke the model with the frozen package; (v) validate the complete response, then adjudicate its effects. Because the iteration event is recorded after the package's presented head, it appears in the **next** iteration's delta, never in the package it describes. An iteration is therefore accounted even if the provider fails, the response is malformed, or the process is interrupted mid-call — a consumed iteration never leaves no trace. **If package construction fails, or the deadline expires before the iteration event is recorded, no model call occurred and no iteration is counted**: the loop records the appropriate stall (§6), subject to dispatch accounting. One iteration is one model call, by definition.
2. **Package.** Each iteration presents: the case view (as the driver builds it, boundary-narrowed per R11), the **record delta** since the last presented position (§5's cursor), the **tool results** settled since the last iteration (each against its dispatch identity, including uncertain outcomes presented *as* uncertain), the **standing dispatch states** for this instance (visible in every package until they settle, uncertain ones included), and the **bounds state** (steps used / ceiling, time remaining against the governing bounds, §4).
3. **Response — terminal outcomes are mutually exclusive.** A **proposals** response may mix **record acts** (the existing proposal vocabulary) and **tool requests** (new, §3). A **yield** response contains only the yield summary. A **decline** response contains only the decline reason. Any combination across those classes — a yield beside a tool request, a decline beside a contribution — is rejected by whole-response validation before any effect: the loop never guesses which terminal meaning governs.
4. **Validation, then adjudication (§5).** The whole response is strictly validated for shape before anything takes effect; after validation, each act and request is adjudicated individually through its proper doorway. A refusal is recorded information — it discards no independent effect and crashes nothing.
5. **Effects.** Every record act goes through `doorway.act` under the instance's credential (A1: instance credentials authenticate while the fold derives "active"; acts bind to the seat the instance fills, provenance-stamped with the instance_id, as A2's TOOL_REQUESTED established). Every tool request goes through A2's `doorway.request_tool` under the temporal admission rule (§4) and, on dispatch, the executor; the loop never executes a tool itself and never retries a request on its own motion (R47: a retry resolves against the standing dispatch).
6. **Step.** One iteration = one model call and the adjudicated effects of its response. The step ceiling counts iterations per activation, counted from the `LOOP_ITERATION` events.

## 3. The adapter extension

- The response vocabulary gains two typed outcomes beside acknowledge / contribute / decline: **`tool_requests`** — a list of `{tool, parameters}` entries (the model supplies tool and parameters, **never** the request identity, §4); and **`yield`** — the instance declares its bounded work done, with its own summary text (strict: yield carries its summary and nothing else). Record acts continue to ride the proposals outcome, unchanged.
- **The activation deadline reaches the callable.** The contract carries the activation's remaining budget to the adapter **outside the model-visible prompt** (a call parameter, never package content the model can see or influence). The adapter treats the activation deadline as its **governing limit**: any configured per-call limit acts only as a tighter ceiling, and beginning a call never resets the activation budget. The rule covers package construction and response handling as well as the call itself (the A6 discipline, applied to the activation rather than the call). **A call that cannot begin within the remaining budget does not begin** — the loop proceeds directly to its bound handling (§4).

## 4. Bounds, identity, and temporal admission

- **Bounds live in the case** (R49, §8): the issued case content for the instance's part carries `loop_bounds: {step_ceiling, deadline_seconds}`. An instance whose case carries no bounds **cannot loop** — fail closed; there is no default bound.
- **The governing bounds are pinned at activation.** The assembly binds the exact issued case (id + version, A1); the loop reads the bounds from **that** version and uses them for the entire activation. A later case correction carrying different bounds does **not** move a running activation: a changed bound is a material change to the assignment and takes effect only through the proper case-and-assembly route, for a future activation.
- **Request identity is loop-assigned and deterministic**: derived from the activation, the iteration number, and the request's ordinal within that iteration's response. The loop binds the identity to the exact request fingerprint (A2) at presentation; an identity is never reused for altered parameters or a different ordinal. A re-presented response (e.g. after a lost outcome) therefore resolves against the standing dispatch by construction, and a new iteration produces new identities.
- **Temporal admission at the doorway — unforgeable.** The deadline is enforced **at the dispatch decision**, and the doorway establishes it **itself**: from the standing activation and its pinned case version, out of trusted framework state (the fold) — never from a caller-supplied value. The loop may carry a remaining-budget figure with a request as an **early-refusal hint** (it lets the doorway refuse sooner), but a supplied value can never extend, replace, or relax the authoritative deadline, and its absence changes nothing. The doorway's deadline check and its dispatch-intent recording are ordered so an expired request cannot cross the boundary: check first, intent only on a pass, fail closed on expiry — refused and recorded on the existing refusal path. A request the model returned in time but which reaches the dispatch decision after the deadline is **not dispatched**. This is the activation's temporal limit on initiating work; it changes nothing about A2's grant authority.
- The total deadline is per **activation**: it starts when the loop starts for that activation and governs every phase of every provider call, package construction, response handling, and dispatch decision inside it.
- **The authoritative clock anchor.** A duration deadline needs a trustworthy zero point, and the record's event timestamps cannot serve: they are UTC wall-clock at whole-second precision — wall clocks move, and the precision cannot establish a deadline. The deadline is therefore derived from a **framework-controlled monotonic activation anchor**: a monotonic reading taken by the framework at activation and held in the doorway's own durable activation state, **bound to the exact INSTANCE_ACTIVATED event (its seq) and the pinned case id + version**. The doorway computes the deadline as *anchor + the pinned case's deadline_seconds*, on the same monotonic clock, every time it checks — so the deadline is identical no matter which component asks or when. The loop's clock readings and any caller-supplied budget remain non-authoritative hints (§4 above); the adapter's governing limit is set from the doorway-derived remaining budget, not from the loop's own clock. **Lifecycle:** the anchor is established exactly once, at activation, before the loop's first iteration; it is never re-established, extended, or re-based for that activation. **Fail-closed:** if the doorway cannot establish the anchor for a standing activation — never written, missing, or not bound to that activation's event and case version — temporal admission **fails closed**: no dispatch is admitted and the loop begins no new iteration. This holds **after a runtime restart** identically: the anchor is recovered from its durable binding or admission stays closed; the doorway never silently substitutes the activation event's wall-clock timestamp, and a restart never grants a fresh deadline. (The anchor's storage mechanism is an implementation choice; its source, binding, and lifecycle as stated here are the contract.)

## 5. The cursor, and validation vs adjudication

- **Presented-position cursor.** The loop holds a record position (a seq) per activation: the position up to which record state has been presented to the instance. A package's delta is **every event after the cursor** relevant to the instance (its own acts, REJECTIONs of its acts and requests, dispatches, outcomes whenever they arrive, and the case view's movement), and the cursor advances **only to the head the package actually presented** — never past an event the package did not include. Iteration *n*'s `LOOP_ITERATION` event records the cursor it presented from and the head it presented to, so the checker and the tests can establish that no delta was skipped and no event was presented twice as new. Standing dispatch states are re-presented in full each iteration regardless of the cursor (§2).
- **Validation is all-or-nothing; adjudication is not.** Whole-response strict validation (shape, field sets, types) precedes all effects: a malformed entry anywhere prevents **every** proposed effect of that response, and the iteration ends as a malformed_response stall (§6). Once a response validates, its acts and requests are adjudicated **individually**: one act's refusal neither blocks nor rolls back its independent siblings, and a refused tool request does not end the loop. Validation is a property of the response; adjudication is a property of each act.

## 6. The recorded stall (R50) and the loop's record (R55 increment)

- **Reaching a bound without a yield act is a recorded stall**: one event kind, **`LOOP_STALLED`**, extending the DRIVER_FAILURE pattern, with a constrained `ground` vocabulary:
  - `step_ceiling` — the iteration count reached the governing ceiling without yield;
  - `deadline` — the activation deadline expired (including a call that could not begin within budget);
  - `provider_failure` — the provider/adapter failed the call (transport, malformed provider behaviour, the adapter's typed failures);
  - `malformed_response` — the response failed whole-response validation;
  - `runtime_failure` — the loop itself failed unexpectedly while assembling a package, reading the record, or processing an otherwise valid response. Narrowly this: an internal machinery failure, never a relabelled provider failure and never an instance's act. If the record mechanism itself is unavailable, the loop **fails closed** and does not claim a stall was recorded.
- A stall names the instance and activation, the exact case version, the ground, and the final iteration count. After a stall the loop admits no new iteration, act, request, or dispatch for that activation; a fresh start is a new assembly's business (A1/A5).
- **Stall timing with a dispatch in flight.** When a bound is reached, admission stops immediately, but `LOOP_STALLED` is recorded only once **dispatch accounting closes**: every in-flight dispatch holds an attributable A2 outcome — result, failure, or uncertain. *Accounted* is not *resolved*: an uncertain outcome closes the accounting without waiting for examiner reconciliation (A5's business). A **late attributable outcome** may still settle an uncertain dispatch after the stall stands; it is executor accounting, not new instance activity, and the checker allows it while refusing any post-stall instance act, request, or dispatch.
- A **decline** is neither a yield nor a stall: a structured non-act (Piece 8 precedent). It ends the loop and is reported to the loop's caller with the worker's declared reason; nothing is recorded for it.
- **The loop identity.** The loop machinery holds its own constrained reporting identity, distinct from the executor's: it may record `LOOP_ITERATION` and `LOOP_STALLED` against standing activations, and nothing else — it cannot submit worker acts, request tools, grant anything, or declare completion. Routes follow the A2 executor pattern (doorway routes; the kinds are absent from every seat's act authority; a seat act naming them is refused and recorded).
- **`LOOP_ITERATION` payload**: activation + instance, the exact case version, the iteration number, the governing bounds (ceiling + deadline as pinned), and the presented cursor range (§5). The checker reconstructs the iteration count from these events, verifies ordering and uniqueness per activation, and verifies the count never exceeds the governing ceiling.
- Fold + both projection-schema copies gain both kinds identically; the checker's new `loop_correspondence` check verifies: iteration events precede their calls' effects; stalls bind standing activations with settled grounds; ceiling arithmetic against the pinned bounds (not any later case version's); cursor ranges chain without gaps or overlaps per activation; no instance activity after a stall, late executor outcomes excepted. Replay executes nothing (R48), as everywhere.

## 7. The examiner's settlements (2026-11-23, INDEX 176)

(a) Bounds in the issued case, pinned to the assembly-bound exact case version for the whole activation — §4. (b) Request identity loop-assigned, deterministic, fingerprint-bound — §4. (c) One stall kind + ground field, `runtime_failure` added, decline a non-act — §6. (d) `LOOP_ITERATION` bookkeeping before the call, under a distinct loop identity — §2, §6. (e) Stall after dispatch accounting closes; accounted ≠ resolved; late outcomes permitted post-stall — §6. Clarifications: the deadline reaches the adapter through the contract (§3); temporal admission enforced at the doorway (§4); the cursor defined (§5); validation vs adjudication stated (§5). **Final corrections (Rev 3):** the iteration sequence is bounds check → frozen package → `LOOP_ITERATION` with its exact cursor range → the call → validation → adjudication, with no call and no count when construction fails or the deadline expires first (§2); the doorway's temporal deadline is derived from trusted state, caller values being hints only (§4); terminal responses are mutually exclusive (§2, §3). **Closure correction (Rev 4):** the deadline is derived from a framework-controlled monotonic activation anchor, established once at activation and bound to the exact INSTANCE_ACTIVATED event and pinned case version, held in the doorway's durable activation state; anchor unrecoverable (including after restart) means admission fails closed — no wall-clock substitution, no fresh deadline (§4).

## 8. Acceptance tests (scripted fake models + the real doorway/executor; the A2 sandbox registry is the tool set)

- A worker that writes, reads the result back in its next package, and yields — the read package's tool result is the write's recorded outcome (uptake inside the loop, witnessed from the record).
- Iteration accounting: every model call — including one whose response is a bare decline, a yield, or a provider failure — has its `LOOP_ITERATION` standing **before** its effects; the checker reconstructs the count exactly.
- Step ceiling: a worker that never yields stalls at exactly the ceiling; `LOOP_STALLED` stands with ground step_ceiling; no iteration beyond it.
- Deadline: a slow provider call is governed by the activation's remaining budget, not a fresh allowance; a call that cannot begin within budget never begins; expiry stalls with ground deadline.
- Bounds pinning: a case correction issued mid-activation carrying larger bounds does not extend the running loop; the stall lands at the **pinned** ceiling.
- Temporal admission: a tool request returned before the deadline but reaching the dispatch decision after it is refused at the doorway and recorded; no dispatch stands.
- Tool sequence end-to-end per R45 inside the loop; a refused grant inside a loop response records its REJECTION and the loop continues.
- An induced uncertain outcome is presented to the instance *as* uncertain in the next package; the instance may yield with the uncertainty standing (A5 accounts it; A3 does not reconcile). A stall with an in-flight dispatch is recorded only after its outcome lands; a late outcome settling an uncertain dispatch **after** a stall is accepted by the checker, while a post-stall instance act is refused.
- Malformed response → stall, ground malformed_response, nothing partial in effect (validation precedes adjudication: a mixed response with one malformed entry effects nothing). Provider failure → stall, ground provider_failure. A forced internal error in package assembly → stall, ground runtime_failure, distinguished in the record from provider_failure.
- Cursor integrity: across iterations with interleaved outcomes, every relevant event is presented exactly once as new; the checker verifies the cursor chain per activation. Each `LOOP_ITERATION` event appears in the *following* iteration's delta, never in its own package; a forced package-construction failure counts **no** iteration and stalls with ground runtime_failure.
- Unforgeable temporal authority: a request presented with a caller-supplied deadline *later* than the activation's true deadline is still refused at the doorway once the true deadline has passed; a supplied *earlier* value refuses sooner and dispatches nothing.
- Terminal exclusivity: a response combining a yield with a tool request, and one combining a decline with a contribution, are each rejected whole by validation — no effect of either stands, and the iteration stalls as malformed_response.
- The anchor: with the framework process restarted mid-activation, the enforced deadline is still the original anchor's — the restart extends nothing. With the anchor's durable binding removed, admission fails closed: requests are refused, no iteration starts, and no deadline is derived from the activation event's wall-clock timestamp.
- Decline ends the loop as a caller-reported outcome; no stall stands.
- A case without `loop_bounds` cannot loop: refused before the first model call.
- Checker: `loop_correspondence` as §6; the two schema copies agree; replay executes nothing (structural witness, as in A2).
- Runtime replaceability: the same scripted scenario runs against a second trivial loop client implementing the contract, with identical record effects (R51).
