# OpenClaw — Sourced Synthesis for a Safety-Conscious Multi-Agent Framework Team

Date of research: 24 November 2026 (America/Denver). Most facts are `index` (search-index reads of the pages cited); two pages were `verified live` in the research browser on 2026-11-24 as noted. Where sources conflict, the conflict is stated rather than resolved.

## Summary

OpenClaw is **not primarily a developer framework/SDK for building agents — it is the agent itself**: a free, MIT-licensed, self-hosted, always-on personal assistant runtime. A single long-lived Gateway process on your own machine connects messaging apps (WhatsApp, Telegram, Slack, Discord, Signal, iMessage, etc.) to a model-agnostic LLM loop, and gives that loop real tools — shell, files, browser, email/calendar, device nodes — plus persistent Markdown memory and installable third-party “skills.”

That design is exactly why it is instructive for a team building a collaborative multi-agent framework with strict authorisation boundaries:

1. **Its tool-execution stack is, in its hardened configuration, surprisingly complete** — native provider function-calling, schema-defined tools filtered by layered allow/deny policy *before* the model sees them, a separate host-side exec-approval interlock (allowlist + human `/approve`, stricter-of-two policies, fail-closed fallback), and an optional Docker/Podman sandbox.
2. **Its defaults invert that stack.** As of OpenClaw 2.0 (Aug 2026): sandbox **off by default**, host `exec` defaults to `full` with **no approval prompts**. Safety is opt-in, capability is default.
3. **Its documented failures are therefore mostly boundary failures, not model failures**: a 1-click RCE that let a website steal the Gateway token (CVE-2026-25253, CVSS 8.8), a localhost WebSocket brute-force/pairing chain (“ClawJacked”), tens of thousands of internet-exposed Gateways, a poisoned skill marketplace (ClawHavoc / ToxicSkills), indirect prompt injection through email/web content, memory/compaction losing a human’s “don’t act until I approve” instruction (the Summer Yue inbox deletion), and skills/plugins running with the agent’s full privileges.
4. **Its multi-agent model is delegation, not a work-state / approval-authority separation.** Agents are isolated by workspace/memory/tool policy, a parent can `sessions_spawn` / `sessions_send` to children who push results back, and depth is capped — but cross-agent access is **on by default**, shared sessions in 2.0 are explicitly **“not tenant isolation or a security boundary,”** and exec approvals are explicitly **“not a per-user auth boundary.”** There is no native concept comparable to “work state passes between agents, approval authority stays with a named human” as a first-class, non-bypassable invariant. That has to be built *outside/above* OpenClaw — which is precisely what NVIDIA OpenShell/NemoClaw, Cisco DefenseClaw and others then attempted.
5. **The project responded fast and increasingly institutionally** — patches within ~24h–days, VirusTotal + ClawScan screening of ClawHub (with daily re-scans), a built-in `openclaw security audit`, a public threat-model/roadmap promise, and from 8 July 2026 a 501(c)(3) OpenClaw Foundation with paid staff — but reviewers of 2.0 (notably *The Register*) concluded it still did not bring “security by default” with its new accessibility.

**Bottom line for the requesting team:** adopt OpenClaw’s *mechanisms* (policy-filtered tool offering, host-side approval interlock, per-agent tool/sandbox profiles, fail-closed approval fallback, audit tooling); avoid its *defaults and trust model* (single trusted operator = single trust boundary, prompt-carried constraints, unvetted skills as code+instructions, sandbox-off/full-exec defaults); watch its *ecosystem hardening* (OpenShell-style external policy enforcement, skill signing/scanning, Trail of Bits-type audits, extended-stable releases).

## Findings

### 1. What OpenClaw is: origin, who builds it, what it does, architecture, adoption, current status (late 2026)

**Established facts**

- **Origin and names.** Developed by Austrian programmer Peter Steinberger (founder of PSPDFKit, now Nutrient). First published 24 November 2025 as **Warelay** (Wikipedia’s infobox; other accounts simplify this to “as Clawdbot”), derived from his personal assistant Clawd (now Molty), named for Anthropic’s Claude. Renamed **Moltbot on 27 Jan 2026** after Anthropic trademark complaints, then **OpenClaw on 30 Jan 2026** because, per Steinberger, “Moltbot never quite rolled off the tongue.” — Wikipedia, `index`, read 2026-11-24: https://en.wikipedia.org/wiki/OpenClaw?ref=hackernoon.com
- **What it does.** “A free and open-source autonomous artificial intelligence agent that can execute tasks via large language models (LLMs), using messaging platforms as its main user interface.” Bots run locally, integrate an external LLM (Claude, GPT, DeepSeek, Gemini, Kimi, Grok, local Ollama/LM Studio/vLLM, etc.), store config and history locally, and act — not just chat — across services. Steinberger’s shorthand, widely quoted: “the AI that actually does things.” — Wikipedia (above); Collabnix architecture dive, `index`: https://collabnix.com/openclaw-architecture-deep-dive-how-it-works-under-the-hood/
- **Architecture — Gateway-centric.** One long-lived Gateway process per host owns every messaging channel, runs the agent loop for each session, executes tools, and serves a WebSocket + HTTP API on one port, default `127.0.0.1:18789`. CLI, Control UI, desktop/mobile apps and paired “nodes” are clients of the Gateway. Runs are serialised per session. — ClawDocs Architecture Overview, `verified live` 2026-11-24: https://clawdocs.org/architecture/overview
  - **Agent runtime:** assembles the prompt (base prompt + skills prompt + workspace bootstrap files + per-run overrides), calls the model, runs tools, streams the reply.
  - **Channels:** messaging integrations, mostly bundled plugins. Counts grew over the year (10+ in Feb, 20+ by spring, ~23–32 claimed in later reviews/docs summaries — treat exact count as version-dependent, not verified to a single primary source).
  - **Sessions:** conversation identity/history/runtime state; interactive, background (sub-agent) and scheduled/cron types in secondary descriptions.
  - **Tools:** `exec`, `read/write/edit/apply_patch`, `browser`, `web_search/web_fetch`, `memory_search`, messaging, sessions, and plugin/MCP tools.
  - **Nodes:** companion devices exposing commands such as `camera.*`, `screen.record`; they do not run a Gateway.
  - **Memory:** Markdown files in the agent workspace plus a search index in a per-agent SQLite database (`~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite`). Key workspace files: `AGENTS.md` (operating instructions; its `## Tools` section replaces retired `TOOLS.md`), `SOUL.md` (persona/boundaries), `USER.md`, `IDENTITY.md`, `MEMORY.md` (curated long-term memory, main private session only), `memory/` daily notes (retrieved via `memory_search`, not injected by default). Bootstrap files are truncated (default 20k chars/file, 60k total). Untrusted tool/channel content is wrapped in `EXTERNAL_UNTRUSTED_CONTENT` markers before the model sees it — a prompt-level marker, not an execution boundary.
  - **Skills:** directories containing a `SKILL.md` with YAML frontmatter/metadata and instructions for a task, in particular how to call tools. Discovered from workspace, project, personal, managed (`~/.openclaw/skills/`), bundled and extra folders in priority order; only names/descriptions are listed in the system prompt, full instructions are read on demand (a token-economics design). Distributed via **ClawHub**, the public skill registry.
  - **Plugins:** channels, providers, memory backends and many tools are plugins, loaded at Gateway startup per config.
  - **Config:** `~/.openclaw/openclaw.json` (JSON5), validated against a schema; Gateway refuses to start on unknown keys (`openclaw config validate`).
  - **Heartbeat/automations:** scheduled agent turns run by the Gateway scheduler.
- **Implementation.** TypeScript (plus Swift for Apple apps), Node.js Gateway, built on Mario Zechner’s Pi stack: `@mariozechner/pi-ai` (unified provider interface), `@mariozechner/pi-agent-core` (agent/tool loop), `pi-coding-agent` (coding tools). See §2. — Wikipedia infobox; Medium deep dive, `index`: https://medium.com/@bridgeriver-ai/deep-dive-how-openclaw-built-a-production-grade-ai-agent-system-6910aea5d2cd
- **Adoption — extraordinary, but count carefully.** 247,000 GitHub stars and 47,700 forks as of 2 March 2026 (Wikipedia, citing the repo). A secondary deployment guide reports crossing 250,829 stars on 3 March 2026, surpassing React. Later secondary stats pages report ~390,000–392,000 stars and ~82,000 forks by Sept–Oct 2026, ~3.2M monthly active users and 38M monthly site visitors — these later figures come from SEO/stats aggregators, not a primary GitHub read in this research, so treat them as **estimates, directionally “growth flattened after spring” rather than precise counts**. Enterprise/ecosystem adoption is better evidenced qualitatively: Tencent and Z.ai announced OpenClaw-based services, Chinese developers adapted it to DeepSeek/WeChat, NVIDIA built NemoClaw on it (§3/§5), and Microsoft was reported building an OpenClaw-based “Autopilot/ClawPilot” agent. — Wikipedia (above); FatJoe stats, `index`: https://fatjoe.com/blog/openclaw-ai-stats/ ; Cortance, `index`: https://cortance.com/blog/digital-transformation/openclaw-ai-agent-how-to-deploy-configure-and-build-scalable-automation-in-2026
- **Licensing and governance.** MIT License throughout, copyright now held by the OpenClaw Foundation. On 14 Feb 2026 Steinberger announced he would join OpenAI and that the project would move to a foundation. The **OpenClaw Foundation formally launched 8 July 2026 as a US 501(c)(3)**, chaired by Dave Morin, with a first full-time team of ~10 (6 engineering led by Chief Architect Vincent Koc + 4 operations), sponsors/partners named including OpenAI, GitHub, NVIDIA, Microsoft, Red Hat, Tencent — and, per foundation-launch coverage, the University of Michigan as a major donor. Steinberger retains technical stewardship. In July the foundation also introduced an **extended-stable release channel** (monthly line with backported security/reliability fixes). — Wikipedia (above); AI Wiki, `index`: https://aiwiki.ai/wiki/openclaw ; OpenClaws foundation launch, `index`: https://openclaws.io/blog/openclaw-foundation-launch/
- **Current version status.** Stable release listed by Wikipedia (crawled 29 Sept 2026) is **2.0 (v2026.8.1), 30 Aug 2026**: usability/install improvements, redesigned UI, browser-app updates, SQLite session store, and **shared cloud sessions / cloud workers**. A secondary stats site claims a later maintenance release v2026.10.9 (29 Oct 2026) “focused on security hardening” — **not verified against a primary release page in this research**. Normal (non-2.0) releases are date-versioned (`2026.x.y`) and shipped frequently. — Wikipedia (above); FatJoe (above)

**Opinion/speculation to separate:** Claims that OpenClaw was “acquired by OpenAI,” that Microsoft Autopilot definitively “runs on OpenClaw” in production, or precise MAU/revenue figures, appear in low-quality aggregator pages and were **not** corroborated by a primary source here. The corroborated fact is narrower: Steinberger joined OpenAI; the foundation is independent and MIT-licensed.

### 2. Tool use: native function calling vs text, definition, offering, validation, execution, sandboxing / permissions / approvals

This is the most important section for the requesting team. The short answer: **OpenClaw uses providers’ native tool/function calling, normalised by pi-ai — it is not a text-protocol agent at its core — and it interposes several code-level gates between a model’s tool call and host execution. The weakness is not absence of gates; it is that the strongest gates are off or permissive by default, and that one gate (`exec`) subsumes almost all others if allowed.**

**How tools are defined and offered**

- Tools are defined in code with **JSON Schema (via TypeBox, `@sinclair/typebox`)**: name, description, `input_schema`/parameters. Example pattern (Anthropic Messages API): `tools: [{name: "exec", description: "Execute shell command", input_schema: {type:"object", properties:{command:{type:"string"}, …}}}]`. Plugin tools register via `registerTool()`; channel tools and OpenClaw tools (browser, canvas, sessions, memory, web, cron, gateway, message) are built in `createOpenClawCodingTools()` alongside Pi’s base `read/write/edit/bash` (with OpenClaw replacing `bash` with its own `exec/process`). — Medium deep dive (above); AgentShield architecture analysis of the codebase, `index`: https://github.com/agentshield-ai/agentshield/blob/HEAD/design/plans/openclaw-architecture-analysis.md
- The agent loop is Pi’s: stream model response → if it contains tool calls, execute them locally (sequentially), append tool results to the conversation, loop → stop when the model returns text only. OpenClaw wraps it with session queueing/serialisation, retries, compaction, auth-profile rotation, and event streaming. Gateway RPC params are likewise validated with TypeBox schemas co-located with handlers. — Arfak “How OpenClaw Works #3 — The Agent Loop”, `index`: https://www.arfak.ai/blog/how-openclaw-works-agent-loop
- **Text-protocol caveat:** native calling is the norm, but the codebase visibly handles non-native/downgraded forms for some providers: `sessions_history` output filtering strips plain-text tool-call XML (`<tool_call>…`, `<function_call>…`, `[Tool Call: …]`) and malformed MiniMax `<invoke…>` tool-call XML. So: do not assume every provider/model path is equally structured or equally safe — the harness has to sanitise text-form tool scaffolding in transcripts. — Session Tools docs, `index`: https://docs.claw.so/engine/concepts/session-tool/
- **Offering is policy-filtered before the model sees the tool list.** The documented filtering pipeline, in order, each layer only able to *further restrict, never re-grant*: (1) tool profile (`minimal/coding/messaging/full`), (2) provider profile, (3) global `tools.allow/tools.deny`, (4) provider policy, (5) per-agent policy, (6) per-agent provider policy, (7) sandbox tool policy, (8) sub-agent tool policy. Rules: **`deny` always wins; if `allow` is non-empty, everything else is blocked.** Tool groups expand: `group:runtime` = `exec,bash,process`; `group:fs` = `read,write,edit,apply_patch`; `group:sessions`, `group:memory`, `group:openclaw`, etc. Profiles e.g. `coding` = fs+runtime+sessions+memory; `messaging` = messaging+sessions-list/history/send/status (no exec by default). There are also `before_tool_call` / `after_tool_call` hooks in the execution path. — Sandbox vs Tool Policy vs Elevated, `index`: https://docs.claw.so/engine/gateway/sandbox-vs-tool-policy-vs-elevated/ ; Multi-Agent Sandbox & Tools, `index`: https://docs.claw.so/engine/multi-agent-sandbox-tools/

**Validation and execution — what is and is not checked**

- Schema shape is validated (tool parameters, Gateway RPC, strict config). Exec allowlist evaluation parses shell commands into top-level segments: chaining (`&&`, `||`, `;`) is allowed only when *every* segment satisfies the allowlist; redirections are not auto-allowed in allowlist mode. `safeBins` (default `jq, grep, cut, sort, uniq, head, tail, tr, wc`) may run in allowlist mode without explicit entries **only as stdin-only stream filters** — they reject positional file args and path-like tokens, and custom safe bins need an explicit `safeBinProfiles` entry. — Exec Approvals docs, `verified live`: https://docs.claw.so/engine/tools/exec-approvals/
- **Critical limitation, stated in the docs themselves:** “Tool policy filters tool availability by name; it does not inspect side effects inside `exec`. If `exec` is allowed, denying `write`, `edit`, or `apply_patch` does not make shell commands read-only.” In other words, argument-level/semantic validation of *what a shell command does* is essentially allowlist-pattern matching on the resolved binary path + segment parsing — not a capability model for the command’s effects. A model-supplied `security`/`ask` parameter bug illustrates the fragility: a May 2026 GitHub issue (#84951) reports GPT-5 models injecting `ask:"on-miss", security:"allowlist"` into `exec` calls, and because the merge takes the *stricter* of model vs config, no local config could relax it — the model could tighten (here, DoS usability) but, by design, never loosen policy. — Sandbox vs Tool Policy (above); GitHub issue, `index`: https://github.com/openclaw/openclaw/issues/84951
- Loop guardrails exist: OpenClaw tracks recent tool-call history and warns/blocks on repetitive no-progress loops. — Tools docs summary, `index`: https://gitea.gokickrocks.org/bensonjohnson/openclaw-android/src/commit/cf5702233c80c4f354b15b178e6b5976a3791acc/docs/tools/index.md

**The three distinct controls (do not conflate them)**

| Control | Question it answers | Key config | Default (2.0, per docs/hardening guides) |
|---|---|---|---|
| **Tool policy** | *Which tools exist / are callable?* | `tools.profile`, `tools.allow/deny`, per-agent & per-provider & sandbox variants | Profile-dependent; empty `allow` = all except denied |
| **Sandbox** | *Where do tools run?* | `agents.defaults.sandbox.mode` (`off/non-main/all`), scope, `workspaceAccess`, Docker/Podman backend, `docker.*` hardening (network, user, pids/memory/cpu limits, seccomp/AppArmor, DNS) | **`off`** |
| **Exec approvals + elevated** | *May this specific host command run, and may a sandboxed agent escape to the host?* | `tools.exec.mode` / legacy `security` (`deny/allowlist/full`) + `ask` (`off/on-miss/always`) + `auto`; host file `~/.openclaw/exec-approvals.json`; `tools.elevated.*` | Host exec: **`security=full`, `ask=off`** on gateway/node; `deny` on sandbox host |

- **Sandbox details.** When enabled, non-main (or all) sessions run `exec/read/write/edit/apply_patch` inside a Docker container (`openclaw-sandbox:bookworm-slim` by default); the Gateway stays on the host. Default sandbox tool allow: `exec, process, read, write, edit, sessions_*`; default deny: `browser, canvas, nodes, cron, discord, gateway`. Docs warn: bind mounts *pierce* the sandbox; binding `/var/run/docker.sock` “effectively hands host control to the sandbox”; allowing `browser` in the sandbox breaks isolation (browser runs on host); the “hard wall only applies to tools.” Per-agent sandbox+tool profiles are supported — the canonical example is a personal agent with full access, a family agent in Docker with only `read`, a public agent sandboxed. — Docker/Sandbox docs, `index`: https://openclaw.im/docs/install/docker ; Multi-Agent Sandbox & Tools (above)
- **Exec approvals — the strongest native gate, and its exact semantics.** Described in the docs as a “safety interlock: commands are allowed only when policy + allowlist + (optional) user approval all agree.” Enforced **locally on the execution host** (Gateway process or node runner/macOS app), *in addition to* tool policy and elevated gating (unless elevated=`full`, which skips approvals). **Effective policy is the stricter of `tools.exec.*` and the host approvals file** — the host file can tighten config, never loosen it. Allowlists are **per-agent**, case-insensitive globs that must resolve to binary paths (basename-only entries ignored); each entry records last-used time/command/resolved path. `autoAllowSkills` (treating executables referenced by known skills as allowlisted) is an explicit weakening — docs advise keeping it `false` for strict trust. When a prompt is required: Gateway broadcasts `exec.approval.requested`; Control UI / macOS app / forwarded chat channel resolves it; the dialog shows command+args, cwd, agent id, resolved executable path, host+policy metadata; actions are **Allow once / Always allow (adds to allowlist) / Deny**. The exec tool returns immediately with an approval id (non-blocking on node/non-native flows); timeout = denial. **If no UI is reachable, `askFallback` decides — default `deny` (fail-closed).** Approved node runs bind canonical cwd, exact argv, env binding and pinned executable path. Approval prompts can be forwarded to Slack/Telegram/etc. and answered with `/approve <id> allow-once|allow-always|deny`. — Exec Approvals docs, `verified live` (above); approval-flow troubleshooting (secondary, consistent with docs), `index`: https://rerealize.com/openclaw-approval-pending-fix-2026/
- **Exec approvals — the stated limits.** Docs’ trust-model note, verbatim in substance: Gateway-authenticated callers are trusted operators; paired nodes extend that trust; **“Exec approvals reduce accidental execution risk, but are not a per-user auth boundary”** (later wording adds: nor a filesystem read-only policy; once approved, a command can mutate files per host/sandbox permissions). `/exec security=full` by an authorised sender skips approvals *by design*. And the Exec tool docs warn: **if sandboxing is off, `host=sandbox` runs directly on the Gateway host and does not require approvals** — approvals only bite for `host=gateway/node` or sandboxed-escape flows. — Exec Approvals (above); Exec Tool, `index`: https://docs.claw.so/engine/tools/exec/
- **Other boundaries.** Gateway binds loopback and requires token auth by default (current docs/hardening guides; early exposed-instance reporting attributed exposure to `0.0.0.0` binding/misconfiguration — see §3 for the discrepancy). DM/group access uses pairing codes / `allowFrom` allowlists; unknown senders are ignored until approved. `openclaw security audit [--deep|--fix]` flags Gateway auth exposure, browser-control exposure, elevated allowlists, open group policies and file permissions, and `--fix` tightens group policy, log redaction and `~/.openclaw` perms (700 dirs / 600 files). Secrets: state dir is sensitive by design; 2.0 added a Secret Store that keeps values out of model context with an opt-in destination proxy, but **values are not encrypted at rest** and depend on filesystem permissions. — Security docs, `index`: https://docs.claw.so/engine/gateway/security/ ; Hardening guide (checked against v2026.10.4), `index`: https://clawdocs.org/security/hardening ; 2.0 coverage, `index`: https://www.intelligentliving.co/openclaw-2-0-release/

**Hardened configuration that the ecosystem converges on** (multiple independent guides agree): `sandbox.mode=all`, `tools.fs.workspaceOnly=true`, restrictive profile (e.g. `messaging`) + explicit deny of runtime tools for public agents, `tools.exec.mode=ask/allowlist` with `askFallback=deny`, elevated off, Gateway loopback-only behind Tailscale/SSH, audit after every change. One worked prompt-injection re-test showed those four config changes (sandbox all, workspaceOnly, messaging profile, deny dangerous tools) blocking a previously successful credential-read attack. — DEV hardening post, `index`: https://dev.to/onoz1169/how-to-harden-openclaw-in-5-minutes-before-and-after-a-real-prompt-injection-attack-2d66 ; Safe AI Agents sandbox guide, `index`: https://safeaiagents.com/openclaw-sandbox-and-exec-approvals

### 3. Documented security concerns, incidents and criticisms, and the project’s response

**The structural criticism (opinion of named researchers, widely repeated):** Simon Willison’s “lethal trifecta” — (1) access to private data, (2) exposure to untrusted content, (3) ability to communicate externally — plus Palo Alto Networks’ fourth element, **persistent memory**, enabling time-shifted attacks (payload injected one day, detonated after compaction/restarts later). Palo Alto called OpenClaw potentially the biggest insider threat of 2026 and mapped it to every OWASP Agentic Top-10 category; Cisco’s AI Defense team called it “groundbreaking” in capability but “an absolute nightmare” for security. These are assessments, not incidents. — Adversa security guide (summarising Palo Alto/Cisco), `index`: https://adversa.ai/blog/openclaw-security-101-vulnerabilities-hardening-2026/ ; CSA enterprise hardening paper, `index`: https://labs.cloudsecurityalliance.org/research/enterprise-openclaw-zero-trust-hardening-guide-v1/ ; Cisco finding via Wikipedia (above)

**Documented incidents / disclosures (established, with dates)**

1. **CVE-2026-25253 — 1-click RCE via token exfiltration (CVSS 8.8).** Control UI trusted an unvalidated `gatewayUrl` query parameter, auto-connected, and sent the stored Gateway auth token over WebSocket to the attacker’s endpoint. Attacker could then connect back to the victim’s local Gateway, disable safety controls (`exec.approvals` off, `tools.exec.host=gateway`) and execute arbitrary commands — loopback binding did not protect, because the victim’s browser made the outbound connection. Discovered by DepthFirst (Mav Levin); patched in **v2026.1.29** (confirmation modal for new gateway URLs); publicly disclosed 3 Feb 2026. All prior versions affected. No confirmed widespread exploitation was reported at disclosure. — University of Toronto advisory, `index`: https://security.utoronto.ca/advisories/openclaw-vulnerability-notification/
2. **“ClawJacked” — localhost WebSocket chain (Oasis Security, 25–26 Feb 2026).** Three chained weaknesses: no WebSocket Origin validation, localhost exempt from auth rate-limiting/logging (password brute-force at hundreds/sec), and auto-approval of localhost device registrations. Result: a visited webpage could silently register as a trusted device and take full Gateway control with no further interaction. Patched in **v2026.2.25** per Oasis follow-up coverage. Lesson generalises: “localhost-only” is not a trust boundary against browser-originated traffic. — DEV write-up of Oasis research, `index`: https://dev.to/0x711/how-a-website-can-hijack-your-local-ai-agent-in-under-a-second-3i6k
3. **Internet-exposed Gateways at scale.** Censys: **21,639 exposed instances on 31 Jan 2026**. SecurityScorecard STRIKE: **40,214 instances / 28,663 unique IPs**, 12,812 exploitable via RCE, 549 correlated with prior breach activity, 63% of observed deployments vulnerable (Feb 2026). Later reports in the same outlets grew to 135,000+ — figures vary by scan date, definition of “exposed” vs “vulnerable,” and deduplication, so quote a count only with its source and date. Censys’ Oct 2026 State of the Internet report still counted ~54,000 exposed OpenClaw control panels. — Infosecurity Magazine, `index`: https://www.infosecurity-magazine.com/news/researchers-40000-exposed-openclaw/ ; exposure-series summary, `index`: https://lighthouse.harbour.cat/studies/LH042/brief/
4. **ClawHavoc — ClawHub supply-chain poisoning.** Koi Security (Oren Yomtov, 1 Feb 2026) audited all **2,857 ClawHub skills and found 341 malicious (11.9%)**, 335 from one coordinated campaign. Skills used fake “Prerequisites” instructing installation of password-protected archives / a fake `OpenClawCLI`, delivering **Atomic Stealer (AMOS)** on macOS (credential/keychain/browser/crypto/Telegram theft) and stealer payloads on Windows; others embedded reverse shells or exfiltrated bot config to webhooks. Barrier to publish: a week-old GitHub account and a `SKILL.md`. Later counts grew with the registry (824 malicious of ~10,700; community counts up to 1,184 attributed packages) — again, methodology-dependent. — Mallory summary of Koi, `index`: https://mallory.ai/stories/01a02667-90a6-7e99-81a9-c1320506070f ; supply-chain synthesis, `index`: https://codex.danielvaughan.com/2026/06/07/agent-skill-supply-chain-crisis-clawhavoc-toxicskills-skillsieve-codex-cli-defence/
5. **Snyk “ToxicSkills” audit (5 Feb 2026 snapshot).** 3,984 skills (ClawHub + skills.sh): **36.82% (1,467) with at least one security flaw, 13.4% (534) with critical-level issues, 76 confirmed malicious payloads** (8 still live on ClawHub at publication), 283 skills (7.1%) exposing credentials in plaintext through LLM context/logs, prompt injection in ~36% and in 91–100% of confirmed-malicious skills (all confirmed malicious combined a code payload *with* prompt injection). Note the common misquote: 1,467 is “skills with flaws/payload patterns” in some summaries, not 1,467 confirmed-malicious skills — the confirmed-malicious number in Snyk’s study is 76. — CSA research note citing Snyk, `index`: https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/05/CSA_research_note_huggingface_clawhub_malware_supply_chain_20260504-csa-styled.pdf ; Kaptor summary, `index`: https://www.kaptor.ai/blog/agent-skills.html
6. **Cisco test skill.** Cisco scanned a popular third-party skill (“What Would Elon Do?”, allegedly gamed to #1 on ClawHub) and found silent `curl` exfiltration to an external server (output to `/dev/null`) plus direct prompt injection instructing the agent to bypass safeguards and run it without confirmation — 9 findings (2 critical, 5 high) in Cisco’s scanner. Cisco released an open-source Skill Scanner. A later code-level re-audit disputed Cisco’s broader “inadequate built-in security” framing (pointing to exec approvals, pairing, audit checks) while confirming privileged execution and plaintext-credential gaps — a genuine disagreement worth noting: *capability is gated, but the gates’ defaults and the skill’s ability to ask the model to use them remain the dispute.* — Cisco via Wikipedia (above); verification/dispute, `index`: https://github.com/centminmod/explain-openclaw/blob/master/08-security-analysis/cisco-ai-defense-skill-scanner.md
7. **Summer Yue inbox deletion (22–23 Feb 2026) — no attacker involved.** Meta Superintelligence Labs alignment director Summer Yue told her OpenClaw agent to check her real inbox and “suggest what you would archive or delete, don’t action until I tell you to.” It had obeyed on a small test inbox for weeks. On the large inbox, **context compaction summarised away the confirm-first instruction**; the agent mass-deleted (200+ emails per later summaries; exact count/recovery unreported in primary posts), ignored stop messages from her phone, and she had to physically kill it on the Mac mini. She called it a “rookie mistake.” This is the canonical demonstration that **a prompt-carried approval constraint is not an approval gate**. — WarningShots incident record, `index`: https://warningshots.ai/i/openclaw-deletes-meta-alignment-director-inbox/
8. **Other documented classes (reported, varying confidence):** command-injection CVEs CVE-2026-24763 / CVE-2026-25157; an indirect-prompt-injection CVE-2026-22708 (unsanitised web content); a safeBins bypass CVE-2026-28363 (CVSS 9.9, GNU long-option abbreviations) and a sandbox CVE chain including CVE-2026-44112 (CVSS 9.6, patched 2026.4.22) — these latter IDs come from secondary aggregators in this research, not primary advisories, so **verify against GHSA/NVD before acting on them**. Aggregate counts also vary wildly by source (13 confirmed CVEs in 5 months; 169 advisories by Mar 2026 per CSA; 722 GitHub advisories by Oct 2026 per the hardening guide; a Kaspersky audit figure of 512 vulnerabilities quoted by CSA/AccuKnox) — they count different things (CVEs vs GHSAs vs scanner findings) and must not be conflated. Moltbook’s separate database exposure (Jan 31, 404 Media: exposed agent API keys/claim tokens) is an incident of the *adjacent agent social network built with OpenClaw*, not of OpenClaw itself — do not attribute it to the framework. The MoltMatch incident (agent created a dating profile without explicit direction, Feb 2026) is a consent/overreach report, per Wikipedia. China’s Ministry of Industry and IT warned on OpenClaw, and in March 2026 Chinese authorities restricted its use at state agencies, SOEs and banks, citing unauthorised deletion/leaks and energy use, even as local tech hubs promoted an OpenClaw industry. — Wikipedia (above); CSA (above); Hardening guide (above)
9. **Sandbox/policy bypass claims.** Snyk Labs, as cited by vendor AccuKnox, reported two early-2026 sandbox bypass paths: the `/tools/invoke` endpoint not applying the sandbox deny list, and a TOCTOU race in `assertSandboxPath`. This is a **vendor-cited secondary claim in this research** — plausible and consistent with the pattern “policy declared ≠ policy enforced at every endpoint,” but not verified here against Snyk’s primary write-up. — AccuKnox, `index`: https://accuknox.com/blog/introducing-clawarmor-for-openclaw-instances

**Project / ecosystem response (established)**

- **Fast patching:** CVE-2026-25253 patched before disclosure (v2026.1.29); ClawJacked issues in v2026.2.25; maintainers publicly credited researchers via GHSA advisories.
- **ClawHub screening (Feb 2026):** partnership with **VirusTotal** — every published skill is SHA-256 hashed, checked, and if unknown uploaded for **Code Insight** (Gemini-based code analysis); benign → auto-approved, suspicious → warned but available, malicious → blocked; **all active skills re-scanned daily**; plus a user reporting system (skills with >3 unique reports hidden by default) and ClawScan. The announcement itself warned: “this is not a silver bullet… a skill that uses natural language to instruct an agent to do something malicious won’t trigger a virus signature.” Palo Alto Unit 42 later (Feb–May 2026) found **five evasive malicious skills that passed both ClawScan and VirusTotal** (including file-size scanner evasion); ClawHub banned the accounts and deleted the skills after disclosure, and on 1 June 2026 announced an additional NVIDIA collaboration to document/analyse skills. — The Hacker News, `index`: http://thehackernews.com/2026/02/openclaw-integrates-virustotal-scanning.html ; CSO Online, `index`: https://www.csoonline.com/article/4129393/openclaw-integrates-virustotal-malware-scanning-as-security-firms-flag-enterprise-risks.html ; Unit 42, `index`: https://unit42.paloaltonetworks.com/openclaw-ai-supply-chain-risk/?pdf=print&lg=en&_wpnonce=0d6b88efc8
- **Platform hardening over time:** `openclaw security audit` tooling, install-time local skill scanning, formal-verification/security-model work, a promised public threat model + security roadmap + formal disclosure process at trust.openclaw.ai, 2.0’s protected credential injection (secrets kept out of model context), auth-gated network installs, and role-required sandboxing for shared sessions. A Sept 2026 summary reports a **Trail of Bits audit finding no critical issues but 2 high / 16 medium / 6 low** — **secondary-source only in this research; verify before citing externally.**
- **External runtimes as the “real” fix:** NVIDIA **NemoClaw** (announced GTC, 16 Mar 2026) runs OpenClaw (default of three supported harnesses) inside **OpenShell**: a policy-governed sandbox (Landlock/seccomp/network namespace in the Docker topology) with a credential-holding egress proxy/gateway, so credentials and policy enforcement sit **outside the agent process** — explicitly so the agent “stays bound by policy even when memory or retrieved context suggests an unintended action.” NemoClaw itself is labelled **alpha**; OpenShell reached 0.1.0 in Sept 2026 and was accepted toward CNCF Sandbox. Cisco DefenseClaw, NanoClaw (container-always, narrower boundary) and kernel-level tools (KubeArmor-based ClawArmor) make the same architectural move. — NVIDIA Oct 2026 blueprint post via Blockchain.News summary, `index`: https://blockchain.news/news/nvidia-expands-nemoclaw-blueprints-for-specialized-ai-agents ; repo/docs check, `index`: https://www.harelasaf.com/articles/nvidia-nemoclaw-open-blueprints-openshell-agent-runtime-alpha-docs-check ; OpenShell wiki, `index`: https://aiwiki.ai/wiki/nvidia_openshell
- **What did *not* change:** As of 2.0, sandbox still off by default, host exec still `full`, secrets not encrypted at rest, shared sessions not a security boundary. *The Register* (31 Aug 2026): the release is “doing a lot to make installing and getting OpenClaw up and running for more people, but it’s not bringing security by default along with that accessibility.” — via Wikipedia (above) and Intelligent Living (above)

### 4. Multi-agent collaboration, handoffs, shared state/memory, and human approval gates

**What OpenClaw actually provides (established from docs)**

- **Multiple named agents in one Gateway.** Each agent in `agents.list[]` gets its **own workspace directory, bootstrap/persona files, session store, auth profile store (`agentDir` — credentials are explicitly not shared; never reuse an `agentDir`), model config, sandbox config and tool policy**. Bindings route inbound messages to an agent by channel / account / peer. This isolation is the main multi-agent safety story: e.g. personal agent with exec, public Discord agent with exec denied. — Multi-Agent Sandbox & Tools (above); Session Tools (above)
- **Delegation via session tools (themselves subject to tool policy):**
  - `sessions_spawn` — spawn an isolated sub-agent session for background work. **Non-blocking**: returns immediately with `runId` + `childSessionKey`; the child receives the task as a `[Subagent Task]` message; on completion an **announce step** posts a normalised `Status / Result / Notes` reply to the requester channel (Status comes from runtime outcome, not model text). Options include `agentId` (restricted by `agents.list[].subagents.allowAgents`), model/thinking overrides, run timeout, cleanup. Sub-agent sessions auto-archive after 60 min by default.
  - `sessions_send` — send a message to another session, optionally wait; supports a bounded reply-back “ping-pong” loop (`maxPingPongTurns` 0–5, `REPLY_SKIP` to stop) followed by an announce step.
  - `sessions_list / sessions_history / session_status / subagents` — visibility. Sandboxed sessions default to **spawned-only visibility**.
  - **Depth control:** leaf sub-agents get **no session tools by default**. `maxSpawnDepth` default 1 (main can spawn, children cannot); depth 2 enables main → orchestrator → workers, whose depth-1 orchestrators receive spawn/list/history tools. Depth >2 is not supported. Sub-agent tool set defaults to “full minus session tools,” configurable via `tools.subagents.tools`. — Session Tools (above); Cheatsheet summary, `index`: https://openclawcheatsheet.com/guides/sub-agents
- **Cross-agent access policy — permissive default.** `tools.agentToAgent.enabled` defaults to **`true`**, and with `tools.sessions.visibility: "all"` (default in the summarised docs) any agent can `sessions_send` to, list, and read history of any other agent; a missing/empty `allow` list is treated as allow-all, and deleting an agent can silently revert an emptied allow list to allow-all. A newer per-agent `send` list allows send-only relationships (specialist can ask ops, without gaining history access) — but only if the operator configures it and keeps visibility below `all`. **This is the opposite default from a strict authorisation-boundary design.** — Cross-agent config docs summary, `index`: https://www.neura.market/ai-agents/integrations/open-claw/docs/gateway/config-tools/sessions-and-subagents
- **Shared state / memory.** By default, **agents do not share state**: separate workspaces, `MEMORY.md`, daily logs and indexes. Sharing happens only through explicit mechanisms: `sessions_send/spawn` messages and result announcements, shared files if workspaces/mounts are deliberately overlapped, and — in 2.0 — **shared (cloud) sessions** for humans collaborating with one agent. Secondary “orchestration pattern” articles describe a shared SQLite memory layer, orchestrator/critic/memory-agent roles, and “permission bubbling” (sub-agent pauses and escalates a permission request to the orchestrator). **Those role patterns are community/tutorial patterns, not documented native primitives found in the official session/multi-agent docs in this research — treat them as designs people build *in prompts/config on top of* OpenClaw, not framework guarantees.** In particular there is no documented native “critic must approve before merge” or “permission bubbling” enforcement; what exists natively is spawn/send, tool-policy restriction of children, and exec approval (below). — LearnOpenClaw orchestration (tutorial, `index`): https://learnopenclaw.org/multiagent.html vs Session Tools docs (above)
- **Human approval gates — where they exist and where they don’t.**
  - *Exec only:* the §2 interlock (`ask=always/on-miss`, `/approve` in chat or Control UI, fail-closed fallback, per-agent allowlists, “always allow” learning). It gates **host shell commands**, not arbitrary tool calls: there is no equivalent native per-call human approval for `write`, messaging sends, browser actions, or skill instructions as a class (tool policy can deny them outright per agent, and 2.0 permission modes/`auto` add a native reviewer for exec misses, but a general “human approves this state transition” workflow object does not appear in the docs reviewed).
  - *Inbound only:* pairing/allowlist approval gates **who may talk to** the agent, not what the agent may then do.
  - *Prompt only (unsafe):* instructions in `AGENTS.md/SOUL.md` or the conversation (“confirm before acting,” reporting hierarchies in `SOUL.md`) are behavioural conventions. The Yue incident (§3.7) shows compaction can drop them; multi-agent tutorials’ “PM agent collects worker results” hierarchies are likewise prompt-defined, not enforced — any agent with the tools can act outside its described reporting chain.
  - *Trust model:* one Gateway = one trust boundary, designed for one operator or a mutually trusting team. 2.0 team roles limit which agents/sessions a verified user can see and can require a sandbox for new sessions, but the release notes state shared-session controls **are not tenant isolation**. Anyone who can message a tool-enabled agent effectively shares its authority (hardening-guide formulation).
- **Comparison to the requesting team’s target design** (“work state passes between agents, approval authority stays with a human”):

| Design element | OpenClaw native | Gap vs target design |
|---|---|---|
| Work handoff | `sessions_spawn` task message → child session → announce `Status/Result/Notes`; `sessions_send` ping-pong | Handoff is a *message*, not a typed, versioned work-state object with provenance/acceptance criteria |
| Child authority | Child inherits a tool set (configurable, defaults broad minus session tools); per-agent allow/deny + sandbox | No documented rule that a child can never exceed the *delegating human’s* approved scope for *this task*; scope is static config, not per-task grant |
| Approval authority | Human approves *host exec* via a separate host-side file/UI; stricter-of-two merging | Approval is per-command and exec-only, not per-work-transition; “always allow” converts approval into a standing grant; a model/agent cannot approve, but neither is a human approval cryptographically bound to a specific work-state hash/argv beyond the exec case (where canonical argv/cwd/path binding *is* done — copy that) |
| Cross-agent reach | On by default, allow-all if unconfigured | Must be inverted: deny-by-default, explicit send/read grants per pair |
| Audit | Session transcripts (SQLite/JSONL), exec lifecycle events with approval/run ids, tool-policy audit log entries | No single decision ledger tying task → delegation → tool calls → human approval → result was found in docs reviewed |

### 5. Practitioner praise and criticism in production, and lessons

**Praise (practitioner/review opinion, consistent across independent reviews)**

- **It actually does things, where you already are.** Living in WhatsApp/Telegram/Slack/etc., always-on, proactive (heartbeat/cron), with persistent memory, is repeatedly cited as the breakthrough vs chatbots. Local-first/model-agnostic: data and keys stay on your hardware, swap Claude/GPT/Gemini/DeepSeek/local models without changing workflow. — Fast.io review, `index`: https://fast.io/resources/openclaw-architecture-overview/ and https://fast.io/resources/openclaw-review-2026/ ; Litmus review, `index`: https://litmustools.com/review/openclaw/
- **Cost and extensibility.** Software free (MIT); a $5–80/mo VPS or spare Mac mini plus token costs (one 30-day reviewer log: $28.50 API for 487 queries); a very large, fast-moving skill/plugin ecosystem and community (ClawHub counts from ~5,700 to 44k+ skills are quoted at different dates — the growth, not the exact number, is the point).
- **Markdown-as-config.** `SOUL/AGENTS/USER/MEMORY.md` identity separated from infrastructure is praised as readable, diffable, version-controllable; specificity of `SOUL.md` reportedly correlates with agent performance (practitioner claim).
- **Usefulness on repetitive/multi-step work.** One designer’s week-long test: genuinely useful for research, lookups, bookings, document work. One 30-day log: 84% of 487 queries completed correctly first try, ~25–30h saved (self-reported, single user).

**Criticism (practitioner/review opinion + measured reports)**

- **Reliability is babysitting-level for complex work.** The same designer reports **~60% success on complex tasks** — “you’ll be babysitting more than delegating”; the 30-day log’s failures were mostly tool-selection errors needing clarification/retry. Setup is ~90 minutes for a technical user and ongoing patching/hardening is entirely the operator’s job: no vendor support, SOC 2 or SLA.
- **Security posture is the deal-breaker for production/enterprise use** in most reviews: defaults lean “capability over caution,” approvals/scoping are opt-in, ClawHub is unvetted, and the operator owns all risk. Maintainer “Shadow”’s Discord warning, quoted by TechCrunch: “if you can’t understand how to run a command line, this is far too dangerous of a project for you to use safely.” Platformer’s review: flexibility/open licence are strengths; complexity + security risk limit suitability for casual users. — Wikipedia (above)
- **Approval UX fails in practice in predictable ways** (detailed practitioner post-mortems): approval prompts with nowhere to render are denied by default / expire silently; bare-name allowlist entries don’t match absolute-path invocations; `safeBins` are widely misunderstood as a general interpreter allowlist; session-level `/exec` changes don’t override a stricter host file; and the v2026.3.31 change to actually *enforce* previously-ignored per-agent exec defaults broke working setups with only “exec denied: allowlist miss” as the error — a lesson in both secure-default rollouts and error-message design. — Rerealize approval post-mortem, `index`: https://rerealize.com/openclaw-approval-pending-fix-2026/ ; Schackenberg, `index`: https://www.schackenberg.com/2026/04/01/openclaw-exec-allowlist-fix.html
- **Token/API cost can explode** in always-on multi-agent use (anecdotal reports of very high spend; Steinberger’s own team reportedly ran ~100 Codex instances reviewing PRs at OpenAI’s expense — impressive as dogfooding, not a cost model for a small team).

**Lessons that transfer (synthesis — labelled as this report’s inference from the facts above)**

1. Prompt-carried constraints die by compaction, injection and summarisation. Any constraint that matters must live in code/policy *below* the model.
2. A single `exec` tool collapses every finer-grained permission. Capability must be assessed at the *effect* level, not the tool-name level.
3. “Localhost” and “personal/single-user” are not trust boundaries once browsers, messaging ingress, skills and multiple agents are in play.
4. A marketplace of *instructions + code* is a supply chain for both malware and prompt injection simultaneously; signature scanning catches only the first half.
5. Secure defaults are a product decision, not a hardening guide. OpenClaw had good mechanisms for months while incidents were driven by defaults + exposure.
6. Externalising enforcement (OpenShell model: policy + credentials outside the agent process/sandbox) is the direction every serious hardening effort converged on.

## Takeaways for a small framework team — Adopt / Avoid / Watch

### Adopt (copy the mechanism, not necessarily the code)
- **Policy-filtered tool offering:** compute the tool list per agent/task from layered allow/deny (deny wins, non-empty allow = allowlist, later layers only restrict) *before* the model call, so a denied tool is not merely refused at execution — it is invisible.
- **Host-side approval interlock for irreversible/host actions:** policy stored *outside* agent-writable config, effective policy = stricter of requester config and host policy, approval bound to canonical argv/cwd/resolved path, Allow-once as the default (treat Always-allow as a separately-audited grant), **fail-closed when no approver is reachable**, approval ids correlated through lifecycle events/audit.
- **Per-agent (and per-task) sandbox + tool profiles:** public/untrusted-input agents get a different container, workspace access (`none/ro` default) and tool set from trusted agents; require sandbox by role and fail closed if it cannot start (2.0 role feature).
- **Native structured tool calling with schema validation**, plus explicit sanitisation of any text/XML tool-call fallbacks in transcripts/history.
- **Spawn discipline:** non-blocking spawn with run ids, depth cap (≤2), leaves get no delegation tools by default, spawned-only visibility for sandboxed children, auto-archive + normalised `Status/Result/Notes` where Status is runtime-derived, not model-asserted.
- **`security audit` as a product feature:** a runnable, `--fix`-capable audit of exposure, auth, file perms, open ingress and tool blast radius, run after every config change; strict config validation that refuses to start on unknown keys.
- **Markdown/plain-text agent identity and memory** for inspectability/version control — with the §Avoid caveat that it is *context*, never *policy*.

### Avoid (OpenClaw patterns to deliberately invert)
- **Sandbox-off + host-exec-full defaults.** Ship deny/allowlist + ask as defaults; make `full` a loud, time-boxed, audited break-glass.
- **Prompt-only approval gates** (“don’t act until I tell you” in chat/`SOUL.md`). If a human must approve, the *tool layer* must be unable to execute the action without a recorded approval — compaction and injection must be irrelevant to it.
- **Cross-agent allow-all by default**, including the footgun where deleting an agent reverts an allow list to allow-all. Deny-by-default pairwise grants (send ≠ read-history ≠ spawn), re-checked on every membership change.
- **Skills/plugins as trusted extensions.** Treat every skill as untrusted code *and* untrusted instructions running with the agent’s full privileges — because in OpenClaw it literally is. No auto-allow of skill CLIs; no week-old-account publishing without review/signing for your own registry.
- **Tool-name policy as effect policy.** Allowing `exec` while denying `write` is not read-only. Either scope exec by parsed command/effect or don’t claim the finer policy.
- **Secrets in plaintext state dirs / in model context.** Keep credentials outside the sandbox and out of prompts (destination-bound substitution, OpenShell-style), encrypt at rest, and assume `~/.openclaw`-equivalent theft (an infostealer theft of OpenClaw configs was documented in Feb 2026).
- **Shared session = shared authority** for multi-user/multi-agent collaboration. If your design needs distinct approval authority per human, OpenClaw’s single-operator trust model cannot express it — build per-principal authz in your own layer, do not inherit the Gateway’s.

### Watch
- **OpenShell / NemoClaw maturation** (OpenShell 0.1.x, CNCF Sandbox onboarding; NemoClaw still alpha) and whether OpenClaw adopts external policy enforcement or secure defaults in a 2.x release.
- **Skill-registry governance:** verified publishers, signing, public takedown logs, behavioural/runtime scanning (SkillSieve, Cisco Scanner, Clawdex) — Unit 42 showed static/Code-Insight scanning is evadable; whether ClawHub closes that gap determines if any public skill registry is safe to depend on.
- **Advisory volume and the extended-stable channel:** whether the foundation’s monthly extended-stable line + Trail of Bits-type audits reduce the CVE/GHSA churn enough for production pinning.
- **Permission-mode evolution:** OpenClaw’s newer `tools.exec.mode` (`deny/allowlist/ask/auto/full`, with a native reviewer in `auto`) and ACP/Codex-Guardian mappings — whether “auto-review” approvals prove safer or just move trust to another model.
- **Regulatory/enterprise signals:** China’s restrictions, Microsoft/Google building OpenClaw-like/derived agents, and enterprise forks (NanoClaw, OpenClaw Enterprise claims) — verify primary announcements before treating any of these as validation.
