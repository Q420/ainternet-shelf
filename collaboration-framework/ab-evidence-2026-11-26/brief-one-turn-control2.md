The framework described in the Vane stock‑take is a control for a whole standing job in a single turn, built around persistent seats, a bounded record‑and‑doorway system, and a set of accountability mechanisms that let a generated worker be assembled, granted limited resources, and run inside a bounded loop. The design defines a clear separation between mechanisms that have passed examination and capabilities that have been shown to work in actual assignments.

What is proven is that the Stage 2 accountability foundation is real and fully implemented, with machinery for record, doorway, bubble, seat drivers, office, onboarding, gates, orchestrator, observer and checker all present and verified. A1, A2 and A3 are passed mechanisms: A1 proves that a worker instance can be assembled, its grants sealed and enforced at dispatch; A2 proves that tool requests, dispatch, and per‑tool registry checks are mediated, counted and accounted for, with a durable execution claim and a recovery contract; A3 proves that a bounded loop can repeatedly present a case view, receive responses, enforce temporal limits, record uncertainty and detect stalls. The A2 implementation scope is authorized and confined to A2, and the A3 scope is authorized and confined to A3, so the core runtime for a bounded worker is demonstrably closed.

What remains unproven is the complete founding proposition that a generated worker can be given a real, bounded assignment, make useful progress, record its actions, yield, and allow another independently generated worker to continue from that state. A4, A5 and A6, which would close the essential parts of that proposition — governed access to the shared brain, a real boundary between authority and continuing work, and a blind‑handoff demonstration — have not been built or examined. The ability for work to move between independently generated agents without authority, context or accountability shifting accidentally has also not been demonstrated.

Four worries are highlighted. First, a correct execution mechanism does not make the model competent; a loop that can perceive, request, act and account for outcomes cannot guarantee useful reasoning or quality work. Second, passing each piece separately hides integration risk at the seams; the whole path may fail even though each component passes its own tests. Third, the strongest evidence comes from environments that are easy to simulate — the checker, test suites and examiner all operate on constructed evidence, while live‑record replay and real work products provide the needed counterweight. Fourth, boundaries versus substrate are unclear; a recorded termination is not proof that a remote model operation ceased, revocation of a credential does not guarantee every copy vanished, and an uncertain outcome does not resolve an external side effect.

The honest next step is to pause and agree on what the existing evidence actually establishes before proceeding to A4. Rather than building more machinery that assumes the worker can succeed, we should run a first generated worker on a modest real bounded assignment and see whether it can complete the task and yield work that another worker can continue. If that test fails early, we learn something the cleanest test suite cannot, and we can adjust the design before investing further effort. The immediate concrete action is to execute a live‑record replay of a complete worker run and to test the blind‑handoff scenario, thereby closing the gap between proven mechanisms and proven agentic collaboration.

We have a serious foundation and three proven implementation pieces, but agentic collaboration has not yet been demonstrated; the next honest move is a pause, agreement on what is proven, and a concrete test of the full worker lifecycle.
