**Central conclusion:** "we should stop treating native tool expression as a compatibility problem to be suppressed, and start treating it as the model's normal request language, with our framework retaining complete authority over what happens next."

1. **The text contract was fighting the model's training.** The evidence converges: Harmony's native tool-call channel and its intended use; agentic training (interleaved reasoning, calls, observations, actions); *The Reasoning Trap*'s mechanism for why an abstention instruction may not override the learned action preference; the independent same-stack failures; the model-specific benchmark cutting against the assumption that text was the safer interface. **She now regards text-only expression as a poor default for this particular model and task shape** — explicitly not a universal judgement about text protocols. Qualification kept: the literature supports the mechanism, but there is still no controlled study of our exact multi-step assignment; the paced repetition adds evidence but cannot settle every question.
2. **Native presentation does not mean native authority** — "the most important architectural distinction in the report." The model may *say* "I want to call `sandbox.read_range` with these arguments"; it must not be able to decide "I am therefore permitted." The framework still: resolves the name against the sealed granted catalogue; validates arguments/schema; checks grant, bounds, policy; dispatches only through the doorway; records request, decision, execution, outcome; returns the result against the original call ID. "The provider's tool schema is an interface description, not an authority document. The sealed briefcase and doorway remain the authority chain." "This is not a concession to agentic behaviour. It is a better way to channel it."
3. **Unoffered calls should become an explicit doorway decision.** Provider wholesale rejection vs provider returning the call to our resolver, which rejects it and returns a structured error: the second is potentially much better (preserves the turn; gives the model an observation it can respond to). Groq's `disable_tool_validation` is worth investigating, with its limit noted (it does not override tool_choice none/required): native tools offered with natural tool-choice, then verify what the provider actually returns for an unoffered name. **Non-negotiable:** an unoffered call is never dispatched merely because the provider returned it; the resolver rejects before execution and returns an error result only after that rejection is recorded; the error stays narrow and factual (tool unavailable; permitted alternatives) and must not imply the rejected action was attempted or executed.
4. **Salvage stays separate from the primary architecture.** `failed_generation` recovery is a defensive fallback, never the worker loop's foundation (unstable payload shape; provider-specific; leaves the interface mismatch in place; risks error-parsing becoming an alternative route into dispatch). If ever implemented, it translates into an ordinary typed request through exactly the same doorway — never executed directly from the error body.
5. **The next architectural decision splits into two distinct questions, kept separate:** (Q1, *empirical*) can the provider reliably return native calls for the granted tools under the exact request configuration? (Q2, *architecture/implementation*) can our adapter translate every returned call into the existing framework request contract without creating a second authority path? **She now favours a native-first adapter for this pinned model, with a closed-world resolver and structured error results — but not jumping straight into building it.** The paced repetition remains useful evidence (it holds the intervention constant); she is **not withdrawing the release requirement and not authorising the five requests**; she will examine the clock-correction letter when it arrives, then decide whether that experiment is still the right next measurement.

**Her overall finding:** "The research does not tell us to make the framework more permissive. It tells us to make the interface more compatible while keeping authority exactly where it belongs." And: **"we should adapt the framework's interface to the model, not adapt the framework's authority to the model."** No build, compatibility scope, or additional provider request is authorised by this letter.
