# GAP MAP 01 — The first real worker in a framework seat

**Date:** 2026-11-23. **Author:** Remmy. **Status:** the inventory's stopping point, per Ben's rule — the map is complete when it suffices to design one real generated worker. It is not a design, not a scope, and authorises no building. The agent paper follows from it (Vane's sequence: Ben's review → paper → examination → revised design/spec → Ben's ruling → implementation scope).
**Evidence base:** Inventories 01–04 (INDEX 145, 146, 149, 150), Vane's examination and its ten framing questions (INDEX 147–148), preliminary observations G1–G13.
**Dispositions:** Own / Borrow / Build / Integrate / Unresolved — borrowing execution never means borrowing authority (Vane).

---

## The worker this map is for

The smallest real generated worker: assembled by the office for one bounded assignment; reads named shelf material; uses a small number of granted tools inside a bounded loop; contributes its work to the run record under its case; yields with a continuation package a second, blind generated worker can pick up. Anything beyond that — more tools, more workers, richer runtimes — is later, one piece at a time.

## The ten areas

**1. Agent assembly — Can the framework generate a worker for one specific assignment?**
State: nothing exists; the office packs cases for seats that already exist (Inv. 04, systems 7/16). Gap: the whole component. **Disposition: Own the function (office), Build the subsystem.** Smallest sufficient step: an assembly act in the office that emits an inspectable assembly record — model choice + basis, identity declaration, skill list with versions, tool grants, case binding — before any worker runs. The record comes first; a generator whose assemblies aren't recorded is the specimen's inheritance with better marketing.

**2. Identity — Can the actual proposed model's identity be established and weighed before activation?**
State: onboarding exists and is demonstrated (declaration verbatim, fingerprint-bound tokens, attested upgrades; the adapter's `identify()` keeps declaration and provider-reported id as distinct claims — Pieces 6.1/8). Gap: it is once-per-seat; a generated instance needs its identity weighed *at its assembly*, and the seat-spec / instance / briefcase distinction is unresolved against Rev 5. **Disposition: Integrate what is built; the reconciliation is a paper decision, not new machinery.**

**3. Skills — Can the office provision the required set without transferring unrelated procedure or authority?**
State: a working library format that grants no authority (Inv. 01); a classified seed set (situational P skills); per-candidate dependency examination still owed for any actual transfer (Vane's caution, INDEX 147). Gap: no provision mechanism — the case must name skills, the office must supply exact versions, and use must be recordable in the four states (available / consulted / applied / verified, as distinct evidence levels). **Disposition: Integrate the format and seed set; Build provision + use-recording (small: a case field, an office supply act, a driver-carried declaration of which skill informed an act — G5).**

**4. Tools — Can exact case grants control availability and dispatch?**
State: the framework has no seat tools at all; the specimen has a rich surface provisioned per-agent with a human veto (Inv. 02). Gap: grants as case content; a dispatch point that checks grant before execution (the doorway pattern, extended from record acts to tool acts); per-tool side-effect data extracted **only for the first worker's candidate grants** (stopping rule). **Disposition: Own the grant + dispatch boundary; Borrow/Integrate execution behind it (the specimen's tool surfaces are the candidate pool); Build the grant check.**

**5. Context — Can the worker reconstruct its context from briefcase + shelf, with no inherited session state?**
State: the case mechanism is built; the shelf stores but does not provision (Inv. 03). Gap: a retrieval manifest in the case (what must be retrieved, what may be, what is sealed off) and read receipts in the record (G10); access partitioning for sealed material (G11) — for the first worker, partitioning can be doorway-mediated retrieval rather than shelf-side access control, if the paper accepts that shape. **Disposition: Own the contract; Build manifest + receipts; Integrate the shelf as the store, unchanged.**

**6. Runtime — Can the seat execute a real bounded tool-use loop?**
State: the adapter is one-exchange (Inv. 04, system 6). Gap: the loop itself — perceive, request tool, receive result, continue, yield — with every iteration visible to the record and a hard bound (steps, time, or both). Candidates on the table (Vane's routes, INDEX 142): extend our adapter into the loop (her preferred destination); a session-system runtime as demonstration substrate (fastest, carries inheritance risks G8 names); Paperclip as execution substrate only. **Disposition: Unresolved — the map's one genuinely open choice.** The paper must decide it against the contract, not by convenience; what is not open is that the runtime never becomes an authority, whatever is chosen.

**7. Record — Can every consequential act be attributed to the generated worker and its case?**
State: the record + doorway + checker are built and passed (Inv. 04, system 9). Gap: new event kinds — tool acts, retrieval receipts, assembly records, skill-use declarations — folded into the same record under the same one-fold rule, and the checker's replay extended to them. **Disposition: Own (exists); Build the new event types as a design-led extension, examined like every piece before it.**

**8. Yield — Can the worker finish its bounded part and leave a usable, verifiable continuation package?**
State: case versioning and corrections exist; yield as a first-class operation does not (Vane's correction, INDEX 141: yielding, construction, validation, approval, receipt are architectural operations). Gap: a yield act whose product is a new case built by the office from the record — never summarised from the worker's memory (the Inventory 01 case-study conclusion). **Disposition: Build on the office's existing machinery.**

**9. Handoff — Can a newly generated, blind worker continue from the new case + shared brain?**
State: **not demonstrated anywhere.** The §7 live run showed influence inside one run (crew-b answering crew-a through the record) — that is collaboration, not handoff: no new case, no blind worker, no reconstruction. Gap: the whole path, and it is the founding picture's core claim — the work surviving the change of agent. **Disposition: Build (areas 1–8 are its parts); its first demonstration is a Stage 3 design question for Ben, not an inventory question.**

**10. Termination — Can the previous worker's authority and execution end cleanly at yield?**
State: seats hold persistent tokens today. Gap: a yielded worker must keep its history and lose its live permissions. A mechanism precedent exists in the build: onboarding-route tokens bind to a fingerprint and a pre-onboarding commission token dies once onboarding stands (Piece 6.1) — token death at a recorded state change is already a built pattern. **Disposition: Build on that precedent — case-bound credentials that die at the yield event, enforced at the doorway.**

## Responsibility summary

| Area | Disposition |
|---|---|
| Assembly contract + office function | **Own** |
| Generator subsystem | **Build** (inside the office) |
| Identity mechanism | **Integrate** (built); reconciliation = paper decision |
| Skill format + seed library | **Integrate**; provision = **Build** |
| Tool grant + dispatch boundary | **Own**; execution = **Borrow/Integrate**; grant check = **Build** |
| Retrieval contract | **Own**; manifest + receipts = **Build**; shelf store = **Integrate** as-is |
| Runtime loop | **Unresolved** (paper decides; authority never borrowed) |
| Record | **Own** (built); new event types = **Build** |
| Yield / handoff / termination | **Build** on office + doorway precedents |

## What this map deliberately does not decide

The runtime choice (area 6); the seat/instance reconciliation (area 2); the ordering of assembly against Generate–Verify–Pack–Approve; whether tool grants extend the case's authority field or sit beside it; and the first job itself — Stage 3 is picked with Ben. Those are the paper's questions and Ben's rulings, in that order. The map's claim is narrower and, per the stopping rule, sufficient: **every gap between the framework as built and one real generated worker is now named, evidenced, and dispositioned — and only one of the ten is an open choice rather than work to design.**

## Examiner corrections carried into the paper (Vane, 2026-11-23 — INDEX 152)

- **A. The write path (G12) and findability (G13) — omission corrected.** Area 5 covers retrieval only. Added as area 5's other half: **a generated worker's durable output must enter the shared brain under its own identity and case** — a contribution in the run record and a durable artifact on the shelf are related, not identical. Disposition: **Own the publication contract; Build attributed publication** — the paper must decide how a worker's deliverable is published, attributed, verified and made discoverable, without Remmy's manual publishing discipline as an invisible dependency. Findability (G13) is likewise the paper's to settle: whether a retrieval manifest suffices or machine-findable structure is needed.
- **B. "Only open choice" — distinction preserved.** The runtime is the one unresolved **responsibility disposition**. The seat/instance reconciliation, assembly ordering, and tool-grant field shape are cross-cutting **design questions** reserved for the paper. The map's closing claim must be read in that sense.
- **C. Skill-use evidence — four states, four mechanisms.** Available rests on provision evidence; Consulted on read receipts; Applied on the worker's declaration; Verified on an examiner's (or authorised process's) finding. A driver-carried declaration supports the applied claim only — it cannot prove consultation or verification. Area 3's "use recording" is to be designed as four distinct mechanisms, never one self-reported field.
- **D. Termination — two guarantees, not one.** Credential death (case-bound authority unusable at the doorway) and execution death (the worker's active process/session actually terminated, with evidence of termination) are distinct. The Piece 6.1 precedent covers the first only. Area 10 requires both; historical identity and contributions remain, live authority and execution do not.
- **Boundary clarification (area 5).** Doorway-mediated partitioning is viable only if every relevant read actually passes through that doorway. The shelf today has broad repository access and no framework read API; a manifest plus receipts does not enforce exclusion against a side route. The paper must specify the first worker's actual access path and make bypass impossible for its protected evidence — instructions and intentions are not access controls.
- **Handoff — the acceptance shape.** The first real demonstration must show the full chain: A generated for a bounded assignment → A retrieves provisioned context and does real work → A records contributions and yields → the office constructs and issues the continuation case → A's authority and execution terminate → B independently generated, no inherited private session or context → B reconstructs from case + shared brain and continues → the record makes the whole chain attributable and independently examinable. Failure conditions, any one sufficient: B needs A's private conversation (continuity failed); A retains authority after yield (boundary failed); the continuation is a summary with no recoverable evidence (handoff failed).
