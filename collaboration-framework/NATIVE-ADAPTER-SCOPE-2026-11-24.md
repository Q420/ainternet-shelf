## §1 The seam, stated plainly

**N1 — Three verbs, three owners.** The model *proposes*: a native tool call is a structured request in the model's native request language, nothing more. The adapter *translates*: it converts a provider-shaped call into the framework's existing typed request, or records why it cannot. The doorway *decides*: grant, bounds, policy, dispatch and recording remain exactly where they have always been. No verb migrates. In particular, translation is a **classification** act (is this call presentable, and as what?) and never a **permission** act — a translated request faces `Doorway.request_tool` exactly as its text-form twin does, and the doorway re-checks it whole (see N9).

**N2 — The offered definitions are derived, never authored.** The native definitions offered to the provider are derived from the package's own tool catalogue by the existing derivation — `OpenAICompatibleAdapter._native_tool_definitions` (adapter.py), the same per-grant derivation the native-offer probe used through `native_probe.derive_offered_definitions` — over the catalogue the loop derives from the sealed ASSEMBLY_GENERATED grants (`Loop._derive_catalogue`, loop.py). The catalogue describes authority; it creates none (A3-CAT's standing rule). The adapter invents, renames and supplements nothing; a tool with no sealed grant has no definition, and a definition's presence in a request is not evidence of a grant.

**N3 — The closed world.** The resolver's world is the sealed catalogue of *this* package: the exact names the derivation offered, under the registry version the iteration records. A name outside that set — `container.exec`, a built-in-shaped name (`browser`, `python`), a plausible near-miss of a granted name — is not a request and can never become one. It is a refusal (§3). There is no fallback that maps an unoffered name onto a granted one, no fuzzy matching, no shell.

**N4 — One authority path, auditable.** After this piece, a native call can reach execution by exactly one route: translation → the loop's adjudication → `Doorway.request_tool` → the doorway's recorded dispatch → the executor. Any code path by which a provider call could reach the executor, the record, or a tool result without passing `request_tool` is a defect in the build, not a feature of it. The build's witnesses (§9) include a doorway-invariance witness whose whole job is this claim.

## §2 The translation contract, step by step

For one iteration whose sealed mode is native (on mode, see N28), the response's handling is:

**N5 — Capture first, interpretation second.** The provider call runs under the standing evidence sequence unchanged: LOOP_ITERATION → CALL_ENTERED → the call → the seam's evidence persisted → the RESPONSE_EVIDENCE disposition committed → only then any effect (Rev 8 §R2-3 ordering). Native mode changes nothing before this point and nothing about it. The full assistant message — `tool_calls` included — already stands in L3 of the evidence artifact (`evidence.derive_layers` derives L3 as the complete message object); translation works from that message and invents nothing the capture does not contain.

**N6 — Per-call extraction; call-ID integrity (Rev 2).** From the captured message's `tool_calls` list, in emitted order, one extraction record per call: the **provider call ID** (`call.id`, exactly as emitted), the **name** (`call.function.name`), the **arguments** (parsed from `call.function.arguments` — the JSON string form the route has emitted in every observation to date; an already-object form is accepted, as the existing translator accepts both), and the call's **provider ordinal** in the response (the first of the two ordinal concepts N20 preserves). *Gap, named:* neither existing native seam preserves the provider call ID — the adapter's `_translate_tool_calls` returns `{tool, parameters}` only, and the probe's `_call_record` likewise records no `id`. Carrying the ID end to end is new, bounded work in the adapter's translation and in the record's request binding (N11), and §9 witnesses it. **Call-ID integrity rule (P3 settlement, INDEX 355):** the provider call ID is the normal correlation mechanism (N11), on the examiner's settled evidence (N38). A call whose ID is **absent**, or whose ID **duplicates** an ID already extracted earlier in the same response, cannot be bound for correlation and is refused at translation under `malformed_call`, with the failing point named (call ID absent / call ID duplicated) and its provider ordinal recorded, so the refusal itself remains correlatable by ordinal in the record. The first occurrence of a duplicated ID stands on its own merits; each later reuse is refused. This is a refusal rule, not an ordinal fallback: the design does not silently re-key a call whose own reference is broken.

**N7 — Closed-world resolution.** Each extracted name is resolved against the sealed catalogue **of the package this iteration presented** (the same catalogue object whose hash LOOP_ITERATION recorded — not a re-derivation, not the registry at large). Resolution has exactly two outcomes: *resolved* (the name is a catalogue entry of this package) or *unknown* (§3 refusal, class `unknown_tool`). Resolution confers nothing: it classifies the call as presentable. The doorway's own grant check (`Doorway._dispatch_check`, against the sealed generated record) runs afterwards on every presented request, unchanged — so a resolution error in the adapter cannot manufacture a dispatch: worst case it presents a request the doorway refuses on its grant ground, recorded as today.

**N8 — Schema validation (Rev 2, OQ5 ruled).** A resolved call's arguments are validated against **its catalogue entry's parameter schema** — the registry's worker-facing schema the catalogue carries (`tool_policy.worker_facing`, joined into the entry by `_derive_catalogue`). *Gap, named:* no such conformance validation exists today. The doorway checks the grant's *scope ceiling* (`tool_policy.check_ceiling` — paths, ranges, bounds) at dispatch; nothing anywhere checks that arguments conform to the advertised schema (required fields present, types as declared, no undeclared fields). This piece adds exactly one new component: a **pure argument validator** over the catalogue entry's schema — no I/O, no record access, deterministic in (schema, arguments) — whose verdict is `valid` or `invalid` with the first failing constraint named. **Settled (OQ5, INDEX 355):** the validator is a pure, deterministic **runtime validator at the native translation boundary**. The doorway does **not** hold a copy of it: schema conformance is a translation classification, not a permission, and the doorway remains the authority for grant, ceiling and dispatch. The checker holds its own independent implementation and reconstructs the schema verdict from the same inputs (§6). Conformance is **strict**: no type coercion, no invented defaults, and **no undeclared fields admitted** — an argument field the schema does not declare is `invalid_arguments`, not a detail left to the ceiling check. A schema construct the validator does not support **fails closed**: the call is `invalid_arguments` with the unsupported construct named, never silently ignored. A schema-invalid call is a §3 refusal, class `invalid_arguments`. The doorway's ceiling check is **not** replaced by this validation: schema conformance and grant scope are different questions, and both are asked, in that order.

**N9 — Conversion to the existing typed request.** A resolved, schema-valid call converts to the framework's existing request shape — `{"tool": <name>, "parameters": <arguments>}` — the exact shape `Loop._validate_requests` admits and `_translate_tool_calls` already produces. No new request type is introduced. The converted requests join the iteration's outcome as its `tool_requests`, in emitted order, and from this point the iteration is **indistinguishable from a text-mode iteration that carried the same requests**: the loop's whole-response validation, per-request adjudication (`Loop._adjudicate`), loop-assigned request identity (`loop-<instance>-<iteration>-<ordinal>`, R47/R48), `Doorway.request_tool`, dispatch, executor performance and TOOL_OUTCOME recording all run exactly as they run today. This is the doorway-invariance claim, and it is the piece's centre: **native mode is a second *entrance* to one corridor, not a second corridor.**

**N10 — What conversion must not do.** Conversion never repairs: it does not coerce argument types, fill defaults the schema declares but the call omitted (a missing required argument is `invalid_arguments`, not an invitation), trim undeclared fields into acceptability, or split one call into several requests or merge several into one. One provider call converts to at most one framework request, under its own ordinal.

**N11 — The result returns under the original provider call ID.** The recorded outcome of a presented request — dispatch result, uncertain outcome, or doorway refusal — is bound to the provider call ID that proposed it: the binding (provider call ID ↔ loop request_id ↔ dispatch_id, with both ordinals, N20) is recorded in the translation record (N32), and the package that presents the outcome to the model (N26) carries the provider call ID beside the loop's request_id, so the model's own reference for its call is the reference its result answers. The provider call ID is a *correlation* identifier only: identity for replay and adjudication remains the loop's (R47/R48 unchanged — a re-emitted call in a later iteration is a new presentation with a new loop identity, exactly as a re-typed text request is).

**N12 — The text channel in a native response (Rev 2, OQ2 ruled).** A native response carrying both non-empty content and tool calls is malformed whole (adapter.py, `_call_typed` native branch) — the channels are not mixed, and a contribution is not quietly combined with a set of proposed effects. A native response with no tool calls is read on the text path exactly as a text-mode response is (the contract remains in the prompt; the outcome set is unchanged). **Settled (OQ2, INDEX 355):** the mixed rule stands as the design. A later design may revisit it with evidence and a separate decision; this scope does not.

**N13 — Fail-whole is replaced by per-call granularity — at translation only.** Today `_translate_tool_calls` fails the whole response on any defective call (unparseable arguments, unreadable name), and the loop's answer is a stall. Under this piece, a defect *inside one call* refuses that call (§3) and does not touch its siblings (§4). Defects *of the response as a whole* — no readable message, an unreadable `tool_calls` structure (not a list, entries not objects in a way that prevents per-call extraction at all) — remain whole-response failures under the existing failure kinds, evidenced as today. The boundary is: where a single call can be individuated, it is individuated; where it cannot, the response has not made separable proposals and there is nothing per-call to refuse.

## §3 Translation and doorway refusals

**N14 — Four refusal classes, one shape (Rev 2: a fifth at N22).** A call that does not reach dispatch is refused under exactly one class, recorded with the call's extraction record (N6):

- `unknown_tool` — the name does not resolve against this package's sealed catalogue (N7). `container.exec` lives here, permanently.
- `malformed_call` — the call cannot be individuated or its arguments cannot be parsed into an object (unreadable name, unparseable arguments string, non-object arguments) — or its provider call ID is absent or duplicated (N6).
- `invalid_arguments` — the call resolves, but its arguments fail the catalogue schema (N8).
- `doorway_refused` — the call was presented as a typed request and the doorway refused it (no grant, ceiling, bound, temporal or aggregate ground). This class already exists in substance: `request_tool` records TOOL_REQUESTED, then a REJECTION naming the ground (R55), and the loop collects the refusal without discarding anything independent of it. Native mode inherits it unchanged.

A fifth class, `call_cap_exceeded`, is defined at N22 (overflow beyond the per-response cap) and shares this shape. The first three classes are new *as recorded per-call decisions*; today the first is indistinguishable from a grant refusal (it reaches `request_tool` and is refused there — recorded, but as a dispatch refusal of a request the framework pretends was well-formed), and the second and third end the run as stalls. After this piece, no defective call is silently dropped, upgraded into a request, or allowed to kill its iteration.

**N15 — Recorded before answered.** A refusal is recorded before any error result is composed or returned — the same durable-before-effects discipline as the evidence regime, applied to decisions: the record holds the refusal (class, the call's name and arguments as extracted, the catalogue hash it was resolved against, the iteration and both ordinals, the provider call ID where one stands) before the model is told anything. Under §4's preflight ordering (N20), *all* of a response's decisions stand recorded before *any* of its calls is dispatched. A refusal that cannot be recorded is not answered; the iteration's handling then follows the record-failure path the loop already takes when the record mechanism is unavailable (fail closed, claim nothing).

**N16 — The error result: narrow, factual, post-decision (Rev 2, OQ8 ruled).** The model receives, for each refused call, a structured error result carrying: the provider call ID it answers (or, where the ID itself was the defect, the call's provider ordinal); the refusal class in plain terms (`tool unavailable` / `call not accepted` / `arguments invalid` / `request refused`); for `invalid_arguments`, the failing constraint the validator named; and — for `unknown_tool` — the names of the tools this package's catalogue *does* offer, as permitted alternatives. It states what was decided and nothing else. It must not imply the action was attempted, dispatched, or executed; it must not carry record internals (grounds in the record's R-numbered form, grant contents, bounds arithmetic) beyond the class and the failing constraint; it must not apologise, speculate, or instruct. **Settled (OQ8, INDEX 355):** the wording is an examined part of this scope, not an implementation detail. Its required properties: it names the call it answers; it states the decision in plain terms; it states **explicitly whether anything was dispatched for that call** — for every §3 refusal, nothing was; it never suggests a refused call ran. Draft templates, for the examiner's markup:

- `unknown_tool`: "Tool unavailable: '<name>' is not one of the tools offered for this task. Nothing was dispatched for this call. The tools offered are: <offered names>."
- `malformed_call`: "Call not accepted: <the failing point — e.g. its arguments could not be read / its call ID was absent or duplicated>. Nothing was dispatched for this call."
- `invalid_arguments`: "Arguments invalid: <the failing constraint>. Nothing was dispatched for this call."
- `doorway_refused`: "Request refused: <the ground in plain terms>. Nothing was dispatched for this call."
- `call_cap_exceeded`: "Call not accepted: this response's call limit was already reached. Nothing was dispatched for this call."

The templates are drafts under examination, not settled text; the build implements the examined wording, never an improvisation of it.

**N17 — Where the error result travels.** Error results travel the same road as dispatch outcomes: they are presented to the model in the next package (N26), in the package's tool-results carriage, each under its provider call ID — because in this framework the next package *is* the tool-result channel (see §5). A refused call therefore costs the model exactly one iteration's delay and teaches it the boundary in its own terms — the in-loop self-correction the research recommends (design implication 5) — instead of ending the run, which teaches it nothing.

**N18 — Bounds accounting for refusals.** A refusal consumes **no dispatch and no grant bound**: nothing was dispatched, and the doorway's bound counts dispatches (R47). A refusal also consumes **no step beyond the iteration that carried the call**: the step ceiling counts iterations (one provider call each), as today — a response of five calls, three refused, is one step, exactly as a text response of five requests, three doorway-refused, is one step today. The activation deadline is untouched by refusals: it governs the whole activation as it does now, and time spent translating and recording is inside it, as all handling time already is. A run whose model proposes only refusals ends the way a run whose requests are all doorway-refused ends today — by the step ceiling or a yield/decline, recorded — never by a special refusal limit. The per-response call cap is a separate, settled matter (N22): overflow calls are refusals under `call_cap_exceeded` and consume no dispatch and no step beyond their iteration, exactly as the classes above.

**N19 — A refusal is not a stall, and not a failure of the run.** Refusals are ordinary adjudication outcomes, collected in the run's result beside dispatched outcomes (as `ctx["refused"]` already collects doorway refusals), presented in the delta (REJECTION events for the seat already enter the loop's relevant set), and examinable per call. The stall grounds are unchanged; none of the five classes is one.

## §4 Multi-call handling

A single native response may carry several calls. The probe's classification already preserved every call in a multi-call response; this piece decides what the loop *does* with them. Rev 1 proposed; the examiner has ruled where marked (INDEX 355).

**N20 — Preflight: classify everything, persist everything, then dispatch (Rev 2, examiner's correction).** Processing runs in three strictly ordered phases. **(i) Extraction and classification:** every individuable call in the response is extracted (N6) and carried through resolution (N7) and validation (N8) — or refused under its §3 class, or counted against the cap (N22) — in emitted order, each on its own merits: no call's verdict waits on, or is contaminated by, another's. **(ii) Persistence:** the complete set of translation and refusal decisions for the response is recorded as the translation record (N32) — durably, before any effect. **(iii) Dispatch:** only then are the converted requests presented, in emitted order, through the loop's ordinary adjudication (N9). A failure while recording the decisions therefore leaves **nothing executed with its decision unrecorded**: if the translation record cannot be persisted, no member of the response is dispatched, and the iteration follows the record-failure path (fail closed, N15's discipline). *Reason:* the ordering the examiner required — a later translation-record failure must never leave earlier calls executed while the response's full set of decisions remains unrecorded — with the loop's existing adjudication philosophy (per act and per request, a refusal discards nothing independent of it) preserved inside it.

**Two ordinals, both preserved.** Every call carries its **provider call ordinal** — its position in the response's `tool_calls`, fixed at extraction (N6). Every *presented* call additionally carries the **loop request ordinal** inside its loop-assigned request identity (R47/R48). The two are distinct concepts; the translation record (N32) records the mapping exactly. Filtering never renumbers: where calls 1 and 3 of a response are refused at translation and call 2 is presented, call 2's provider ordinal remains 2 in every record and every result, whatever its position among the presented requests. Results assemble in provider call order (N24).

**N21 — Partial success stands.** If three of five calls convert and dispatch and two are refused, the record shows three dispatches and two refusals, and the next package presents five results. A refusal does **not** poison its siblings. Under N20's ordering, partial success is a property of the *recorded decision set*: the conversions and the refusals stand recorded together, before any of the three dispatches occurs. *Reason:* the alternative — fail-whole — is today's behaviour and is precisely what made one defective call a run-ending event; the research's denial-as-tool-result pattern (implication 5) and the framework's own per-request adjudication both reject it. The one exception is N13's boundary: a response whose calls cannot be individuated has made no separable proposals, and there is nothing to partially succeed.

**N22 — The per-response call cap (Rev 2, OQ3 ruled).** A single response may present at most **CAP** individuable calls to classification and possible dispatch. The cap exists because iteration count and per-response work are **different resource dimensions**: the step ceiling bounds responses, not the processing, recording, dispatch and next-package carriage a single response can generate. **Settled (OQ3, INDEX 355):** an explicit cap is required before build. Its value is a **build-gate precondition, fixed by this derivation and no other**: before the build is examined, the build note must (i) measure the per-call processing and recording cost the implementation actually imposes (a translation-record entry per call; per presented call, its adjudication chain — TOOL_REQUESTED, dispatch, TOOL_OUTCOME or REJECTION); (ii) measure the next-package envelope the standing package construction actually affords one iteration's results carriage, alongside the record delta that same package must also carry; and (iii) set CAP as the largest count whose worst case fits both measurements with the margin the examiner accepts — recording the measurements and the arithmetic in the build note for her examination. A build presented without the cap fixed this way has not met this scope. **Overflow:** individuable calls beyond CAP, in emitted order, are refused under the fifth class, **`call_cap_exceeded`**. An overflow call is recorded with its provider call ID, its name as emitted, and its provider ordinal — enough of its identity and ordinal to correlate its refusal — and its **arguments are not processed as a request**: not parsed, not validated, not converted (the raw arguments stand in L3, as all raw material does; the translation record does not touch them). Overflow is never a silent truncation of the call list: every overflow call carries its recorded refusal and its N16 error result in the next package.

**N23 — Duplicates within one response (Rev 2, OQ4 ruled).** Two calls in one response with the same name and arguments are two proposals: each takes its own provider ordinal and its own loop request identity, and each is adjudicated on its own — the doorway's fingerprint/identity machinery (R47) governs replays *of the same presentation*, and two ordinals are not the same presentation. **Settled (OQ4, INDEX 355):** no deduplication. The framework does not silently collapse two requested acts into one effect or one result, because the model asked twice and the record should say what happened twice. The doorway's standing bounds and dispatch controls remain in force over both calls. (A duplicate provider call *ID* is a different defect, and is refused under N6.)

**N24 — Results assemble in call order.** The next package's tool-results carriage presents the iteration's outcomes — dispatches, uncertain outcomes, doorway refusals, translation refusals, cap refusals — assembled in the calls' **provider call order** (N20), each under its provider call ID and loop request_id where one stands. The model reads its own proposals answered in the order it made them.

## §5 Tool-result continuation

**N25 — The honest architectural fact.** This framework has no provider conversation. The adapter builds each call's messages fresh — a system message and one user message rendered from the iteration's package — and the provider retains nothing between calls. Results reach the model because the *loop* carries them: settled TOOL_OUTCOME events enter the next iteration's package in its `tool_results` carriage and its delta (with the retrieval regime's single-carriage rule where it governs). Any design for "returning the tool result" must be built on that fact, not on the provider's conversation shape, which this framework does not have.

**N26 — Option A (settled): continuation stays package-mediated; the call ID rides along.** The native piece changes the *entrance* (how proposals arrive) and the *binding* (N11), not the road results travel. Concretely: (i) TOOL_OUTCOME and REJECTION events stand as they do; (ii) the package's `tool_results` entries gain the **provider call ID** beside the loop's `request_id` and `dispatch_id`, for outcomes and refusals alike, so the model correlates each result with the exact call it made; (iii) translation refusals (§3) are presented in the same carriage, in provider call order (N24), in the N16 error form. The provider's `role: "tool"` message form is **not** used, because there is no conversation to append it to — claiming to "return the result in the provider's tool-result form" inside a freshly built prompt would be a costume, not a continuation. **Settled (OQ1, INDEX 355):** the call ID's presence in the carriage is a **correlation reference** beside the framework's own request identity — it is not a claim that a native tool-role response was sent to a continuing provider conversation. What the model actually needs — its call answered, under the ID it gave the call, with the outcome or the refusal — Option A supplies in the framework's real channel.

**N27 — Option B (named; outside this scope).** The adapter could hold a conversation open within one iteration: on tool calls, the loop dispatches, the adapter appends the assistant message and `role: "tool"` results under the call IDs, and calls the provider again — the model's next proposal arriving in the same iteration. This is the provider's native loop shape, and it is the shape the words "return the result under the call ID" most literally describe. This scope does **not** adopt it, for three stated reasons: (1) it builds a **second control loop** inside the adapter — iterations within iterations — whose steps the step ceiling does not count and whose calls each owe their own CALL_ENTERED and disposition under the evidence regime (a sub-sequence the Rev 8 contract does not contemplate and the checker cannot currently reconstruct); (2) it moves adjudication timing — the loop would dispatch *during* a provider conversation rather than between recorded iterations, weakening the package-freeze/cursor discipline every iteration currently stands on; (3) it is unnecessary for the capability Q2 asks about: Option A already gives the model its results and its refusals, one iteration later, inside the bounds that exist. **Settled (OQ1, INDEX 355):** Option B stays outside this scope. If the literal tool-result form is ever judged load-bearing for a model's behaviour, it returns as its own scope, with its own evidence and bounds design — and its own acceptance probe (N39). It is not smuggled into this piece.

**N28 — Mode is sealed, per assembly, as today (Rev 2, OQ7 ruled).** Native mode is not a runtime toggle. The adapter's mode for a run is read from the sealed packed package (the ASSEMBLY_PACKED act's `adapter_mode`, judged at assembly — the probe piece's §6 mechanism, unchanged), passed by the loop only for governed assemblies. This piece is **native-first for the pinned model**: a future assembly of the first-worker kind, on this model and route, is expected to be judged native. It is **not a deletion of the text path**: the text contract, its rendering, and its whole validation stand byte-identical for assemblies judged text, and a native-judged assembly's no-tool-call responses are still read on the text path (N12). **Settled (OQ7, INDEX 355):** a native judgement is **fresh and assembly-specific** — the existing probe → judgement → receipt discipline carries over, bound to the assembly's model, route, catalogue and request construction, with evidence appropriate to the actual worker request. A previous native-offer result is **not a permanent mode grant**, and first-response success does not prove a complete worker run. Any live run needs its own release regardless (§9).

**N29 — Accounting under continuation.** Under Option A the accounting is *unchanged*, and the paper claims this as a virtue to be witnessed, not assumed: one iteration = one provider call = one step against the ceiling; dispatches and refusals within an iteration add no steps; the activation deadline (the doorway's absolute deadline, INDEX 222) governs every call and all handling; a model that spends its steps proposing refused calls spends its steps, exactly as on the text path. No new clock, counter, or budget is introduced. (The per-response call cap, N22, bounds work *within* an iteration; it is not a step counter and changes none of this accounting.)

**N30 — What the model is told about the arrangement (Rev 2, OQ8 ruled).** The contract text **does** name the native arrangement, and the wording is examined scope content — taken explicitly here, not slipped in by the build. Its required properties: it states plainly that native calls are **proposals**, not actions; that a call takes effect only if the framework accepts it and performs it; and that each call's outcome or refusal **arrives in the next package**, under the call's own ID. Draft wording, for the examiner's markup: *"You are offered the tools in this package as native tool calls. A tool call is a proposal, not an action: it happens only if the framework accepts it and performs it. The outcome of every call — its result, or a refusal stating that nothing was dispatched — will be presented in your next package, under the call's own ID."* The build implements the examined wording; it does not improvise model-facing language while implementing. The refusal wording itself is settled the same way, at N16.

## §6 The evidence regime

**N31 — The Rev 8 discipline carries over unchanged.** Every native-mode call is a call: CALL_ENTERED before it, the seam's capture persisted and read-back-verified, the disposition committed before any effect of the answer — translation included. A native response that cannot be evidenced cannot be translated; `evidence_capture_failure` ends the run exactly as it does today. No disposition class, failure class, ceiling, or store rule changes.

**N32 — The translation record: a distinct record event, bound to the evidence (Rev 2, OQ6 corrected).** The artifact's L3 already retains the full message, `tool_calls` included — the raw material of translation is therefore already durable before interpretation, by construction. What is missing today, and this piece adds, is the **translation record**: a **distinct, durable record event** of the iteration, committed **after** the response-evidence disposition (N31) and **before the first dispatch** of the iteration (N20's persistence phase), and **bound to the exact response-evidence artifact hash** the disposition committed. It carries, per call: provider call ID, **provider call ordinal**, extracted name, arguments hash (over the parsed arguments' canonical form — an overflow call under N22 carries no arguments hash, because its arguments are not parsed), resolution outcome, validation outcome (with the failing constraint where invalid), refusal class where refused, and the **loop request_id** where presented — the exact provider-ordinal ↔ loop-identity mapping of N20. The record is total: one entry per individuable call, `not_reached` with its reason where translation never ran for an entry. **What it is not:** it is not a layer of the response-evidence artifact, and it is not written into one. The artifact is persisted, verified and committed before translation (N31) and is **never mutated afterwards**; **L5 is never retroactively altered** to carry a later interpretation — the Rev 1 draft's proposal to summarise translation in L5 is **withdrawn**: a committed artifact cannot grow a verdict. If a human-readable translation supplement is wanted, it is a **new artifact with its own hash**, explicitly bound to the response-evidence artifact hash and to the translation record event — never a rewrite of either.

**N33 — What the checker must be able to reconstruct (Rev 2).** From the record and the artifacts alone, in its own copies as established: (i) the catalogue the iteration presented (already reconstructed from the sealed grants, checker.py's own `_derive_catalogue`); (ii) the calls the response made (from L3 of the bound artifact); (iii) the translation of each call — re-running resolution and the pure schema validation (N8, the checker's own independent implementation) deterministically over (ii) against (i) — agreeing with the recorded **translation record event**, per call; (iv) the binding from each presented call to its TOOL_REQUESTED / dispatch / TOOL_OUTCOME or REJECTION chain — provider ordinal, loop request_id and provider call ID in exact correspondence — and from each refused call to its recorded refusal and its presentation in the following package; (v) doorway invariance at the record level: every dispatch in a native-mode run traces to a `request_tool` presentation whose contents equal the translated call's, with no dispatch lacking a translation record and no translation record silently lacking its adjudication. A native-mode history the checker cannot reconstruct this way is a failed history, however clean the run felt.

**N34 — The probe's evidence is not the worker's evidence.** The native-offer probe's artifacts (per-call classifications over raw captures) stand as probe evidence and are not re-used as worker-run evidence, nor does this piece change the probe. The classifications' *vocabulary* (offered / unoffered / malformed) is deliberately consonant with §3's classes, but the worker piece's records are the record's own events, under the Rev 8 regime.

**N35 — Uncertain outcomes stay uncertain.** A dispatch whose outcome stands uncertain is presented as uncertain under its call ID (the loop's standing rule — never upgraded), and a reconciled outcome is presented as reconciled, in the package where the cursor gives it. Native mode inherits the whole standing discipline of outcomes, including the stall-time accounting closure (R50).

## §7 Empirical unknowns — probed, not assumed

Each unknown names its probe shape and its reading, stated in advance. Probes are observation-only single-generation captures on the probe piece's settled pattern (the raw seam — `probe_raw_call` / the connector raw call — with responses captured whole under the evidence discipline), run only under their own release. No probe dispatches, executes, or answers a call. In Rev 2, P1 and P2 stand as formal proposals accompanying this scope, and **the detailed scope does not close until their results are examined**; P3 is settled; P4 is closed.

**N36 — P1: an unoffered name, with tools offered — EMPIRICAL GATE.** *Unknown:* when native tools **are** offered and the model emits a call to a name **not** among them, what does this provider, on this route, actually do — return the call in the message's `tool_calls` (our resolver then refuses it, §3), refuse the whole response with a `tool_use_failed` 400 whose `failed_generation` carries the attempt, or silently drop the call? *Probe:* `NATIVE-ADAPTER-P1-PROBE-PROPOSAL-2026-11-24.md` — the standing assignment context with a deliberately narrowed offered set (`sandbox.list` and `sandbox.search` offered; `sandbox.read_range` withheld) and the source listing pre-presented, so the natural next step is the withheld read; run under two conditions differing only in Groq's `disable_tool_validation` (off / on), five trials each, first response only, complete raw capture including HTTP errors and `failed_generation`, pacing against the measured token budget designed in. *What each outcome settles in this design:* (a) **the call arrives in `tool_calls`** → the §3 resolver design stands as written, and the resolver's unoffered-call handling is live-shaped, not hypothetical; (b) **a 400 with the attempt in `failed_generation`** → the examiner rules whether a provider refusal may serve as refusal evidence via a translation-input seam: the attempt extracted **from the error body as evidence**, classified and recorded as a refusal on the strength of that provider evidence — which remains provider evidence and is never promoted into a delivered call — salvage used as a *translation input*, never as an execution route (INDEX 345 §4's condition) — with the model-facing error result still travelling in the next package, since no turn exists to preserve; (c) **a refusal without the attempt visible** (a provider refusal whose error body carries no identifiable attempt) → an unoffered attempt may have occurred, but its content is not observable at this seam; the design records exactly that, and infers nothing more about the attempt; (d) **accepted responses carrying no unoffered trace** → the safe conclusion, and the only one: **no unoffered attempt was observed under that construction and condition.** The model may simply have chosen an offered action; nothing follows about what the provider would have done with an attempt. The probe therefore does not establish the provider's handling of an unoffered attempt; the resolver can refuse only calls it receives; provider handling of an unoffered attempt remains uncharacterised, and this scope's closure and the build's account record it in those terms — the closed world still guarantees nothing unoffered was executed. The two-condition comparison answers the `disable_tool_validation` question **only where an unoffered attempt actually occurred**: if neither condition produces one, the variable has not been tested against an actual attempt and the comparison is recorded as **inconclusive for the flag's effect** (the research documents that the flag does not lift `tool_choice` none/required enforcement; this design sends no `tool_choice`, so its effect on unoffered names under the natural setting remains unknown wherever no attempt occurred).

**N37 — P2: multi-call response shape — EMPIRICAL GATE.** *Unknown:* does the pinned model on this route emit parallel calls in one message under a task construction whose natural opening is two independent calls, and in what envelope — multiple `tool_calls` entries, each with its own `id`, in emitted order? *Probe:* `NATIVE-ADAPTER-P2-PROBE-PROPOSAL-2026-11-24.md` — a disclosed variant of the standing first-worker material requiring two sources, both needed in full and neither's inspection dependent on the other's result, the full granted catalogue offered natively, five trials, first response only, every call's ID, name, arguments and emitted order captured. *What each outcome settles:* **two-or-more calls observed** → §4's semantics are exercised by reality, and the build's multi-call witnesses use the observed envelope; **exactly one call in every settled trial** → the evidence establishes only that **the first response contained one call in each of those trials**: the probe ends before any result is returned, so it cannot observe what the model would propose in a subsequent response, and no claim follows that the model generally works one call at a time. §4 stands as designed defensively, the build's witnesses use stub envelopes shaped like the observed single-call one, and **this scope's closure and the build's account must say plainly that multi-call handling rests on defensive witnesses rather than live multi-call evidence, and that no live multi-call response was observed** — the language obligation the examiner set, which this paper accepts in advance. Either way the design does not change; what changes is what the build may claim.

**N38 — P3: call-ID presence — SETTLED by existing evidence (INDEX 355).** The examiner checked the raw provider bodies in both native-offer runs herself: **all six delivered calls carry non-empty provider call IDs, and all six IDs are distinct**; the four HTTP 429 failures produced no calls and are correctly excluded. No live probe — and no further desk check — is spent on P3. N6 and N11 therefore stand: provider call IDs are the normal correlation mechanism, with the explicit refusal rule for a missing or duplicate ID added at N6 (Rev 1's contemplated ordinal fallback is not adopted: a call whose own reference is broken is refused, not silently re-keyed). If a future model or route change re-opens the question, it re-opens as a fresh desk check on that line's retained artifacts first.

**N39 — P4: tool-result message acceptance — CLOSED by the OQ1 ruling.** Under Option A the design never sends a tool-result message into a continuing provider conversation, because there is none (N25). With Option B ruled outside this scope (N27), no P4 probe is proposed: probing an unused behaviour would spend provider requests on architecture this piece does not build — empirical-before-architectural cuts both ways. If Option B ever returns as its own scope, its acceptance probe is designed there (single conversation, one offered call, one stub result returned in the provider's form, the continuation captured whole).

**N40 — P5: arguments encoding.** *Observed, not unknown:* every delivered call to date carried arguments as a JSON string; the existing translator also accepts an object form. The build must accept both and refuse a third shape as `malformed_call` — no probe needed; the witnesses cover both encodings from stubs shaped on the observed bodies.

## §8 Non-goals, explicit

**N41 — No direct environment execution.** Nothing in this piece executes a provider call, a translated request, or an error body's contents except through `Doorway.request_tool` → recorded dispatch → the executor. `container.exec` is a refusal class, never a route.

**N42 — No salvage as foundation.** `failed_generation` recovery is not the worker loop's mechanism. Its only contemplated use is the one N36's reading (b) puts to the examiner: as *evidence and translation input* for a refusal, under the same recording discipline — never as a dispatch source, never executed from the error body (INDEX 345 §4).

**N43 — No second authority path.** No new grant source, no adapter-side permission cache, no doorway bypass for "obviously fine" calls, no policy decision taken anywhere but the doorway. The adapter's resolution and validation classify; they never permit.

**N44 — No change to grants, bounds, assignment, or record semantics.** The sealed grants, the step ceiling, the activation deadline, the first-worker assignment, the event types' meanings, and the stall grounds are all exactly as they stand. This piece adds: per-call translation, per-call refusal records, a pure schema validator, call-ID carriage, the translation record event, and the per-response call cap. It amends no existing contract's meaning; where an existing behaviour changes (fail-whole translation, N13), the change is named in this scope and witnessed in the build.

**N45 — No generality claim.** This piece is for the pinned model (`openai/gpt-oss-120b`) on the Groq route, under the task shapes the framework actually runs. It does not claim native-first is right for other models (the research's own counter-evidence stands: on parameter-free selection, text beat native on average across models — just not for this one), and a future model or route change re-opens the mode question under N28's judgement discipline, with its own probe evidence.

## §9 Acceptance shape for the eventual build

The build, when Ben authorises it, passes examination on witnesses of these shapes (stub-provider witnesses in the suites' established pattern, plus the checker over the produced records):

**N46 — W-a, translation fidelity.** A stub native response carrying a well-formed offered call produces exactly the typed request its text-form twin produces — same tool, same parameters, byte-equal after canonicalisation — and the iteration's record from adjudication onward is identical in shape to the text-mode record of the same request.

**N47 — W-b, doorway invariance.** Across a matrix of stub responses (offered, unoffered, malformed, schema-invalid, doorway-refusable, mixed), every dispatch that occurs traces to a `request_tool` presentation, every refusal is recorded under its §3 class before any package presents it, and zero dispatches occur for refused calls. The witness fails if any call reaches the executor by any other route.

**N48 — W-c, closed-world refusals.** A stub response calling `container.exec` (and, separately, a built-in-shaped name and a near-miss of a granted name) yields: a recorded `unknown_tool` refusal, zero TOOL_REQUESTED events for it, zero dispatches, and an N16 error result in the next package naming the offered alternatives — while a sibling offered call in the same response dispatches normally (N21).

**N49 — W-d, per-call granularity, preflight, and the cap (Rev 2).** A multi-call stub response with one unparseable-arguments call, one schema-invalid call, and two valid calls: two dispatches, two recorded refusals of the right classes, results assembled in provider call order under their call IDs (N24), the iteration completing without a stall — and the complete translation record standing persisted **before** the first of the two dispatches (N20), verifiable from the record's ordering. A stub response exceeding the cap: the overflow calls refused `call_cap_exceeded`, each with provider call ID, name and provider ordinal recorded, arguments unprocessed, no silent truncation (N22). A stub response with a missing and a duplicated provider call ID: those calls refused under N6's rule, their siblings unaffected.

**N50 — W-e, evidence and checker reconstruction.** A governed native-mode run over stubs: every iteration's artifact binds, L3 retains the calls, the translation record event stands total per call and bound to its iteration's artifact hash, and the independent checker reconstructs §6's (i)–(v) and reports all-ok. The text-mode suites and the evidence suites pass at their standing counts, unweakened; a text-judged assembly's packages and requests are byte-identical to before the build (the text path's regression witness).

**N51 — The first live demonstration.** The natural candidate is the standing first-worker assignment — the three sealed sources read, the plain-words brief written — under a **fresh assembly judged native** (the fresh, assembly-specific judgement of N28), on the pinned model and route, with the evidence regime live. It is *not* part of the build's acceptance: it requires its own release examination (the mode judgement, the run's bounds, and — learned from INDEX 339/352 — a **pacing plan against the provider's measured token budget**, since a multi-step run makes several large calls in a minute's span and the release must plan for that rather than discover it). The build's passage establishes that the adapter *can* translate under examination; the demonstration establishes that a worker *did* work. The two claims are never merged.
