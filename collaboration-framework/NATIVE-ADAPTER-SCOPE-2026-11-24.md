# SCOPE — THE DOORWAY-PRESERVING NATIVE ADAPTER (2026-11-24, Rev 1)

Drafted at Ben's tap (2026-11-24 04:06 MST, scope ledger): **the paper only**. This scope authorises nothing — no build, no provider request, no run. The build waits on the examiner's scope pass and Ben's separate build decision, as every piece in this programme has.

The piece answers the second of the two questions the research response separated (INDEX 345 §5): **Q1 (empirical)** — can the provider reliably return native calls for the granted tools under the exact request configuration? — is **supported** (INDEX 353: six of six delivered native-offer observations produced well-formed offered calls; the four HTTP 429s are not model observations and stand outside the denominator). **Q2 (architecture)** — can the adapter translate every returned call into the existing framework request contract **without creating a second authority path**? — is this paper's question.

Settled ground this paper does not reopen:

- The seam (INDEX 345 §2): native tool expression is the model's normal request language; the framework retains complete authority over what happens next. The provider's tool schema is an interface description, not an authority document; the sealed briefcase and the doorway remain the authority chain.
- The qualifications INDEX 353 kept explicit: the paced observations are one repeated first action under one request construction — repeatability, not multi-step competence; and because the shell was never offered, the trials do not establish that the model would never propose an unoffered tool in another context.
- The evidence discipline (WORKER-RESPONSE-EVIDENCE-SCOPE Rev 8, PASSED at INDEX 312) is standing law for any call the loop makes; this piece sits inside it, not beside it.
- Empirical before architectural (Ben's standing order, INDEX 274): no part of this design may rest on an unprobed provider behaviour. §7 names the unknowns and their probes; the build does not begin until the probes the examiner requires have reported.

## §1 The seam, stated plainly

**N1 — Three verbs, three owners.** The model *proposes*: a native tool call is a structured request in the model's native request language, nothing more. The adapter *translates*: it converts a provider-shaped call into the framework's existing typed request, or records why it cannot. The doorway *decides*: grant, bounds, policy, dispatch and recording remain exactly where they have always been. No verb migrates. In particular, translation is a **classification** act (is this call presentable, and as what?) and never a **permission** act — a translated request faces `Doorway.request_tool` exactly as its text-form twin does, and the doorway re-checks it whole (see N9).

**N2 — The offered definitions are derived, never authored.** The native definitions offered to the provider are derived from the package's own tool catalogue by the existing derivation — `OpenAICompatibleAdapter._native_tool_definitions` (adapter.py), the same per-grant derivation the native-offer probe used through `native_probe.derive_offered_definitions` — over the catalogue the loop derives from the sealed ASSEMBLY_GENERATED grants (`Loop._derive_catalogue`, loop.py). The catalogue describes authority; it creates none (A3-CAT's standing rule). The adapter invents, renames and supplements nothing; a tool with no sealed grant has no definition, and a definition's presence in a request is not evidence of a grant.

**N3 — The closed world.** The resolver's world is the sealed catalogue of *this* package: the exact names the derivation offered, under the registry version the iteration records. A name outside that set — `container.exec`, a built-in-shaped name (`browser`, `python`), a plausible near-miss of a granted name — is not a request and can never become one. It is a refusal (§3). There is no fallback that maps an unoffered name onto a granted one, no fuzzy matching, no shell.

**N4 — One authority path, auditable.** After this piece, a native call can reach execution by exactly one route: translation → the loop's adjudication → `Doorway.request_tool` → the doorway's recorded dispatch → the executor. Any code path by which a provider call could reach the executor, the record, or a tool result without passing `request_tool` is a defect in the build, not a feature of it. The build's witnesses (§9) include a doorway-invariance witness whose whole job is this claim.

## §2 The translation contract, step by step

For one iteration whose sealed mode is native (on mode, see N28), the response's handling is:

**N5 — Capture first, interpretation second.** The provider call runs under the standing evidence sequence unchanged: LOOP_ITERATION → CALL_ENTERED → the call → the seam's evidence persisted → the RESPONSE_EVIDENCE disposition committed → only then any effect (Rev 8 §R2-3 ordering). Native mode changes nothing before this point and nothing about it. The full assistant message — `tool_calls` included — already stands in L3 of the evidence artifact (`evidence.derive_layers` derives L3 as the complete message object); translation works from that message and invents nothing the capture does not contain.

**N6 — Per-call extraction.** From the captured message's `tool_calls` list, in emitted order, one extraction record per call: the **provider call ID** (`call.id`, exactly as emitted), the **name** (`call.function.name`), the **arguments** (parsed from `call.function.arguments` — the JSON string form the route has emitted in every observation to date; an already-object form is accepted, as the existing translator accepts both), and the call's **ordinal** in the response. *Gap, named:* neither existing native seam preserves the provider call ID — the adapter's `_translate_tool_calls` returns `{tool, parameters}` only, and the probe's `_call_record` likewise records no `id`. Carrying the ID end to end is new, bounded work in the adapter's translation and in the record's request binding (N11), and §9 witnesses it.

**N7 — Closed-world resolution.** Each extracted name is resolved against the sealed catalogue **of the package this iteration presented** (the same catalogue object whose hash LOOP_ITERATION recorded — not a re-derivation, not the registry at large). Resolution has exactly two outcomes: *resolved* (the name is a catalogue entry of this package) or *unknown* (§3 refusal, class `unknown_tool`). Resolution confers nothing: it classifies the call as presentable. The doorway's own grant check (`Doorway._dispatch_check`, against the sealed generated record) runs afterwards on every presented request, unchanged — so a resolution error in the adapter cannot manufacture a dispatch: worst case it presents a request the doorway refuses on its grant ground, recorded as today.

**N8 — Schema validation.** A resolved call's arguments are validated against **its catalogue entry's parameter schema** — the registry's worker-facing schema the catalogue carries (`tool_policy.worker_facing`, joined into the entry by `_derive_catalogue`). *Gap, named:* no such conformance validation exists today. The doorway checks the grant's *scope ceiling* (`tool_policy.check_ceiling` — paths, ranges, bounds) at dispatch; nothing anywhere checks that arguments conform to the advertised schema (required fields present, types as declared, no undeclared fields). This piece adds exactly one new component: a **pure argument validator** over the catalogue entry's schema — no I/O, no record access, deterministic in (schema, arguments) — whose verdict is `valid` or `invalid` with the first failing constraint named. Where it lives (adapter, loop, or a shared module the doorway and checker mirror, per the programme's own-copies pattern) is the examiner's to rule (OQ5); that it is pure and shared-in-contract is not optional, because the checker must recompute it (§6). A schema-invalid call is a §3 refusal, class `invalid_arguments`. The doorway's ceiling check is **not** replaced by this validation: schema conformance and grant scope are different questions, and both are asked, in that order.

**N9 — Conversion to the existing typed request.** A resolved, schema-valid call converts to the framework's existing request shape — `{"tool": <name>, "parameters": <arguments>}` — the exact shape `Loop._validate_requests` admits and `_translate_tool_calls` already produces. No new request type is introduced. The converted requests join the iteration's outcome as its `tool_requests`, in emitted order, and from this point the iteration is **indistinguishable from a text-mode iteration that carried the same requests**: the loop's whole-response validation, per-request adjudication (`Loop._adjudicate`), loop-assigned request identity (`loop-<instance>-<iteration>-<ordinal>`, R47/R48), `Doorway.request_tool`, dispatch, executor performance and TOOL_OUTCOME recording all run exactly as they run today. This is the doorway-invariance claim, and it is the piece's centre: **native mode is a second *entrance* to one corridor, not a second corridor.**

**N10 — What conversion must not do.** Conversion never repairs: it does not coerce argument types, fill defaults the schema declares but the call omitted (a missing required argument is `invalid_arguments`, not an invitation), trim undeclared fields into acceptability, or split one call into several requests or merge several into one. One provider call converts to at most one framework request, under its own ordinal.

**N11 — The result returns under the original provider call ID.** The recorded outcome of a presented request — dispatch result, uncertain outcome, or doorway refusal — is bound to the provider call ID that proposed it: the binding (provider call ID ↔ loop request_id ↔ dispatch_id) is recorded with the iteration's adjudication (§6 states the evidence form), and the package that presents the outcome to the model (N26) carries the provider call ID beside the loop's request_id, so the model's own reference for its call is the reference its result answers. The provider call ID is a *correlation* identifier only: identity for replay and adjudication remains the loop's (R47/R48 unchanged — a re-emitted call in a later iteration is a new presentation with a new loop identity, exactly as a re-typed text request is).

**N12 — The text channel in a native response.** Today's probe-piece rule stands as this paper's proposal: a native response carrying both non-empty content and tool calls is malformed whole (adapter.py, `_call_typed` native branch) — the channels are not mixed. A native response with no tool calls is read on the text path exactly as a text-mode response is (the contract remains in the prompt; the outcome set is unchanged). Whether the mixed rule should relax — content admitted as a contribution beside calls — is an examiner ruling (OQ2), not a default this paper takes.

**N13 — Fail-whole is replaced by per-call granularity — at translation only.** Today `_translate_tool_calls` fails the whole response on any defective call (unparseable arguments, unreadable name), and the loop's answer is a stall. Under this piece, a defect *inside one call* refuses that call (§3) and does not touch its siblings (§4). Defects *of the response as a whole* — no readable message, an unreadable `tool_calls` structure (not a list, entries not objects in a way that prevents per-call extraction at all) — remain whole-response failures under the existing failure kinds, evidenced as today. The boundary is: where a single call can be individuated, it is individuated; where it cannot, the response has not made separable proposals and there is nothing per-call to refuse.

## §3 Refusals as doorway decisions

**N14 — Four refusal classes, one shape.** A call that does not reach dispatch is refused under exactly one class, recorded with the call's extraction record (N6):

- `unknown_tool` — the name does not resolve against this package's sealed catalogue (N7). `container.exec` lives here, permanently.
- `malformed_call` — the call cannot be individuated or its arguments cannot be parsed into an object (unreadable name, unparseable arguments string, non-object arguments).
- `invalid_arguments` — the call resolves, but its arguments fail the catalogue schema (N8).
- `doorway_refused` — the call was presented as a typed request and the doorway refused it (no grant, ceiling, bound, temporal or aggregate ground). This class already exists in substance: `request_tool` records TOOL_REQUESTED, then a REJECTION naming the ground (R55), and the loop collects the refusal without discarding anything independent of it. Native mode inherits it unchanged.

The first three classes are new *as recorded per-call decisions*; today the first is indistinguishable from a grant refusal (it reaches `request_tool` and is refused there — recorded, but as a dispatch refusal of a request the framework pretends was well-formed), and the second and third end the run as stalls. After this piece, no defective call is silently dropped, upgraded into a request, or allowed to kill its iteration.

**N15 — Recorded before answered.** A refusal is recorded before any error result is composed or returned — the same durable-before-effects discipline as the evidence regime, applied to decisions: the record holds the refusal (class, the call's name and arguments as extracted, the catalogue hash it was resolved against, the iteration and ordinal, the provider call ID) before the model is told anything. A refusal that cannot be recorded is not answered; the iteration's handling then follows the record-failure path the loop already takes when the record mechanism is unavailable (fail closed, claim nothing).

**N16 — The error result: narrow, factual, post-decision.** The model receives, for each refused call, a structured error result carrying: the provider call ID it answers; the refusal class in plain terms (`tool unavailable` / `arguments invalid` / `request refused`); for `invalid_arguments`, the failing constraint the validator named; and — for `unknown_tool` — the names of the tools this package's catalogue *does* offer, as permitted alternatives. It states what was decided and nothing else. It must not imply the action was attempted, dispatched, or executed; it must not carry record internals (grounds in the record's R-numbered form, grant contents, bounds arithmetic) beyond the class and the failing constraint; it must not apologise, speculate, or instruct. The wording template is part of the build's examined surface (OQ8), not an implementation detail.

**N17 — Where the error result travels.** Error results travel the same road as dispatch outcomes: they are presented to the model in the next package (N26), in the package's tool-results carriage, each under its provider call ID — because in this framework the next package *is* the tool-result channel (see §5). A refused call therefore costs the model exactly one iteration's delay and teaches it the boundary in its own terms — the in-loop self-correction the research recommends (design implication 5) — instead of ending the run, which teaches it nothing.

**N18 — Bounds accounting for refusals.** A refusal consumes **no dispatch and no grant bound**: nothing was dispatched, and the doorway's bound counts dispatches (R47). A refusal also consumes **no step beyond the iteration that carried the call**: the step ceiling counts iterations (one provider call each), as today — a response of five calls, three refused, is one step, exactly as a text response of five requests, three doorway-refused, is one step today. The activation deadline is untouched by refusals: it governs the whole activation as it does now, and time spent translating and recording is inside it, as all handling time already is. A run whose model proposes only refusals ends the way a run whose requests are all doorway-refused ends today — by the step ceiling or a yield/decline, recorded — never by a special refusal limit. Whether a per-iteration *call* cap should exist at all is separate (N22, OQ3).

**N19 — A refusal is not a stall, and not a failure of the run.** Refusals are ordinary adjudication outcomes, collected in the run's result beside dispatched outcomes (as `ctx["refused"]` already collects doorway refusals), presented in the delta (REJECTION events for the seat already enter the loop's relevant set), and examinable per call. The stall grounds are unchanged; none of the four classes is one.

## §4 Multi-call handling

A single native response may carry several calls. The probe's classification already preserved every call in a multi-call response; this piece must decide what the loop *does* with them. Proposal, with reasons — the examiner rules where marked.

**N20 — Independence, in emitted order.** Calls are processed in emitted order, each through N6–N9 on its own merits: extraction, resolution, validation, conversion. No call's verdict waits on, or is contaminated by, another's. *Reason:* this is the loop's existing adjudication philosophy — per act and per request, a refusal discards nothing independent of it — extended from the text path, where it is already the settled rule, to the translation stage in front of it.

**N21 — Partial success stands.** If three of five calls convert and dispatch and two are refused, the record shows three dispatches and two refusals, and the next package presents five results. A refusal does **not** poison its siblings. *Reason:* the alternative — fail-whole — is today's behaviour and is precisely what made one defective call a run-ending event; the research's denial-as-tool-result pattern (implication 5) and the framework's own per-request adjudication both reject it. The one exception is N13's boundary: a response whose calls cannot be individuated has made no separable proposals, and there is nothing to partially succeed.

**N22 — A cap, proposed for ruling.** The number of calls one response may present is capped. This paper proposes the cap be the **step ceiling's own arithmetic made local**: no number is proposed here, because the honest options are (a) no cap beyond the iteration's own bounds — dispatch bounds and the deadline already limit effects, and each presented request is individually doorway-checked; or (b) a named per-response cap, overflow calls refused under a fifth class (`call_cap_exceeded`) without examination of their contents. *For the examiner to rule (OQ3).* What is not optional: whatever the ruling, overflow behaviour is defined in advance and recorded per call — never a silent truncation of the call list.

**N23 — Duplicates within one response.** Two calls in one response with the same name and arguments are two proposals: each takes its own ordinal and its own loop request identity, and each is adjudicated on its own — the doorway's fingerprint/identity machinery (R47) governs replays *of the same presentation*, and two ordinals are not the same presentation. Whether the second identical call should instead be answered with the first's outcome (deduplication as a courtesy) is *for the examiner to rule (OQ4)*; this paper's default is no deduplication — the framework does not silently collapse two proposals into one effect or one result, because the model asked twice and the record should say what happened twice.

**N24 — Results assemble in call order.** The next package's tool-results carriage presents the iteration's outcomes — dispatches, uncertain outcomes, doorway refusals, translation refusals — assembled in the calls' emitted order, each under its provider call ID and loop request_id. The model reads its own proposals answered in the order it made them.

## §5 Tool-result continuation

**N25 — The honest architectural fact.** This framework has no provider conversation. The adapter builds each call's messages fresh — a system message and one user message rendered from the iteration's package — and the provider retains nothing between calls. Results reach the model because the *loop* carries them: settled TOOL_OUTCOME events enter the next iteration's package in its `tool_results` carriage and its delta (with the retrieval regime's single-carriage rule where it governs). Any design for "returning the tool result" must be built on that fact, not on the provider's conversation shape, which this framework does not have.

**N26 — Option A (proposed): continuation stays package-mediated; the call ID rides along.** The native piece changes the *entrance* (how proposals arrive) and the *binding* (N11), not the road results travel. Concretely: (i) TOOL_OUTCOME and REJECTION events stand as they do; (ii) the package's `tool_results` entries gain the **provider call ID** beside the loop's `request_id` and `dispatch_id`, for outcomes and refusals alike, so the model correlates each result with the exact call it made; (iii) translation refusals (§3) are presented in the same carriage, in call order (N24), in the N16 error form. The provider's `role: "tool"` message form is **not** used, because there is no conversation to append it to — claiming to "return the result in the provider's tool-result form" inside a freshly built prompt would be a costume, not a continuation. What the model actually needs — its call answered, under the ID it gave the call, with the outcome or the refusal — Option A supplies in the framework's real channel.

**N27 — Option B (named, not proposed): intra-iteration continuation.** The adapter could hold a conversation open within one iteration: on tool calls, the loop dispatches, the adapter appends the assistant message and `role: "tool"` results under the call IDs, and calls the provider again — the model's next proposal arriving in the same iteration. This is the provider's native loop shape, and it is the shape the words "return the result under the call ID" most literally describe. This paper does **not** propose it, for three stated reasons: (1) it builds a **second control loop** inside the adapter — iterations within iterations — whose steps the step ceiling does not count and whose calls each owe their own CALL_ENTERED and disposition under the evidence regime (a sub-sequence the Rev 8 contract does not contemplate and the checker cannot currently reconstruct); (2) it moves adjudication timing — the loop would dispatch *during* a provider conversation rather than between recorded iterations, weakening the package-freeze/cursor discipline every iteration currently stands on; (3) it is unnecessary for the capability Q2 asks about: Option A already gives the model its results and its refusals, one iteration later, inside the bounds that exist. *For the examiner to rule (OQ1):* if she judges the literal tool-result form load-bearing for this model's behaviour (an empirical claim — see P4), Option B returns as its own scope, with its own evidence and bounds design. It is not smuggled into this piece.

**N28 — Mode is sealed, per assembly, as today.** Native mode is not a runtime toggle. The adapter's mode for a run is read from the sealed packed package (the ASSEMBLY_PACKED act's `adapter_mode`, judged at assembly — the probe piece's §6 mechanism, unchanged), passed by the loop only for governed assemblies. This piece is **native-first for the pinned model**: a future assembly of the first-worker kind, on this model and route, is expected to be judged native. It is **not a deletion of the text path**: the text contract, its rendering, and its whole validation stand byte-identical for assemblies judged text, and a native-judged assembly's no-tool-call responses are still read on the text path (N12). What evidence a *native* judgement for a real run requires — the native-offer results are first-response evidence; a run judgement is a stronger act — is the examiner's to state (OQ7), and any such run needs its own release regardless (§9).

**N29 — Accounting under continuation.** Under Option A the accounting is *unchanged*, and the paper claims this as a virtue to be witnessed, not assumed: one iteration = one provider call = one step against the ceiling; dispatches and refusals within an iteration add no steps; the activation deadline (the doorway's absolute deadline, INDEX 222) governs every call and all handling; a model that spends its steps proposing refused calls spends its steps, exactly as on the text path. No new clock, counter, or budget is introduced.

**N30 — What the model is told about the arrangement.** The prompt's contract text and catalogue section are unchanged in this piece. The model is not told its results will arrive in a later package — on the text path it was never told either; the package *is* its world each iteration, and its `tool_results` carriage is self-describing. If the examiner judges the contract text should name the native arrangement (you are offered these tools natively; call them; results and refusals return in your next package), that wording is an examined change to the contract, taken explicitly — not slipped in by the build (OQ8).

## §6 The evidence regime

**N31 — The Rev 8 discipline carries over unchanged.** Every native-mode call is a call: CALL_ENTERED before it, the seam's capture persisted and read-back-verified, the disposition committed before any effect of the answer — translation included. A native response that cannot be evidenced cannot be translated; `evidence_capture_failure` ends the run exactly as it does today. No disposition class, failure class, ceiling, or store rule changes.

**N32 — Translation is evidenced as a verdict-layer fact.** The artifact's L3 already retains the full message, `tool_calls` included — the raw material of translation is therefore already durable before interpretation, by construction. What is missing today, and this piece adds, is the **translation record**: per call — provider call ID, ordinal, extracted name, arguments hash (over the parsed arguments' canonical form), resolution outcome, validation outcome (with the failing constraint where invalid), refusal class where refused, and the loop request_id where presented. The translation record is recorded with the iteration's adjudication in the record (the binding N11 names), and summarised in the artifact's L5 beside the two standing verdicts — the adapter verdict extended to state the translation outcome per call, or a third verdict component, *the examiner to rule on the form (OQ6)*; that it exists, is total (one entry per extracted call, `not_reached` with reason where translation never ran), and is recomputable is not optional.

**N33 — What the checker must be able to reconstruct.** From the record and the artifacts alone, in its own copies as established: (i) the catalogue the iteration presented (already reconstructed from the sealed grants, checker.py's own `_derive_catalogue`); (ii) the calls the response made (from L3 of the bound artifact); (iii) the translation of each call — re-running resolution and the pure schema validation (N8) deterministically over (ii) against (i) — agreeing with the recorded translation record, per call; (iv) the binding from each presented call to its TOOL_REQUESTED / dispatch / TOOL_OUTCOME or REJECTION chain, and from each refused call to its recorded refusal and its presentation in the following package; (v) doorway invariance at the record level: every dispatch in a native-mode run traces to a `request_tool` presentation whose contents equal the translated call's, with no dispatch lacking a translation record and no translation record silently lacking its adjudication. A native-mode history the checker cannot reconstruct this way is a failed history, however clean the run felt.

**N34 — The probe's evidence is not the worker's evidence.** The native-offer probe's artifacts (per-call classifications over raw captures) stand as probe evidence and are not re-used as worker-run evidence, nor does this piece change the probe. The classifications' *vocabulary* (offered / unoffered / malformed) is deliberately consonant with §3's classes, but the worker piece's records are the record's own events, under the Rev 8 regime.

**N35 — Uncertain outcomes stay uncertain.** A dispatch whose outcome stands uncertain is presented as uncertain under its call ID (the loop's standing rule — never upgraded), and a reconciled outcome is presented as reconciled, in the package where the cursor gives it. Native mode inherits the whole standing discipline of outcomes, including the stall-time accounting closure (R50).

## §7 Empirical unknowns — probed, not assumed

Each unknown names its probe shape and its reading, stated in advance. Probes are observation-only single-generation captures on the probe piece's settled pattern (the raw seam — `probe_raw_call` / the connector raw call — with responses captured whole under the evidence discipline), run only under their own release. No probe dispatches, executes, or answers a call.

**N36 — P1: an unoffered name, with tools offered.** *Unknown:* when native tools **are** offered and the model emits a call to a name **not** among them, what does this provider, on this route, actually do — return the call in the message's `tool_calls` (our resolver then refuses it, §3), refuse the whole response with a `tool_use_failed` 400 whose `failed_generation` carries the attempt, or silently drop the call? *Probe shape:* observation-only captures in a task context shaped to invite an unoffered call — the standing assignment context with a deliberately narrowed offered set (e.g. `sandbox.list` offered where the natural next step is a read), so the model's likely second-choice call is unoffered by construction. Narrowing the *offer* in a probe is legitimate: the probe tests the provider's delivery behaviour, dispatches nothing, and grants nothing. *Readings, stated in advance:* (a) the call arrives in `tool_calls` → the §3 resolver design stands as written; (b) a 400 with the attempt in `failed_generation` → the refusal path gains a seam: the attempt is extracted **from the error body as evidence**, classified and recorded as a refusal exactly as if delivered — salvage used as a *translation input*, never as an execution route (INDEX 345 §4's condition) — and the model-facing error result still travels in the next package, since no turn exists to preserve; (c) the call is silently dropped (a clean response, no trace) → the design records a known blind spot: an unoffered attempt the provider swallows is unobservable at this seam, stated in the build's account, and the closed world still guarantees it was not executed. **Sub-question P1b:** whether Groq's `disable_tool_validation=true` changes any of (a)–(c) under natural tool choice (the research documents that it does not lift `tool_choice` none/required enforcement; this design sends no `tool_choice`, so its effect on unoffered names under the natural setting is the unknown). The probe runs P1 with the flag off and on, as separate captures, and reports both.

**N37 — P2: multi-call response shape.** *Unknown:* does the pinned model on this route emit parallel calls in one message under the real task construction, and in what envelope — multiple `tool_calls` entries, each with its own `id`? *Probe shape:* first-response captures over a task context whose natural opening is two independent calls (two sources listable at once), on the settled five-trial pattern. *Readings:* multi-call messages observed → §4's semantics are exercised by reality, and the build's multi-call witnesses use the observed envelope; single calls only → §4 stands as designed defensively, and the build's witnesses use stub envelopes shaped like the observed single-call one, with the multi-call path explicitly marked unexercised live. Either way the design does not change; what changes is what the build may claim.

**N38 — P3: call-ID presence — a desk check before any live probe.** *Unknown:* do the provider's calls on this route carry `id` fields, present and distinct per call? *Shape:* re-read the already-captured native-offer artifacts (both runs' probe-evidence and retained bodies) — the bodies stand retained whole, so this is answerable from existing evidence with **no new provider request**. *Readings:* IDs present and distinct → N6/N11 stand as written; IDs absent or non-distinct → the binding falls back to ordinal correlation (provider call ID recorded as absent; the package correlates by ordinal and loop request_id), and N11's "under the original call ID" is amended to say so before any build. A live probe is authorised only if the artifacts cannot settle it.

**N39 — P4: tool-result message acceptance — conditional, probably moot.** *Unknown:* would this route accept a follow-up request carrying an assistant `tool_calls` message plus `role: "tool"` results, and continue coherently? *This probe exists only if the examiner rules Option B into consideration (OQ1).* Under Option A the design never sends such a message, and probing an unused behaviour would spend provider requests on architecture the piece does not build — empirical-before-architectural cuts both ways. If ruled in: single-conversation probe, one offered call, one stub result returned in the provider's form, the continuation captured whole; reading stated then.

**N40 — P5: arguments encoding.** *Observed, not unknown:* every delivered call to date carried arguments as a JSON string; the existing translator also accepts an object form. The build must accept both and refuse a third shape as `malformed_call` — no probe needed; the witnesses cover both encodings from stubs shaped on the observed bodies.

## §8 Non-goals, explicit

**N41 — No direct environment execution.** Nothing in this piece executes a provider call, a translated request, or an error body's contents except through `Doorway.request_tool` → recorded dispatch → the executor. `container.exec` is a refusal class, never a route.

**N42 — No salvage as foundation.** `failed_generation` recovery is not the worker loop's mechanism. Its only contemplated use is P1 reading (b)'s: as *evidence and translation input* for a refusal, under the same recording discipline — never as a dispatch source, never executed from the error body (INDEX 345 §4).

**N43 — No second authority path.** No new grant source, no adapter-side permission cache, no doorway bypass for "obviously fine" calls, no policy decision taken anywhere but the doorway. The adapter's resolution and validation classify; they never permit.

**N44 — No change to grants, bounds, assignment, or record semantics.** The sealed grants, the step ceiling, the activation deadline, the first-worker assignment, the event types' meanings, and the stall grounds are all exactly as they stand. This piece adds: per-call translation, per-call refusal records, a pure schema validator, call-ID carriage, and a package field. It amends no existing contract's meaning; where an existing behaviour changes (fail-whole translation, N13), the change is named in this scope and witnessed in the build.

**N45 — No generality claim.** This piece is for the pinned model (`openai/gpt-oss-120b`) on the Groq route, under the task shapes the framework actually runs. It does not claim native-first is right for other models (the research's own counter-evidence stands: on parameter-free selection, text beat native on average across models — just not for this one), and a future model or route change re-opens the mode question under N28's judgement discipline, with its own probe evidence.

## §9 Acceptance shape for the eventual build

The build, when Ben authorises it, passes examination on witnesses of these shapes (stub-provider witnesses in the suites' established pattern, plus the checker over the produced records):

**N46 — W-a, translation fidelity.** A stub native response carrying a well-formed offered call produces exactly the typed request its text-form twin produces — same tool, same parameters, byte-equal after canonicalisation — and the iteration's record from adjudication onward is identical in shape to the text-mode record of the same request.

**N47 — W-b, doorway invariance.** Across a matrix of stub responses (offered, unoffered, malformed, schema-invalid, doorway-refusable, mixed), every dispatch that occurs traces to a `request_tool` presentation, every refusal is recorded under its §3 class before any package presents it, and zero dispatches occur for refused calls. **N48 — W-c, closed-world refusals.** A stub response calling `container.exec` (and, separately, a built-in-shaped name and a near-miss of a granted name) yields: a recorded `unknown_tool` refusal, zero TOOL_REQUESTED events for it, zero dispatches, and an N16 error result in the next package naming the offered alternatives — while a sibling offered call in the same response dispatches normally (N21).

**N49 — W-d, per-call granularity.** A multi-call stub response with one unparseable-arguments call, one schema-invalid call, and two valid calls: two dispatches, two recorded refusals of the right classes, results assembled in call order under their call IDs (N24), the iteration completing without a stall.

**N50 — W-e, evidence and checker reconstruction.** A governed native-mode run over stubs: every iteration's artifact binds, L3 retains the calls, the translation record stands total per call, and the independent checker reconstructs §6's (i)–(v) and reports all-ok. The text-mode suites and the evidence suites pass at their standing counts, unweakened; a text-judged assembly's packages and requests are byte-identical to before the build (the text path's regression witness).

**N51 — The first live demonstration.** The natural candidate is the standing first-worker assignment — the three sealed sources read, the plain-words brief written — under a **fresh assembly judged native**, on the pinned model and route, with the evidence regime live. It is *not* part of the build's acceptance: it requires its own release examination (the mode judgement under OQ7, the run's bounds, and — learned from INDEX 339/352 — a **pacing plan against the provider's measured token budget**, since a multi-step run makes several large calls in a minute's span and the release must plan for that rather than discover it). The build's passage establishes that the adapter *can* translate under examination; the demonstration establishes that a worker *did* work. The two claims are never merged.
