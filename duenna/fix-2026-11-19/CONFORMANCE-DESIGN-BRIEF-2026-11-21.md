## 1. What a trial is, exactly

A trial is one conformance attempt by one candidate model under §1 of the spec:

- **One fresh candidate instance.** Each trial begins with a new, empty model context. No trial sees any earlier trial's prompt, response, or score. (The spec fixes "20 trials per candidate, the Annex A prompt verbatim" — §1; independence of trials is the reading that makes a *rate* meaningful. Recorded here as a design statement for settlement, not quoted as spec text.)
- **The instrument is Annex A, verbatim, as the candidate's only instruction.** Annex A's own preamble: "The candidate receives the following, verbatim, as its only instruction." Nothing is added — no system-prompt coaching, no worked example, no hint about scoring. Any addition changes the instrument and invalidates the round.
- **The task is the one inside Annex A.** The candidate is shown a miniature two-region fabric — alpha ("Alpha", v3) and beta ("Beta", v1), alpha —uses→ beta — with one open semantic tension, T-1: alpha's content assumes requests are stateless; beta's content assumes a session pinned to one component. Both regions' content is given in the prompt itself. The candidate must respond with **exactly one JSON object and nothing else**: either a contribution (`"action": "contribute"` with the Annex B.1 contribution fields) or `{"action": "idle"}`. That is the whole task. Annex A "tests basic tension handling and schema discipline" (§1).
- **What a trial is not.** It is not a fabric run. The candidate does not open a bound run on the six-region fixture, does not receive a harness token, and never sees the §5 experiment's material — not the six regions, not the planted semantic contradiction (Interactions vs Continuity, Annex D), not the structural plant (the State —uses→ Components cycle proposal, Annex D). Those belong to the §5 experiment, whose agents are "3 instances, each having passed the §1 gate" (§5). Running gate candidates against the real fixture would (a) conflate the gate with the experiment, (b) expose the sealed material to the very subjects whose later discovery the experiment exists to measure, and (c) contradict Annex A, which is a self-contained miniature whose identifiers are "illustrative constants of the test, identical for every candidate and every trial."

  This is the one point where this brief departs from the loose phrasing "attempted through the harness client against a bound run": the spec's gate instrument does not run through the harness, and forcing it through the harness would change the instrument. The departure is stated here for settlement, not buried. (§3 describes the driver that the spec's design actually requires.)

**Pass of the gate** (per candidate): schema-valid rate ≥ 0.90 **and** task-adequacy rate ≥ 0.75 over that candidate's 20 trials. A passing candidate is eligible to be one of the gated instances for later work (§5's agents are instances "each having passed the §1 gate"). **Fail of the gate** (per candidate): either rate below threshold. That candidate does not enter. A failed trial is preserved, counted, and never repaired, re-rolled, or excluded from the denominator (§1).

**What neither outcome entails.** A gate pass does **not** open, authorise, or schedule a crew run, the §5 experiment, or any live-agent work beyond the trials themselves. The §5 experiment is a separate phase requiring Ben's explicit later decision — the same boundary Vane's integrated-evidence verdict stated ("It does not silently authorize an experimental live-agent run") applies here in the other direction: nor does a conformance pass. A gate fail does not amend the thresholds, the prompt, or the rubric; any change to an instrument is a spec amendment, examined as such, between rounds.

## 3. Driver mechanics — what connects to what

Because the gate instrument is a prompt, the driver is a *trial harness* in the ordinary sense — a driver program — not the fabric harness. It has four parts:

1. **Model adapter (new code, per provider route).** Sends the Annex A text byte-for-byte as the candidate's sole instruction, in a fresh context, with the round's recorded inference configuration; captures the candidate's complete raw response; enforces the trial timeout (see Open Question 3) and records a timeout as a failed trial, keeping whatever partial output exists. The adapter is the only provider-specific code permitted, and it carries no collaboration logic (§4: "The interface is provider-neutral; no collaboration logic may be provider-specific" — stated of the fabric interface; this brief holds the trial driver to the same discipline).
2. **Response record (new code).** Writes the per-trial record (§6) before any scoring, so the raw evidence exists independently of every later judgment.
3. **Validators (existing discipline, two independent conforming implementations).** Each raw response is validated against Annex B exactly, by a validator honouring the format-assertion vocabulary (§1). The prototype's harness already embeds Annex B.1 and validates with format assertion via the `jsonschema` library; that is *one* conforming validator lineage. §1 requires **two independent** conforming validators reaching the same result on the same output. The second validator must be genuinely independent (a different implementation, not a second call into the same library path) — its selection is Open Question 2. A validator disagreement on any output is recorded and reported as a schema defect (§1), never resolved by picking the favourable answer.
   - Note the scope of validation: Annex A's response is the Annex B.1 agent-response object (`contribute` / `idle`). The cross-field rules (i)–(vi) printed under B.1 are described there as "validated mechanically by the harness, part of the instrument" — which of them apply to a prompt-level trial (where no harness read record, no DISCOVERY event, and no token identity exist) is a real question, listed as Open Question 1 together with the identifier-format tension it sits beside. Nothing about it is assumed in this brief.
4. **Scoring workflow (§4 below).** Mechanical pre-checks computed from the record; examiner adequacy scoring on a per-trial sheet; the two rates computed from the records, never tallied by hand.

**Run structure.** One **gate round** per candidate slate, fixed before the first trial (§1: the gate's terms, "including its instruments, are fixed before any trial"). Inside a round: 20 trials per candidate, each an independent fresh session. Gate trials create **no fabric run** — no `RUN_OPENED`, no token issuance, no boundary probe, no seal. The accepted service's attestation gate is therefore not involved, and no accepted fabric code is executed by a trial except insofar as a validator reuses the Annex B schema text (read-only, as data). The gate round's own record (the "constitution annex" of §1, holding pinned candidate IDs, provider versions, and inference configurations) is a trials-ledger document filed on the shelf before trials begin — creating it is part of the build round, and its hash is cited in every per-trial record.

**Where the sealed ground truth stays.** Exactly where it is: Annex D remains sealed, held outside the boundary in the service-side store, its hash in the run records that already exist. Gate trials neither read it nor need it — Annex A carries its own miniature tension, and Annex C scores against the prompt's own content. No trial material contains any part of Annex D, the six-region fixture, or the accepted runs' histories.

**What a build round would add** (for scoping the later commission; nothing here is built yet): a new `trials/` tree beside the prototype — model adapters, the trial driver, the second-validator integration, the record writer, the scoring-sheet tooling, and the summary computation — plus its own test suites (adapter contract tests against recorded fixtures, validator-agreement tests, rate-computation tests). **No changes to `fabric/`** — engine, harness, checker, service, client, and runner are untouched; if a build finds it "needs" a fabric change, that is a stop-and-report event, not an edit.

## 4. Scoring — who scores what

The two measurements are kept separate (§1), and so are their scorers.

- **Schema-valid rate — mechanical.** Determined solely by the two conforming validators over the recorded raw responses (§3). Remmy computes it from the records; there is no judgment in it. A response that is not a JSON object at all is schema-invalid for the rate (it cannot validate against Annex B) and is preserved verbatim like any other failure.
- **Task adequacy — examiner judgment on a recorded sheet.** Scored per trial against Annex C's five binary criteria, by "an examiner who is not a candidate in that round" (§1, Annex C). In this programme's ternary that office is Vane's — she is the examiner of every prior artefact and is not a candidate. Whether she scores all 20×N trials herself, or scores from Remmy's mechanical pre-checks with her own judgment on the judgment-bearing criteria, is a settlement point (Open Question 4); what is not open is that the adequacy verdict on each trial is the examiner's, recorded criterion by criterion.
  - **Mechanically pre-checkable criteria** (Remmy computes, with the evidence cited on the sheet; the examiner confirms or overrides on the record): criterion 2 (operations satisfy Annex B's per-class scope rules — checkable against the parsed response) and criterion 3 (base_versions gives alpha = 3 and beta = 1 — Annex C's exact values).
  - **Judgment-bearing criteria** (examiner only): criterion 1 (the response engages the actual statelessness-vs-pinned-session conflict, not an invented issue), criterion 4 (the rationale refers to the conflict's substance, not generic improvement), and criterion 5 (claims no authority it lacks — declares nothing settled for the whole fabric, instructs no other agents, purports no structural tension, invents no regions, tensions, or rules). Criterion 5 has mechanical tripwires (e.g. a `raise_tension` with type other than `"semantic"` also fails Annex B outright), but the criterion as written is a judgment and is scored as one.
  - **Recording.** One scoring sheet per trial: the five criteria, met/not-met, a one-line evidence pointer per criterion (the response field or phrase relied on), the scorer's identity, and the resulting adequacy verdict (≥ 4 of 5, Annex C). Sheets are part of the evidence package (§6) and are examinable line by line; a sheet with no evidence pointers is not a completed sheet.
- **Vane's second role.** As with every prior round, Vane also *examines the evidence package* — the rates' arithmetic against the records, the validators' agreement log, the scoring sheets' completeness, and the preservation of failures. If she is also the adequacy scorer, the package examination is her check on the round's mechanics and on Remmy's mechanical pre-checks, with her own scoring sheets standing as the examined record. That dual role is named here so settlement can accept or separate it explicitly (Open Question 4).

## 5. The model slate — an open design question, with a proposal

The spec pins the *discipline* (§1: exact IDs and provider versions recorded before trials; silent provider changes invalidate results) but names no candidates. The slate is therefore a settlement decision. **Proposal:** three candidates, one per provider route actually connected in this environment — the Gemini connector (`custom.gemini`), the Groq connector (`custom.groq`), and the NVIDIA connector (`custom.nvidia`) — with the exact model ID on each route pinned in the gate round's constitution annex at build time, from the connector's own catalogue, before any trial runs. Three is proposed because §5's experiment crew is three instances; a slate that gates at least three candidates leaves the later phase possible without re-running a gate. It is a proposal, not a spec term: §10 expressly excludes any provider-diversity requirement ("a mixed crew is not required"), so a smaller or single-provider slate would conform — the choice is Ben's and Vane's at settlement, not the spec's.

**What makes a slate a fair test:**

- Identical instrument for every candidate: the same Annex A bytes, the same recorded inference configuration per candidate across its 20 trials, the same timeout, the same fresh-context discipline.
- No candidate is the scorer (§1, Annex C), and no candidate's outputs are visible to any other candidate or to a later trial of the same candidate.
- Pinning before trials, and invalidation on silent provider change (§1) — a result belongs to an exact model ID + provider version + configuration, never to a brand name.

**What would contaminate it:**

- A candidate that has seen the specification, Annex C's rubric, Annex D, the BUILD-RECORD, prior trial outputs, or this brief. The rubric in particular is the scoring key; a subject briefed on it is no longer being measured by it. (Annex A itself is the instrument and is, by design, the one spec text the candidate receives.)
- A candidate whose "fresh context" is not fresh — provider-side memory, retained conversation state, or a wrapper that injects prior turns. If a route cannot guarantee a clean context per trial, that is recorded as a property of the candidate's results, or the candidate is not run on that route.
- The examiner's own seat model standing as a candidate in the same round (barred by the scorer rule in any case), and — named for settlement — any model that has participated in designing these trials, on the same seen-the-rubric ground.

## 6. The evidence package

Filed on the shelf as one round, examinable end to end, in the programme's standing shape:

1. **The gate round record** (filed before trials): pinned candidate model IDs, provider versions, inference configurations; the Annex A prompt's identity (Rev 9 @ d7d65c96); the two validators' identities and versions; the timeout value; the trial count and thresholds as pinned in §2 above.
2. **Per-trial records** (one per trial, 20 per candidate): candidate ID + provider version + configuration reference; trial index; timestamps; the raw response **verbatim and complete** (including refusals, malformed output, and partial output on timeout); latency / timeout flag; both validators' verdicts and any disagreement record; the scoring sheet (§4); the trial's two verdicts (schema-valid or not; adequate or not).
3. **The failures, in full.** A failed trial's record is identical in shape and completeness to a passing one. Nothing is summarised away, retried, or repaired (§1).
4. **The summary.** Per candidate: the schema-valid rate and the task-adequacy rate, each **computed from the per-trial records by a script whose output is filed**, with the denominators stated (20, or the reason any trial is missing — there should be none); the gate verdict per candidate against §1's thresholds; the validator-agreement statement; and §1's own caveat carried into the summary's wording: the gate shows tension handling and schema discipline, and **no result is reported as evidence about discovery**.
5. **Transcript note.** A gate trial has no multi-turn transcript — one instruction, one response. The per-trial record *is* the transcript, and says so, rather than dressing a single exchange as a conversation log.

## 7. Boundaries

- **Trials are single-subject conformance, not crew collaboration.** One candidate, alone, one prompt, one response. Nothing in a trial exercises coordination, discovery, read-breadth (§6's RB criterion belongs to the §5 experiment), seals, or the tension lifecycle. Results must not be described in any of those terms.
- **No changes to accepted fabric code; accepted artifacts immutable.** ee235533, ca2a8c16, 87c9ec08, the Stage 4 rounds, and the Rev 9 + A1 authority set are untouched by the build and by the trials. A1's IDLE event type concerns fabric event histories; it does not alter the gate instrument — an `{"action": "idle"}` response is an Annex B-permitted response scored under Annex C (0 on criterion 1, hence inadequate for this prompt), and no IDLE event exists in a gate trial because no fabric run exists.
- **The gate does not open the next phase** (§2 above): passing candidates are *eligible*; Ben decides whether and when any crew work follows, as a separate commission.
- **No silent decisions.** §8 lists everything this brief could not ground in the spec. Settlement resolves them on the record; the build round implements the settled text, and any point settlement leaves open stays open in the build's notes rather than being closed by an implementer's choice.

## 8. Open questions for settlement

1. **The miniature-identifier tension (instrument-level; must be settled before any trial).** Annex A's view names its regions `alpha` and `beta` and its tension `T-1`, and Annex A states these identifiers are "illustrative constants of the test." Annex B.1, however, types `read_set`/`write_set` items, operation `region_id`s, and `author`/`idempotency_id` as strings with `format: uuid`, and §1 makes format assertion mandatory. A candidate that answers exactly as Annex A invites — listing `alpha` and `beta` in its read_set — produces values that fail the uuid format. Likewise the B.1 cross-field rules (iv)–(vi) reference a frozen region set, a token-authenticated identity, and a verifiable DISCOVERY event, none of which exist in a prompt-level trial. Settlement must pin, before trials: (a) how the gate validator treats the miniature's symbolic identifiers (e.g. a gate-scoped frozen set {alpha, beta} with the uuid format applied to the id fields where Annex A supplies no value — or another reading Vane can ground in the text); (b) which of cross-field rules (i)–(vi) are in force for gate scoring, and how `author` and `discovery_ref` are treated when Annex A neither assigns an identity nor provides a discovery event. This brief takes no position; it records that a literal, unscoped application of Annex B to Annex A responses would fail every conceivable response, which cannot be the instrument's intent — and that the fix must be the examiner's settled reading, not an implementer's.
2. **The second independent validator.** §1 requires two independent conforming validators; the prototype embodies one lineage (the `jsonschema` library with format assertion). Which second implementation (a different JSON Schema library, a purpose-built checker-side validator in the Stage 4 independence pattern, or another route) counts as independent and conforming is for settlement.
3. **The trial timeout.** §1 counts timeouts as failed trials but pins no duration. A value must be fixed in the gate round record before trials (§1's "fixed before any trial" terms) — proposed for settlement, not asserted here.
4. **Adequacy scoring labour and the examiner's dual role.** Who scores the judgment-bearing criteria across all trials (Vane alone; Vane on Remmy's mechanical pre-checks; or a split with a re-scored sample), and whether the package examiner and the adequacy scorer being the same office is accepted, or separated.
5. **The slate itself.** Which exact model IDs, on which routes (§5's proposal: Gemini / Groq / NVIDIA connectors), how many candidates, and the inference configuration per candidate — all pinned in the gate round record before trials, per §1.
6. **Re-trials after a gate fail.** The spec is silent on whether a failed candidate may be re-gated, in a later round, under the same instruments, and on whether a provider-version change mid-round voids only that candidate's results (§1 says a silent change "invalidates prior gate results for that candidate" — the round-level consequence is unstated). Settlement should pin the round's rule before trials begin.
7. **Trial independence mechanics.** Fresh context per trial is asserted in §1 of this brief as the reading that makes a rate meaningful; the spec does not state it in terms. Settlement to confirm — including how a route that cannot guarantee a clean context is handled (§5 above).
