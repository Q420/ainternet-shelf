1. B1-6 — Option A recommended, subject to specific design corrections

Option A recommended

I agree with Remmy's recommendation: the launcher should remain the child's OS parent and reaper; the Python supervisor should own the records, issuance and authoritative lifecycle decisions.

The division is coherent:

- Spawn and establish child — Launcher
- Child's OS parent — Launcher
- waitpid() — Launcher
- Child privilege transition — Child, under launcher-controlled sequence
- Terminal-event decision — Supervisor
- Issuance and commitments record — Supervisor
- Report child exit status — Launcher
- Independent examination — Examiner

This preserves the parent relationship on which the existing child PR_SET_PDEATHSIG design depends. It also avoids making the supervisor pretend it can waitpid() a process that is not its child.

Option B is not an acceptable substitute as currently described. There is a material Linux detail missing from its reasoning: when the child has already armed PR_SET_PDEATHSIG against the launcher with SIGKILL, termination of the launcher triggers that signal. The child does not get a safe opportunity to re-arm against the supervisor. Deferring arming until after reparenting instead introduces the race Remmy identified.

The Linux documentation also explicitly says the parent is the thread that created the child, and that a parent-death signal is sent on termination of that thread. See the Linux PR_SET_PDEATHSIG documentation.

Four matters Option A must resolve before I recommend it for adoption

A. The launcher-to-supervisor parent-death race

The proposal says the launcher drops root and then arms its own parent-death signal against the supervisor. That ordering is correct because credential changes can clear the setting.

But it needs the same race protection already specified for the child:

Supervisor captures its own expected PID before launching.

That expected identity reaches the launcher through the fixed, validated launch request.

Launcher drops privilege.

Launcher arms and reads back its parent-death signal.

Launcher verifies that its parent is still the expected supervisor.

Any mismatch or failed read-back aborts the launch.

Simply calling getppid() after arming is insufficient if the supervisor already died before the launcher armed the signal: the launcher could observe its reaper as its parent and mistake that for the original supervisor.

B. The supervisor's spawning thread

The Linux parent-death relationship is thread-based, not merely process-based. The supervisor must therefore guarantee that the thread which spawned the launcher remains alive for the entire launcher lifecycle, or explicitly design around that fact.

The launcher being single-threaded is necessary for the existing child-parent reasoning, but it does not by itself establish the supervisor side.

C. Launcher loss and terminal-event closure

This is the most important remaining lifecycle issue.

The proposal says that if the launcher dies, the child receives SIGKILL, the supervisor sees EOF without a status word, and the supervisor records LAUNCHER_LOST.

The signal delivery does not itself prove that the child has already terminated when the supervisor closes the issuance.

The design must prevent a terminal record from being written while the child might still be executing.

My preferred solution is a child pidfd transferred to the supervisor before the launch gate is released. The supervisor can then observe actual child termination even if the launcher disappears. The design must define what happens if the descriptor transfer fails or the launcher dies before the supervisor receives it.

At minimum:

No gate release before the supervisor has the required child-lifecycle handle.

No terminal closure merely because the launcher descriptor reaches EOF.

No successful issuance after launcher loss.

If child termination cannot be established, the issuance remains unresolved and the run halts pending recovery.

D. Status-channel contract

The proposal needs to specify the descriptor protocol precisely: request framing, status framing, descriptor ownership, close-on-exec behaviour, EOF semantics, malformed or partial messages, and acknowledgement of the pre-release handoff.

The supervisor must distinguish a valid child exit report from a truncated status message or an unexpected launcher death.

My recommendation to Ben

Option A is the technically preferable architecture. Option B should be rejected in its proposed form.

I recommend that Ben approve Option A only with the four matters above incorporated into the architecture decision. This is a recommendation, not an architecture ruling. No Rev 15 amendment should be drafted until Ben decides.
